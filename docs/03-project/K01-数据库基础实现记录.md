## 第二批：数据库任务/项目删除（2026-09-13）

已补充 `WorkspaceRepository.deleteTask/deleteProject` 与数据库验证服务的DELETE接口。请求必须提供revision，身份由认证取得；管理员同样不能删除其他用户数据。删除消息与关联记忆全部在线修订正文，保留无正文的遗忘标记和outbox清理事件，推进knowledge epoch；项目/任务名称替换为固定删除占位名称。项目删除同时清除成员关系及子任务，单任务删除保留项目记忆，项目删除保留个人记忆。记录ID、归属和workspace key保留用于后续文件清理，不能称为物理删除所有元数据。

父项目、任务、记忆采用一致的事务锁顺序，创建子任务/项目记忆及写入任务消息/记忆与删除串行化；删除失败不部分提交，重复删除幂等，旧revision冲突返回409。queued/running/waiting任务当前返回409，整项目存在这些任务时不清理任何子项；尚未实现数据库执行取消，不以修改状态假装取消成功。

### 第十一批：聊天文件入口与消息引用（2026-09-14）

- schema v8增加task_runs.attachment_ids（最多10个具体文件版本）。附件与运行/用户消息在同一事务提交；拒绝重复ID、不存在、已删除和不属于当前任务的文件，即便同一用户其他任务的文件也不能直接引用。重试同时核对正文和附件ID顺序，不重复创建消息。数组保留已删除版本的无正文ID用于幂等，不保留文件名副本。
- 历史页、轮内补拉和增量事件均动态读取附件名；删除原件版本后返回“附件已删除”，不回传名称。已有客户端内存中的旧消息要重新读取才更新占位，实时删除广播尚待后续。模型上下文注明附件尚未解析，不注入原件内容，也不声称已读取文档。
- 数据库客户端在输入框上方接入添加文件：选中即上传，显示SVG类型图标/文件名和上传中、已上传、失败状态；上传未完成/失败不允许发送，失败需移除后重选。仅有附件也可发送，后台接收成功后清空托盘；消息保留图标和名称，不提供内嵌打开链接。移除待发送附件只取消本次附带，不删除已上传服务器原件。
- 原件上传仍是application/octet-stream，名称只作元数据；每消息最多10附件、单文件10MiB。health.filesEnabled控制入口，未启用文件仓储的后台不显示按钮。请求失败且内容/附件未改时，在当前页面内保留同一requestId供手动重试；刷新后的请求恢复尚未实现。切换任务会取消未完成上传并清空当前附件草稿，已落盘但未关联文件暂留后台，跨任务草稿恢复待完善。

### 第十批：K02文件原件与版本基础（2026-09-14）

- schema v7添加documents/document_versions，任务归属、当前版本、名称、字节数、SHA256及请求幂等键入库；两表强制RLS和归属外键，管理员不能访问其他用户资料。文件按随机版本ID保存在服务端，用户文件名不参与路径构造。
- FileRepository保存不可变原件并保留历史版本；同一requestId重试不重复写入，不同内容重用请求返回409；更新和删除携带revision。上传与按用户回收持有同一事务锁，下载与任务删除串行。磁盘写入或数据库提交出现异常时不冒险删除可能已提交的原件，无引用文件由collect回收。
- GET `/api/tasks/:id/files`返回当前版本；POST同路径以application/octet-stream上传，query提供name、requestId，新版本另加documentId、revision；GET `/api/tasks/:id/files/:documentId/versions`列历史；GET `/api/tasks/:id/file-versions/:versionId`验证大小/校验值后作为附件下载。DELETE文件路径删除元数据和全部版本，随后回收磁盘原件。
- 任务和项目删除同步清除关联版本元数据，立即阻止读取；启用文件仓储时HTTP删除随后回收原件。磁盘清理失败返回cleanupPending=true，用户可POST `/api/files/cleanup`重试。崩溃遗留对象、备份副本不会被宣称已自动清除；定时全用户回收worker及备份遗忘后续实现。
- 初始限制：单文件10MiB、单用户全部历史版本100MiB、每任务100文件、每文件100版本。未提供自动淘汰旧版本或配额管理UI。

启用要求：先用独立结构账号升级schema至v7，再配置服务器`WORKPIVOT_DATABASE_FILES_ROOT`到专用可写持久卷。默认不启用文件API；文件根目录不对外静态托管。当前部署脚本仍对应已发布的v6，不能直接用本批源码覆盖线上容器而不升级结构和配置文件卷。

验证：W38临时PostgreSQL15集成203/203通过，含26项新增文件检查：HTTP二进制上传/下载/删除、UUID规范化、损坏拒绝、用户隔离、幂等、并发版本、原件不可变、任务/项目删除清理与孤立对象回收；类型/lint通过，临时容器和文件清理完成。本批仅后端基础，未接上传界面、聊天附件引用、解析、RAG、语义去重及跨资料遗忘，不代表模型已能阅读上传文件。未重新部署公网。

### 第七批：数据库持久授权与MCP执行接通（2026-09-13）

- v6新增run_permissions，按用户强制RLS，授权绑定任务/运行并存储请求、决定、期限及消费状态。请求和任务waiting状态、确认事件在事务内写入；默认3分钟，当前只允许本次MCP外部调用，不支持永久授权或任意文件/命令授权。
- 提供GET `/api/tasks/:id/permissions` 查询有效待确认请求、POST `/api/tasks/:id/permissions/:permissionId` 允许/拒绝。相同决定重复提交幂等，冲突决定拒绝；管理员不能查询或确认其他用户请求。任务保持等待，直到执行器消费决定后恢复running。
- 消费在运行令牌/租约校验与事务锁下执行，允许结果仅一次有效；超时默认拒绝。停止、完成和过期运行恢复取消未消费授权；删除任务/项目清除授权正文。新服务实例可读到同一待确认请求，旧执行器失效后授权不能用于新的运行。
- DatabaseExecution默认对外部调用创建持久确认，发送permission_request并轮询结果；非外部文件/命令仍拒绝。决定/超时事件保存在历史补拉流，客户端接入时须消费这些事件清除卡片；尚未实现独立的实时决定通知订阅。
- 显式数据库对话验证开关开启后，从当前用户数据库加载启用MCP工具，执行前经持久授权；filePolicy仍拒绝文件访问。该入口仍为独立接口验证，不承诺原正式页面可直接兼容。
