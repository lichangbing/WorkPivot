# 后台管理强化计划（2026-10-16）

## 范围与当前状态

用户要求强化后台，已确认 token 按每月额度管理，并进一步确认将本文件列出的后台能力统一纳入开发计划。当前阶段先完善计划与需求，不进入业务代码开发。模块范围已确认，涉及权限、额度处置和知识库目标的具体行为仍需逐项确认。既有管理页面、产品需求和历史计划不等于当前数据库实现已完成。

当前模型注册、默认模型、密钥加密、用户创建与密码重置已有基础；数据库后台仍有未接入页面。模型流协议尚未完整采集供应商 usage，也没有用户级用量账本、月额度及查询管理闭环。后续实施前再次核对代码与当前改动。

## 已确认：用户用量查询与后台每月额度管理

### 产品行为

- 用户查看自己的本月、今日及指定时间段用量，按模型、项目、任务和用途查看明细；不得查询其他用户。
- 管理员按用户、模型、时间及用途查看汇总和明细，配置用户每月额度、调整并留审计。
- 周期采用北京时间 Asia/Shanghai，每月 1 日 00:00 开始新周期；保留历史记录，不通过删除账本实现重置。周期归属以模型请求开始时间为准，跨月请求不重复计数。
- 额度限制默认关闭；无额度配置不隐式限制用户。用户已确认：开启限制后额度不足时阻止新模型请求，提示联系管理员调额；不静默截断已有输出。硬限制模式须先完成预留与结算方案。
- 额度为模型 token 数量，不是充值余额、供应商金额或积分；暂不实施支付、发票、计费审批及价格换算。
- 新增额度管理是本次对历史 J05“只统计/可选积分”的范围补充；不借此提前实施完整 K10 多用户调度。

### 计量与实现约束

- 按实际使用者归账，共用管理员模型密钥不把所有用量记到管理员。
- 记录输入、输出、可用的缓存明细和供应商实际返回用量；缓存是否包含在输入中按协议规范归一化，不能重复累加。
- 区分对话、上下文摘要、记忆整理和专家经验整理等现有模型调用用途。后续知识库 embedding/重排接入时分别计量，不提前伪造这类记录。
- 缺少 usage、中断或供应商错误导致统计不完整时标记未知/不完整；不把未知显示为零，不声称估算等于供应商账单。旧历史无原始用量时不倒推成准确数据。
- 工具循环中的每次模型请求、辅助请求和实际重试分别记录；幂等写入防止重复结算。请求关联用户、模型、时间、用途及可取得的项目/任务标识，不记录提示正文或密钥。
- 开启额度限制前完成原子准入、并发预留、最终结算和未知用量处置设计；后台调额保留版本与修改者，避免只读余额再扣减的竞态。
- 用户请求、后台作业与管理员检查统一计量边界；不能绕过主对话限制继续无限运行辅助模型。未发送模型请求前的拒绝与可能已到达供应商的请求分别处理。
- 不新增 LangChain/Agent 框架依赖；先沿现有 ModelClient 和数据库权限边界实施。重要数据模型与未知额度处置策略在编码前形成可审阅方案。

## 知识库权限、时效与存储方案（设计建议，具体规则待细化）

### 内置知识库与 PostgreSQL

用户补充要求增加内置知识库。建议与当前业务系统共用 PostgreSQL 服务及现有 workpivot schema，在独立的知识库/资料/授权/索引作业表中组织数据；不要再创建一套账号或把业务关系复制到另一数据库。现有 knowledge_versions/knowledge_chunks 和解析/原件版本机制是复用基础，不能标为完整独立知识库管理已经实现。

数据库保存知识库及资料元数据、提取的文本片段、索引、权限、版本、来源和作业状态；Office/PDF 等原件继续进入现有后台文件存储，不默认塞入数据库大字段。语义检索阶段评估同一 PostgreSQL 中的 pgvector 与 embedding 服务，先明确模型、部署支持、维度和索引迁移；有向量索引不等于具备 embedding 模型。初期不另起向量数据库、不迁移 Agent 内核，后续仅在容量与性能证据支持时拆分。

外部知识库通过后台适配其检索 API/MCP；默认按需检索，不未经确认全量复制外部资料。内置与外部返回统一的来源、版本和权限结果，但保留数据源身份、检索时间与能力差异。

### 必须明确的权限边界

- 分开“配置知识库连接”“授权谁可以使用”“阅读资料内容”。后台管理员可配置连接不等于默认可读所有私有知识、聊天或记忆。
- 用户可用知识库与当前项目绑定范围取交集；若上游有文档权限，还须按当前用户身份或可靠的权限映射执行文档级过滤。账号/组映射来源和更新方式在具体集成时确定，不先引入完整部门平台。
- 权限必须在片段进入模型前由服务端/上游检索服务执行，正文、摘要、标题和引用均不能交给模型自行判权。返回结果后的界面隐藏不能补救已进入模型的越权内容。
- 上游只有管理员全量密钥时，不声称已经继承用户文档权限；需可信 ACL 同步、权限隔离的数据集/连接或仅接入已确认对该范围公开的库。权限无法判断时拒绝或明确不可用，不自动扩大访问范围。
- 缓存、原文查看/下载、引用核对和后续对话复用均需守住同一权限边界；缓存不能仅按问题文本共享。撤权或删除后不继续将旧片段/派生记忆送进新模型请求。

### 时间与版本不是一个字段

- 分别保存文档版本、更新时间、索引/同步时间、检索时间；有适用期的资料另保存生效/失效日期。报表的业务期间独立记录，不拿文件修改时间代替。
- 默认使用当前有效且索引就绪的版本；上游更新但新索引未就绪时明确旧版本状态，不能静默标为最新。询问历史时按指定期间检索，不能只选最后上传的文件。
- 上游权限与资料更新的通知/轮询、缓存失效和最长允许延迟按系统能力确认；不凭空承诺立即同步。失效后阻止后续引用与上下文复用，已经发送给外部模型的数据不能声称可以撤回。
- 多来源冲突时并列标明出处、版本和适用期，不让模型按“较新”自动判定事实正确。日志保留与源文档有效期分开管理。

### 其他需要纳入验收的情况

- 只读检索的超时、取消、有界重试与限流；区分“没有命中”“无权限”“索引未完成”“上游不可用”，不把故障当成资料不存在。
- 返回带出处的片段，不只返回无法核查的上游生成答案；能力不足时标记限制。检索数量、片段大小和上下文预算有上限。
- 文档是资料而非指令；不因文档中的命令自动运行工具、外传文件或提升权限。检索词及片段是否发往外部知识库/模型、日志是否含私有内容要明确。
- 区分知识库检索服务费用、上游生成答案 token 与 WorkPivot 自己模型 token；上游不返回用量时保留未知，不用同一 token 数重复扣账。
- 必测跨用户/项目拒绝、文档撤权、缓存命中后的权限变化、旧版本/过期资料、引用失效、删除传播及跨会话复用；知识库事实不自动提升为私人长期记忆。

后续优先确认：外部系统名称和接口、内置知识库的个人/项目/企业共享范围、是否需要带生效期的制度类检索。权限模型需与已确认的私人数据默认不可见一致。
