# ADR-004：业务事实采用项目级 PostgreSQL 权威模型

| 项 | 值 |
| --- | --- |
| 状态 | ✅ 已接受、实现并部署 |
| 日期 | 2026-10-28 |
| 关联 | [PRD-08](../product/PRD-08-业务事实.md)、[业务事实架构](../architecture/业务事实模型与项目检索-20261028.md) |

## 背景

原始对话和交互记忆会包含推测、修正和前后矛盾。将它们直接作为项目事实会造成旧值与新值
同时召回、实体串项目、金额无法计算和来源不可追溯。业务事实需要稳定实体、类型化值、历史版本、
证据和可见范围。

## 决策

1. PostgreSQL 是业务对象、事实、关系、证据、冲突和版本状态的唯一权威存储。
2. 首版使用 PostgreSQL 复合索引、JSONB、全文查询和递归 CTE；向量只作后续候选增强。
3. 所有业务事实数据强制包含 `project_id`，临时任务不生成事实。
4. 事实使用稳定 series 和不可变 revision；关系采用相同模式。
5. 无冲突新增可自动发布；值变化、替代、合并和关系冲突需要用户确认。
6. 存在未确认冲突时，默认检索隐藏该事实值；历史和证据查询仍可查看双方。
7. 业务事实与 `memories` 分离。业务事实保存项目对象和值，交互记忆保存偏好、要求和交代。
8. 模型只能提交候选；项目范围、状态和版本转换由服务端确定性校验。

## 结果

优点：

- 不引入多数据库双写，事务、备份、恢复和权限边界一致。
- 类型化字段支持金额、日期和聚合；JSONB 保留领域扩展能力。
- 可回查来源并区分业务有效时间与系统记录时间。
- project_id 和 RLS 可阻止跨项目召回。

代价：

- 领域模型、提取提示和实体消歧需要持续评测。
- 关系遍历只适合首版有限跳数，大规模分析需要压测和后置扩展。
- 冲突管理增加交互和状态复杂度，但这正是避免错误记忆进入答案的必要成本。

## 不采用

- 单独 Neo4j 作为首版权威库：增加双写、一致性和运维成本。
- 独立向量库作为事实真相：向量只能找候选，不能表达版本、证据和事务状态。
- 纯 JSON 文档：难以保证跨对象约束、金额类型和细粒度查询。
- 每个项目独立数据库或 schema：连接与迁移成本高，`project_id` 加复合约束和 RLS 已满足首版。
- 全部历史对话自动回填：会把旧错误和临时推测升级为权威事实。
