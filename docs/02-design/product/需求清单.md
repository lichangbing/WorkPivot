# A. 桌面客户端

## A01 桌面应用壳

- **背景**：产品第一入口，Windows 优先（企业客户主流），macOS 次之；框架已定 Electron（TECH-02）。
- **用户故事**：作为企业用户，我双击图标打开 WorkPivot，登录后 3 秒内进入可用界面，使用中感觉和本机应用一致。
- **功能要求**：
  1. **启动登录门（2026-08-28 用户确认）**：启动后先登录再进入主界面；当系统**没有任何用户时提供注册入口，第一个注册的用户自动成为管理员**；此后注册入口关闭，**由管理员在用户管理中新增用户（用户名/密码）**（OWB 同款模式；企业 IdP 场景见 J07）；会话记住登录态，重启免重复输密码（可锁屏再验证）
  2. 主窗口单实例（二次启动聚焦已有窗口）；Chrome 式多 Tab（详见 A02）
  3. MVP 采用形态 A：Express 服务 + 前端静态资源与 Electron main 同进程；**拆分边界纪律：前端只经 localhost HTTP/SSE 与服务层通信，禁止 import 服务层代码、禁止调用 Electron 专属 API**（保住 Web-ready 与未来 A' 拆分）
  4. 系统集成：托盘图标（含未读/运行状态）、窗口关闭最小化到托盘（可配置）、系统通知
  5. 启动链路分段计时日志（Electron 就绪/服务初始化/服务就绪/页面加载）——冷启动 P95 < 3s，超时输出瓶颈段
- **边界**：不做多窗口/独立浮窗（需求池）；不做主题市场（内置明暗两套）；登录安全（密码哈希/防爆破）在 J01 承载
- **验收**：首装→注册→自动成为管理员→管理员新增用户→新用户登录成功全流程；冷启动 P95<3s；断网重启不丢 Tab 状态；`npm start` 纯浏览器模式功能等价（除托盘/通知）
- **依赖**：TECH-02、J01（本地账户）、J07（企业登录）

## A02 多会话/多任务并行

- **背景**：任务=对话+工作目录是品类核心模型（WorkBuddy 官方「创建任务四步」）。
- **用户故事**：作为用户，我同时开 5 个任务互不阻塞；关掉窗口半夜跑的任务，断网/重启后打开能看到完整过程并继续对话。
- **功能要求**：
  1. 三栏结构：左任务列表（按项目分组、状态标记）｜中对话流｜右成果区（产物/文件/变更/预览）
  2. 任务创建四步（对标 WorkBuddy）：自然语言描述 → 选工作目录（必选或记住上次）→ 添加上下文（@文件/截图/拖拽）→ 开始
  3. 并行任务互不排队；运行中发新消息默认插入当前任务队列
  4. **断点续流**：断网/刷新/电脑睡眠唤醒后，运行中任务自动重连接回实时流（OWB 实证），过程不丢
  5. 任务中途可补充消息、可停止（停止不再产生费用）
- **边界**：单机并行上限 8 个任务（超出提示，防御资源耗尽）；不做任务间依赖编排
- **弱网适配（2026-08-29 用户问询确认）**：高延迟环境自动降级为「整段刷新」渲染（不做逐字流式，避免卡顿感）；断线期间服务端任务照常执行，重连后从服务器补全内容（不猜增量）。服务端形态下出差弱网仅影响实时体感，任务执行与成果不受影响
- **验收**：5 任务并行 30 分钟无 UI 冻结；断网 60s 恢复后流自动接回且无消息丢失；模拟高延迟（RTT>800ms）时自动切换整段渲染
- **依赖**：A01、F01

## A03 任务过程可视化（2026-08-28 用户确认修订：核心内容为主，细节折叠）

- **用户故事**：作为业务用户，我一眼看懂 AI「干到哪一步了、拿到了什么关键结论」；过程细节我不关心但需要时可查。
- **设计原则**：**展示层做过滤（核心内容），记录层保全量（F01 转写一个字不丢）**——两层解耦，用户默认看摘要，排查时看全程。**过程记录使用中文叙事**（2026-08-28 用户确认）：按「获取了什么数据 → 做了什么处理 → 得出什么结论」三段式表述，不暴露英文工具名/参数等机器细节。
- **中文叙事实现**：系统提示词纪律（C01 产品层注入）要求 AI 在每个阶段节点产出一句中文过程摘要（如「已获取近三年销售流水（来源：ERP 导出表格），按季度汇总并剔除退款记录，得出 Q3 环比下降 32%」）；工具层的英文调用明细仅存转写与折叠层，不上主线。
- **功能要求**：
  1. **阶段主线展示**（默认视图）：以 AI 的执行计划为主线的进度视图——「✅ 读取 Excel 完成 → 🔄 分析销售数据中(3/8) → ⬜ 生成图表」；阶段来自任务计划结构，不是逐条工具调用
  2. **关键节点卡片**：阶段性核心结论以卡片呈现（如「发现 Q3 环比下降 32%」），细节收进折叠；任务完成时顶部汇总「做了什么/产出哪些文件」
  3. **异常前置**：需要用户决策/授权的时刻（界外访问、等待审批）在主线上突出显示，不被过程流淹没
  4. **细节折叠层**：工具调用明细（名称/参数/完整结果）折叠在阶段之下，点开才见；**来源收录**（真实访问过的网页，工具层记录而非模型自述——OWB 防假凭证）附在最终回复底部
  5. **全程回看**：转写查看器入口（读 F01 全量记录，含每次工具调用原文），用于排查与复盘
- **边界**：不做过程回放编辑器；不做实时性能分析面板
- **验收**：①一个 20+ 工具调用的任务，默认视图主线条目 ≤ 计划阶段数（非 20 行流水账）②主线条目为中文叙事且含「获取/处理/结论」要素，无英文工具名裸露 ③关键结论以卡片出现且数字与最终报告一致 ④来源列表与实际 HTTP 日志一致（测试断言）⑤转写查看器能看到全部工具调用原文

## A04 内嵌浏览器/网页预览

- **功能要求**：AI 输出中的 HTTP(S) 链接默认在内嵌 WebView 打开（Ctrl/Cmd+点击走系统浏览器）；HTML 产物一键预览；抓取空壳时自动真渲染兜底（OWB 模式）
- **边界**：不做多标签浏览器；WebView 零权限（不可访问应用 API，WorkBuddy browser.json 模式）
- **验收**：SPA 页面能读到完整内容；预览无法触达应用内部接口（安全测试）

## A05 本地全文搜索

- **功能要求**：跨会话历史搜索 + 工作区文件内容搜索；中文分词；结果定位跳转
- **边界**：P2；技术选型 SQLite FTS5 起步（够用再上 Tantivy）
- **验收**：10 万条消息下搜索 <1s；中文同义词召回可用

## A06 任务通知

- **功能要求**：后台任务完成/失败/等待审批 → 系统通知（点击跳转对应任务）；托盘显示运行状态；**免打扰时段**可配置
- **验收**：任务完成 2s 内通知到达；免打扰时段静默且不丢

## A07 自动更新

- **用户故事**：作为 IT 运维，我在企业内网搭一个静态更新源，客户端自动检测升级，出问题能回滚；作为开发者，我调试时能快速分发构建。
- **功能要求**：electron-updater + **自建 feed**（内网静态文件服务，不依赖公网）；差分增量下载；签名校验；**一键回滚到上一版本**；开发期提供「复制构建到本地 feed」脚本
- **边界**：不做灰度/分批推送（P2）；强制更新策略由管理员配置
- **验收**：内网无公网环境完成 A→B 升级与 B→A 回滚；升级中断电可恢复

## A08 数据备份/恢复

- **功能要求**：一键备份 data/config/skills/workspace 至指定目录（tar）；恢复前自动做 before-restore 安全备份；恢复后提示重启；提供 `workpivot backup` CLI 命令（供企业运维 cron 调度）
- **边界**：不做应用内定时自动备份（P2）
- **验收**：备份→清空→恢复→功能完整；恢复中断不损坏现有数据

## A09 语音输入

- **功能要求**：输入框语音按钮，按住说话转文字（本地 Whisper 模型或云端 API，设置页选择）；TTS 朗读回复为可选开关
- **边界**：P2；不做实时语音对话
- **验收**：中文识别抽样准确率 ≥90%；无网络时本地模型可用

## A10 上下文查看与管理（2026-08-28 新增，P1）

- **用户故事**：作为用户，AI 表现不对时我想知道「它现在带着哪些信息」，并能手动清理或压缩；全程看中文，不要求我读英文提示词。
- **功能要求**：
  1. `/usage`：当前会话 token 占用分解（系统提示/记忆/历史/工具结果），中文呈现
  2. `/compress`：手动触发压缩；自动压缩阈值管理员可配（默认 70%）
  3. **压缩摘要中文化**：被压缩的内容以中文摘要形式展示给用户（「已将早期 15 次网页查询压缩为摘要，保留 3 个关键结论」）；原始内容保转写（F01）
  4. 上下文组成可视化：当前会话带了哪些记忆条目/引用文件，可单条移除
- **边界**：不开放系统提示词直接编辑给普通用户（管理员经 S03；进阶用户经 D02 个人 agent.md）
- **验收**：中文会话中 /usage 与 /compress 输出全中文；压缩后用户视角摘要与转写原始记录可对照
- **依赖**：K04、F01、S03

# B. 工作区与项目

## B01 工作区=真实目录

- **用户故事**：作为用户，我的成果就是真实可用的文件——单机用户在磁盘上直接打开，服务端用户在预览区/下载中拿到。
- **功能要求**：
  1. 任务/项目绑定真实目录，产物直接写盘（不用虚拟文件系统/数据库 blob）
  2. **拓扑一（单机）**：工作区=本地目录（默认 `~/WorkPivot/workspace/`，可自定义），产物在资源管理器立即可见，可双击用 Office/WPS 打开
  3. **拓扑二（服务端集中，2026-08-28 用户定稿）：本地完全没有 workspace 概念**——生成内容全部保存在服务端（`data/workspaces/{uid}/` + 共享项目目录）；**本地角色只有「素材来源」**：用户通过上传对话框（文本/文件/截图）把本地素材送进服务端工作区，之后一切生成、加工、版本迭代都在服务端完成；用户经 ①右栏预览（主力）②按需下载（单文件/批量打包，需本地编辑或外发时）取用结果；**不做本地同步盘、不生成隐藏的本地工作目录**
  4. 对话中 **@ 引用文件**：单机=本地文件选择器；服务端=服务端工作区文件选择器 + 「上传本地素材」入口（上传后即成为服务端工作区文件，可被 @ 引用）
- **边界**：不做虚拟文件系统/数据库 blob 存储；不做本地同步盘；服务端形态不做「映射到本地目录」的客户端功能
- **验收**：①单机——产物在资源管理器立即可见，Office/WPS 双开正常 ②服务端——上传素材→生成→迭代全流程不产生任何本地工作目录，预览与下载内容和服务器完全一致 ③@ 引用的文件内容确实进入模型上下文

## B02 版本号文件名交付

- **背景**：WorkBuddy 实测（方案 v1.0→v2.5 一天六版）——版本纪律让迭代可追溯。
- **功能要求**：系统提示词约定「同一交付物修改时另存新版本号文件，不覆盖」；文件名模式 `{标题} v{X.Y} {日期}.{格式}`；成果区按版本链展示
- **边界**：不做内容级 diff（B03 快照承担回滚）
- **验收**：连续修改同一方案 5 次产生 v1.0→v1.5 且旧版完好

## B03 文件修改快照、回收站保护与临时文件治理

- **用户故事**：作为用户，AI 改错了我的文件、或者我手滑删错了，我能找回；任务完成后工作目录里只有干净的交付物，没有过程垃圾文件。
- **功能要求**：
  1. **修改快照**：agent 修改/删除文件前自动快照至 `~/.workpivot/file-history/`（服务端形态在服务端对应目录）——内容哈希版本链（同文件多版本 `{hash}@vN`，WorkBuddy 同款）；异步执行不阻塞任务
  2. **删除保护**：agent 删除文件默认进系统回收站（服务端形态进服务端回收站目录），不直接物理删除；永久删除需用户明确指令
  3. **恢复入口**：成果区「历史版本」——查看文件快照列表，一键恢复到任意版本
  4. **临时文件治理（2026-08-28 用户确认新增）**：任务完成收尾时清理过程文件——`_tmp_*`/`temp_*` 中间产物、调试脚本、`__pycache__` 等缓存目录、未引用草稿；**清理前先快照**（误删过程文件可从快照找回）；交付物与用户上传素材永不清理；清理动作记入 I03 审计（附文件清单）。系统提示词写入「临时文件命名约定 + 收尾清理」纪律，F02 收尾核验增加「无临时文件残留」检查项
  5. 性能保护：>10MB 大文件跳过快照并提示
- **边界**：不做全目录回滚（快照粒度=单文件）；不做快照自动过期清理（P2：默认保留 30 天）
- **验收**：①AI 修改文件 3 次→历史版本 3 条，任选恢复正确 ②AI 删除文件可从回收站找回 ③任务完成后工作目录无 `_tmp_*`/缓存目录残留（F02 核验断言），被清理文件可从快照找回 ④>10MB 文件跳过快照不影响任务执行

## B04 任务转交（P2）

- **功能要求**：转交=产物文件+进度摘要+元数据（标题/说明/处理人/状态/截止）+附件打包到新会话；接收方带完整上下文继续
- **边界**：单机形态为「导出任务包/导入」，多人共享留企业形态
- **验收**：转交后新会话能回答「之前做到了哪一步」

# C. Agent 内核与模型接入

## C01 Agent 编排运行时

- **背景**：内核 = Cordis 模式 + jiti（TECH-01 方向已定）；工具面以 pi 的 7 内置工具为基线（bash/read/write/edit/find/grep/ls）+ 记忆/技能管理工具。
- **功能要求**：
  1. 工具循环（agent loop）：模型请求→工具调用→结果回填→循环到完成；每步事件流式输出（A03）
  2. 子代理：主 agent 可委派子任务（D02 专家委派复用同一机制）；子代理独立上下文、汇报回主 agent
  3. 上下文组装四层（dsh 模型）：Runtime 基础 prompt / 产品层（L1 身份、L2 入口场景、L3 场景段、L4 能力发现）/ 工作区指令（CLAUDE.md/AGENTS.md 自动加载）/ 按轮 system-reminder
  4. **「模型可见即已记录」不变量**（dsh）：任何进入模型请求的内容必须可从会话日志重建，运行时断言强制
- **边界**：MCP/技能/连接器工具经 D 模块动态注册，内核不硬编码
- **验收**：eval 题库基线建立（K01）；不变量断言在 CI 常驻
- **依赖**：ADR-002（PoC 通过）

## C02 双协议模型接入

- **功能要求**：OpenAI 兼容（DeepSeek/Qwen/GLM/Kimi/MiniMax/OpenRouter/Ollama…）+ Anthropic 协议两套适配；供应商预设表（选名称自动填 base_url）；**保存前真实请求验活**（OWB：不发消息才发现 key 错）
- **权限边界（2026-08-28 定稿）**：模型配置权唯一属于后台管理员，**用户不可自配**（M03：界面+API 双层封死）；用户端模型选择器只列管理员开放的范围
- **验收**：接入任一新供应商 ≤2 分钟且无需改代码（管理员操作口径）

## C03 私有化模型热插拔（差异化核心）

- **用户故事**：作为企业 IT，我把 Ollama/vLLM 部署在内网 GPU 服务器，WorkPivot 全员使用内网模型，数据不出网；需要更强能力时混合配置商用 API。

# D. 扩展体系（专家/技能/连接器）

## D01 技能系统

- **背景**：SKILL.md（agentskills.io 标准）是事实格式；热加载是产品性格（改完即生效）。
- **功能要求**：
  1. 格式：YAML frontmatter（name/description/**disable-model-invocation**/metadata）+ Markdown 正文 + references//scripts/ 子目录

  3. **热加载**：每次任务重读磁盘（OWB 模式，免重启）；`disable-model-invocation: true` 的技能仅用户斜杠触发（权限粒度）

- **边界**：不做签名/远端市场（D05 P2）

## D01a 用户自定义 Skill：创建·编辑·调试（2026-08-28 用户确认新增）

- **背景**：用户不仅「用」技能，还要能「造」技能——这是 OpenWorkBuddy（加技能=写一个 Markdown）、Hermes（skill_manage 自动生成）、pi（.pi/skills 自扩展）共同验证的核心扩展体验；也是 D08（AI 自生成技能）的人工 counterpart。
- **用户故事**：作为用户，我在界面里新建一个自己的技能，写完保存立即生效；运行不对时我边看执行过程边改，不用重启、不用懂代码框架。
- **功能要求**：
  1. **技能编辑器（双层，入口在左栏「技能与工具」，居中大面板编辑）**：①MD 层——表单填 frontmatter（name/description/触发方式）+ 正文 Markdown 编辑（语法高亮/预览）②**代码层**——scripts/ 脚本文件编辑（Python/Node/Shell，语法高亮），/templates/、/assets/ 文件管理；技能目录结构 = SKILL.md + references/ + scripts/ + templates/ + assets/；高级用户可直接编辑文件（「打开所在目录」）
  2. **创建方式三选**（对标 WorkBuddy 技能市场）：① 空白模板 ② **描述生成**：用自然语言描述「我想要什么技能」，AI 生成初稿（人工确认后保存——与 D08 同一确认流）③ **从对话沉淀**：把当前会话的成功做法一键转为技能草稿
  3. **调试闭环**：技能详情页显示「最近生效版本/上次被调用的时间与任务/触发词命中情况」；「试运行」入口——输入模拟任务走一遍加载→注入→执行观察；**脚本类技能可在试运行中直接执行 scripts/ 并看输出**（执行经 I01 沙箱）；改完保存即热生效（D01 机制）
  4. **作用域**：个人技能（全局）与项目技能（仅当前项目）创建时选择；项目覆盖同名全局（D01 规则）
  5. **企业约束挂钩**：S01 公共技能对成员只读，但成员可「复制为我的技能」再改（副本归个人）；管理员策略可禁用个人技能（合规场景，默认允许）
  6. 调试技巧内置指引：技能正文模板（触发条件/编号步骤/坑列表/验证步骤——Hermes 好技能范式）+ 常见问题（不触发=description 写得不含触发词等）
- **边界**：不做技能脚本市场/分享平台（D05）；脚本类技能（scripts/）的调试依赖沙箱（I01），首版以文档型技能为主
- **验收**：①零基础用户 10 分钟内走完「描述→生成→确认→使用」创建出一个可用技能 ②修改技能正文后下一条任务即生效（无需重启）③试运行能看到技能是否被命中与注入内容
- **依赖**：D01（格式与热加载）、D08（AI 生成共用确认流）、I01（脚本执行）、S01（企业约束）

## D02 专家系统（2026-08-28 用户确认修订：后台配置制）

- **背景（用户定调）**：WorkBuddy 做专家广场是因为它是通用平台（靠专家生态获客）；**私有化企业平台只需要固定的几个贴合自身业务的专家，由后台管理员配置**，不做用户端广场/召唤/自定义的 C 端形态。
- **用户故事**：作为管理员，我在后台配置 3-5 个企业专属专家（如「私募数据分析师」「尽调助手」「报告撰写」），设置人设/绑定技能/数据源；作为普通用户，我在对话中选择专家（下拉或新建任务时选择），AI 以该专家的专业方式完成任务——全程无需理解什么是提示词。
- **功能要求**：
  1. **专家构成**（格式与 agent.md 定义一致，D02 格式即专家格式）：agents/*.md 人格提示词（角色/方法论/行为规范）+ maxTurns 预算 + 元数据（名称/头像/描述）+ 绑定技能 + 绑定数据源（S02a RAG/S02 连接器的可见范围可随专家预置）
  2. **后台配置界面**（挂 M04）：专家列表/新建/编辑/启停/删除；表单化编辑（人格提示词文本框 + 技能勾选 + 数据源勾选），进阶管理员可直接编辑 agent.md 文件
  3. **用户端使用**：新建任务时选择专家（下拉，含「通用助手」默认项）；对话中显示当前专家标识；无广场、无召唤按钮、无用户自定义入口
  4. 内置通用专家模板随产品发行（调研专员/文档写作/数据分析/PPT 设计等），管理员可修改/停用；**企业专属专家数量不设限制，按需配置**
  5. 专家人格叠加在企业默认 agent.md（S03）之上，红线不可覆盖
- **边界**：不做专家广场/市场（通用平台形态，与定位不符）；不做用户自定义专家（统一后台配）；专家团接力 P2（确有流水线需求再议）
- **验收**：①管理员后台配置「尽调助手」专家（绑定 RAG 数据源+文档技能）→用户新建任务选择它→AI 以尽调方法论工作且引用企业知识库 ②停用某专家→用户端 60s 内不可选 ③专家人格不覆盖 S03 企业红线
- **依赖**：C01（子代理机制）、S03（企业默认层）、D01（技能）、S02/S02a（数据源）、M04（配置界面）

## D05 Agent 自生成技能（用户确认的内核能力）

- **背景**：Hermes 四层闭环实证（技能=程序性记忆，低风险先行）。
- **用户故事**：作为用户，AI 完成复杂任务后提议「把这次的做法存为技能」，我确认后下次同类任务它自动用；使用中发现技能有坑，它自己修补并告知我。
- **功能要求**：
  1. 工具 `skill_manage`：create/patch/edit/delete，**策略编码进工具描述**（何时创建：复杂任务成功 5+ 调用/踩坑克服/用户纠正有效；好技能的形状：触发条件+编号步骤+坑列表+验证步骤）
  2. **用户确认前置**：创建/删除必须用户点头（对话内确认卡）
  3. **nudge 提醒**：每 N 轮（默认 10，可配）注入「回顾技能」提醒；技能工具实际使用即归零
  4. 安全：写后扫描（frontmatter 校验+内容尺寸+可疑模式）；pinned 防删可改；删除须声明 absorbed_into（合并/修剪语义）
- **可控性原则（2026-08-28 用户确认，修正 Hermes 不可控缺陷）**：AI 生成一律为「草稿」，用户才是发布者。三条保障：① **结构可控**——抽取按固定 JSON schema 强约束（技能名/适用场景/前置条件/步骤序列/注意事项/验证方法），套固定 SKILL.md 模板渲染，产出永远是标准五段式；字段缺失/置信度低→明示「该文档不适合提炼技能」而非硬编 ② **内容可控**——步骤须带原文依据引用，低置信字段在编辑器中标黄提示重点核对 ③ **过程可控**——人工编辑为必经环节（D01a 编辑器逐段核对），确认后才入技能目录
- **入口场景**：① 上传文档→自动分析生成技能草稿（如把 SOP 文档/操作手册提炼为技能）② 复杂任务成功后提议沉淀 ③ nudge 周期提醒回顾
- **边界**：只生成 SKILL.md 知识技能；代码生成走 D06（P2）
- **验收**：①同一文档重复生成 3 次，结构均为标准五段式且核心步骤一致（可控性断言）②含幻觉步骤的样本在编辑确认环节被用户识别修改 ③eval 题——同类任务第二次执行引用了生成的技能且耗时下降
- **依赖**：D01、D01a、K01

# F. 任务系统与长任务韧性（2026-08-28 定位升级：**agent 效果核心层，优先级高于一切增值功能**）

> 用户感知的产品质量几乎全在本层：对话丢不丢（F01）、AI 会不会骗人（F02）、任务会不会烂尾（F03）、会不会白跑（F04）、会不会傻转圈（F05）、承诺的定时会不会漏（F06）。F 定效果，K01 验效果——本层验收全部做成 eval 题常态化跑。

## F01 会话转写持久化（P0）

- **功能要求**：JSONL 追加式转写（消息/工具调用/产物引用全量）；**原子写+.bak 兜底+坏文件隔离**（OWB store 三原则）；「模型可见即已记录」不变量（C01）；转写查看器（回放过程）
- **验收**：kill -9 后重启会话完整恢复；人为损坏 JSONL 能回退 .bak 并告警

## F02 成果核验闸门（P0）

- **功能要求**：任务收尾前校验「声称产出的文件真实存在且非 0 字节/非空壳」；不合格打回重做（**最多 2 次**）；核验结果进事件流（A03 可见）
- **验收**：eval 题——诱导模型谎称生成文件，拦截并要求真做的通过率 ≥95%

## F03 强制收尾（P0）

- **功能要求**：撞步数/时长上限时追加一次**无工具请求**，只答三件事：完成了什么/产出了哪些真实文件/下次从哪继续；用户手动停止不触发（省钱）
- **边界**：步数/时长默认 200 步/30 分钟，可配
- **验收**：长任务超限的收尾消息包含三要素

## F04 任务与进程解耦 + 自动续跑（P0，2026-08-28 用户确认强化）

- **核心原则（用户确认）**：**任务保持工作状态（state），进程关掉后还能继续启动**——任务不依赖应用进程存活。
- **功能要求**：
  1. **状态实时落盘**：任务状态（转写/执行进度/计划节点/工作目录变更）实时持久化，不依赖进程内存（F01 原子写）
  2. **中断可见**：应用重启/崩溃/关机后重新打开，未完成任务在任务列表中状态=「已中断」（不是消失也不是假装还在跑），明确提示「可从断点继续」
  3. **断点续跑**：用户点「继续」→ AI 读取 PROGRESS.md 进度档 + 转写尾部 → 从断点接着干，已完成的部分不重做
  4. **自动续跑**（原 F04）：撞步数/时长上限后按设定轮数自动重置预算续跑（大任务第一步建 PROGRESS.md 写入系统提示词纪律）；手动停止与模型挂死不自动续
  5. 服务端形态（J02 拓扑二）：任务跑在服务器，用户关浏览器不影响执行；重连接回直播（A02）——进程解耦天然满足
- **边界**：单机形态关机期间任务必然暂停（桌面应用的物理限制），恢复=重启后断点续跑；真正的「关机也继续」需要服务端形态
- **验收**：①任务跑到 20 步时 kill 进程→重启后任务显示「已中断」→点继续→从断点完成且无重复工作（eval 题）②服务端形态：用户关浏览器 1 小时后回来，任务已完成且成果可预览

## F05 卡循环检测（P0）

- **功能要求**：同工具+同入参+同结果连续 3 次→注入提醒换思路；5 次→拦截执行返回错误说明；结果指纹防误伤（文件变了内容就变，计数清零）
- **验收**：压测脚本验证 3 提醒/5 拦截/正常读写循环不误伤

## F06 定时任务（P0）

- **功能要求**：cron 表达式+自然语言预设模板（每日简报/周报）；**错过补跑**（重启后发现错过的调度补执行一次）；结果推送通知（A06）；执行历史与审计
- **边界**：不做依赖编排/工作流 DAG（P2+）
- **验收**：设定每日报错任务，重启后错过的一次被补跑

## F07 Activation Trigger（P2）

- **功能要求**：命令型定时任务到点先跑本地零成本检测器（脚本输出 quiet/activate），quiet 不唤醒模型——省 token
- **依赖**：F06

## F08 Goal 长程目标模式（P2）

- **功能要求**：目标→自动拆验收清单→每轮验收员核对（**对成果文件机器实测**：语法/解析/截断检查）→未达成自动补跑（≤3 轮）→目标卡实时打勾
- **依赖**：F02/F04

## F09 想法速记（P2）

- **功能要求**：随手记想法（按月归档）；AI 讨论对齐后一键沉淀为任务（含讨论上下文）
- **依赖**：F06

- **验收**：分叉点前内容一致、后互不影响

  1. **通用层：标准 OAuth 2.0/OIDC 接入**——统一认证适配层，配置化接入任意标准 IdP（企业微信/钉钉/Keycloak/Azure AD/Authing…）：授权端点/token 端点/client_id/secret/scopes 表单配置 + 回调地址自动生成

  3. **内置账户管理**：无外部 IdP 时的账密登录（J01 承载）
  4. **管理员分配制**：无自主注册；用户经 IdP 登录后若未分配账户→提示联系管理员（可配自动开通白名单域）
  5. **桌面端流程**：系统浏览器授权 + loopback 回调（RFC 8252）+ PKCE；token 走 I04 加密
  6. **术语边界**：企业封闭账户体系，非 SaaS 多租户；未来 SaaS 为超集扩展（+租户隔离+计费）
- **验收**：飞书扫码登录→自动建号→角色同步全流程；Keycloak 标准对接演示；未分配用户被拒并提示
- **依赖**：I04、M02（角色管理界面）

# M. 后台管理（v2 新增——企业管理能力的界面载体）

## M03 模型管理（P1 企业形态；**单机形态=管理员即本机用户，规则相同**）

- **背景（2026-08-28 用户二次确认，最终定稿）**：**平台可用模型只允许后台管理员配置，严格禁止用户自行配置**——通过管理员配置的模型进行分析，数据流向完全由企业掌控。单机形态下管理员=使用者本人（同一规则）。
- **用户故事**：作为管理员，我在后台统一配置可用模型平台（内网 vLLM/Ollama 或审批过的商用 API）并分配可见范围；作为普通用户，模型选择器里只有管理员开放的模型，**产品中不存在用户自配模型的任何入口（界面与 API 双层封死）**。
- **功能要求**：
  1. 企业模型池配置（唯一入口=后台，**以 OpenAI 接口模式为主**：base_url + API Key + 模型 ID 即可接入任何 OpenAI 兼容服务——vLLM/Ollama/DeepSeek/各类中转）：增删模型供应商与模型条目/连通测试/启停/**用户可见范围**（按角色/部门）；默认模型指定；用量视图入口（J05）；**并发配置**：企业最大并发会话数（J01 排队依据）、单用户并行任务上限、按模型分档并发（如内网大模型限 5 并发、轻量模型不限）
  2. **用户端全面封死自配**：设置页无自定义模型表单；**API 层同样拒绝**——非管理员提交的模型配置请求一律 403（防绕过 UI 直调接口）；不提供用户级模型配置文件机制
  3. 凭据管理：模型 API Key 仅管理员录入，走 I04 加密，**用户端永不暴露**（模型对用户呈现为名称+说明，不显示 base_url/key）
- **对标**：WorkBuddy 企业版「模型部署管理」（API_KEY+部署地址+测试+创建+可见范围全流程一致）
- **边界**：不做模型用量计费审批流（J05 只做统计）；不做模型性能测评
- **验收**：①管理员配置内网 vLLM→指定研发部→研发部可选、其他人不可见 ②普通用户设置页无自配入口，API 直调模型配置被 403 ③用户端全程看不到企业模型凭据
- **依赖**：C03、I04、J07（角色）、M01（后台框架）

# S. 公共 Skill/MCP 服务（v2 新增——「企业共享能力中心」）

> **定位**：管理员/连接器管理员配置一次、全员可用的共享能力层——解决「每个成员自己配数据库连接、自己找技能」的混乱与安全风险。**与 D03（个人连接器）、D01（个人技能）的关系：S 是企业公共层，D 是个人层，两层并存，公共优先**。

## S01 公共 Skill 管理（P1 企业形态）

- **用户故事**：作为连接器管理员，我把「私募基金数据清洗」技能配置为公共技能，全部门同事对话里直接可用，无需各自安装。
- **功能要求**：
  1. 公共技能库：管理员上传/配置技能包（D01 格式）→ 全员任务中自动可用（注入技能目录并标注「企业」来源）
  2. **配置型公共技能**：管理员预填参数的技能（如数据源地址、部门模板）——成员零配置使用
  3. 分版本：技能更新推送全员（成员端提示新版本）；回滚上一版
  4. 启用范围：全员/指定部门（对接 J07 组织架构）
  5. 成员端**只读**（不可改公共技能；可复制副本到个人区修改）
- **边界**：单机形态=「本机共享技能目录」简化版
- **验收**：管理员发布→成员新任务立即可用；更新推送与回滚全流程；成员尝试修改被拒

## S02 公共 MCP 连接器服务（P1 企业形态，本模块核心）

- **用户故事**：作为连接器管理员，我配置一次「生产数据库（只读）」和「内部 Wiki」两个 MCP 连接器，全员对话中即可查库、查 Wiki，凭据无人可见、调用全部留痕。
- **功能要求**：
  1. **服务端公共连接器**：MCP 服务运行在服务端（随部署形态：同进程/独立容器/Docker Compose 模板），成员端经**本地聚合代理（D03）远程挂载**——成员本机不落任何凭据
  2. **凭据集中托管**：连接器凭据存服务端加密库（I04）；绑定连接器资源而非个人（可轮换、人员离职不失效）；连接器管理员可见配置、**全员不可见明文**
  3. **使用范围控制**：全员/指定部门/指定项目
  4. **调用审计**：谁、何时、调了哪个连接器的哪个工具、参数摘要——连接器管理员与企业管理员可查（M06）
  5. **启停即时生效**：管理员停用→成员端下轮对话该工具即消失
  6. 典型内置场景模板：数据库只读查询（连接串配置+白名单表）、内网网站/API 抓取（域名白名单）、Wiki/文档系统检索
- **边界**：成员个人连接器（D03 个人层）并存但**协作/共享任务中个人连接器自动禁用**（WorkBuddy 规则，防不可追溯访问）；**写型数据库操作默认禁用**（只读起步，写需连接器管理员显式开启+审计）
- **验收**：①管理员配置数据库连接器→成员自然语言查数成功且**成员端磁盘无凭据**（测试断言）②管理员停用→成员端 60s 内失效③审计可查完整调用记录④写操作默认被拒
- **依赖**：D03（聚合代理）、I04（加密）、J07（部门范围）、M04（管理界面）、M06（审计）

## S02a 外部 RAG 服务接入（2026-08-28 用户新增，P1）

- **背景（用户定调）**：企业知识检索**不自己做 RAG 产品**（文档上传/索引管理/切片调优交给专业 RAG 产品与企业 IT），WorkPivot 只做**接入方**——IT 部署好 RAG 服务（Dify/MaxKB/RAGFlow 或自建），WorkPivot 对接。
- **用户故事**：作为企业 IT，我把公司已部署的 RAG 服务的 API 地址和密钥填进后台，全员对话中 AI 就能检索企业知识库并标注来源；换 RAG 产品只改配置不动客户端。
- **功能要求**：
  1. 后台配置项（连接器管理员/IT）：RAG 服务地址、API Key、检索接口协议选择（标准 REST：query→top-k 文档片段+来源元数据）
  2. agent 检索工具 `knowledge_search`：任务中按需检索，结果带来源标注（文档名/链接），注入上下文
  3. 连通测试；启停；使用范围（全员/部门）
  4. 调用审计（M06：谁检索了什么）
- **边界**：不做文档上传/索引/切片等 RAG 本体功能（企业 IT 的 RAG 产品负责）；无 RAG 时功能缺失不影响其他能力
- **验收**：IT 填入 Dify 知识库 API→成员对话提问→AI 引用知识库内容并标注来源；停用后工具消失
- **依赖**：I04、M04、M06

## S03 默认 Agent 定义（后台配置，2026-08-28 用户确认新增，P1）

- **背景**：企业希望全体成员的 AI 有统一的行为基线——回答风格、安全红线、公司术语表、报告格式规范等，不应要求每个用户自己配置；与 S01（公共 Skill）、S02（公共连接器）同属「管理员配一次、全员生效」的公共层。
- **用户故事**：作为企业管理员，我在后台编辑一份默认 agent.md（系统指令/人格基调/输出规范），新用户开箱即得统一行为；作为进阶用户，我可以在个人层覆盖它。
- **功能要求**：
  1. **默认 agent 定义管理**（后台界面，挂在 M04 管理入口下）：管理员编辑默认 agent.md（YAML frontmatter + 系统指令正文，格式同 D02 agent 定义），保存后对新会话生效
  2. **分层组装**：最终系统提示 = 平台基础层（C01 L1）→ **企业默认层（S03，不可被用户关闭）** → 用户个人层（D02 自定义 agent/工作区指令，可选）——企业层负责注入红线与规范，个人层做个性化叠加
  3. **版本与生效**：默认 agent.md 带版本号；更新后新会话即生效（进行中会话不中断）；历史版本可回滚
  4. **用户可见性**：会话中可查看「当前生效的企业默认指令」（透明原则，不搞暗箱人格）；用户可在个人设置里查看自己叠加了什么
  5. **与个人自定义的关系**：无个人自定义→直接用企业默认；有→个人层叠加（冲突时企业红线优先，实现上企业层指令声明「以下约束不可覆盖」）
  6. 单机形态：设置页提供同一编辑器（本机管理员=自己）
- **边界**：不做多套默认方案按部门分发（列 P2，依赖 Q6 组织复杂度）；不做用户级禁用企业默认（红线性质）
- **验收**：①管理员修改默认 agent.md（如加入「所有报告用公司模板格式」）→成员新任务输出遵循该规范 ②进阶用户自定义个人 agent 后，企业红线仍生效 ③回滚到上一版本后行为还原
- **依赖**：C01（上下文组装四层）、D02（agent 定义格式）、M04（管理入口）、J07（角色）
