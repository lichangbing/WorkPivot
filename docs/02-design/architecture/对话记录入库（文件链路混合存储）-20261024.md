# 对话记录入库（文件链路混合存储）（2026-10-24）

状态：设计完成，未实现。对应 backlog R007。

## 1. 目标与非目标

**目标**：文件链路继续用工作目录与磁盘文件，只把**对话记录与任务元数据**写入 PostgreSQL，解决“聊得越久、任务越多，加载越慢”的问题。

**非目标**：

- 不切换到数据库链路（不把文件改成版本、不取消工作目录）
- 不迁移历史数据（可清空重装）
- 不把附件/成果文件的字节放进数据库

## 2. 现状：哪些内容在磁盘

| 内容 | 位置 | 现状 |
| --- | --- | --- |
| 任务元数据 | `$WORKPIVOT_HOME/data/tasks/<id>/task.json` | 每任务一个 JSON，`listTasks()` 遍历目录逐个解析 |
| 对话记录 | `$WORKPIVOT_HOME/data/tasks/<id>/transcript.jsonl` | 每行一条；读取时全量读入并逐行 JSON.parse |
| 会话索引 | `$WORKPIVOT_HOME/data/sessions/index.jsonl` | 仅记录 `task_created` |
| 工作目录与文件 | `$WORKPIVOT_WORKSPACE/.accounts/<userId>/…` | **保持不动** |
| 记忆/计划/脚本/截图 | 任务目录下 `.workpivot/` | **保持不动** |
| 设置 | `$WORKPIVOT_HOME/config/settings.json` | 本轮不动 |

读路径的实际代价（这是“越用越慢”的根因）：

- `readTranscript()` 全量读 + 解析：`/api/tasks/:id/transcript` 每次请求都全量，`readChatMessages()` 每次对话前都全量。
- `listTasks()` 扫描目录并解析所有 `task.json`：被 `file-policy.ts` 在**每次工具调用**时调用。
- `task-deletion.ts` 在删除任务时把**所有同项目任务的转写**读出来拼成字符串比对引用，随消息量线性增长。

## 3. 存储划分（本方案的核心）

| 内容 | 去向 |
| --- | --- |
| 任务元数据（标题、状态、目录、项目、归属、创建时间） | **PG** |
| 对话消息（用户/助手文本、工具调用与结果摘要、meta 事件） | **PG** |
| 会话索引 | **PG**（由任务表推导，取消独立文件） |
| 工作目录、上传件、成果、附件字节 | 磁盘（不变） |
| `.workpivot/`（记忆、计划、run-code、截图） | 磁盘（不变） |
| 技能、模板、设置 | 暂不动 |

## 4. 表结构

独立 schema `chat`，不与数据库链路的 `workpivot` schema 混用（两套用户模型与权限模型不同，混在一起会互相绑架）。

```sql
CREATE SCHEMA IF NOT EXISTS chat;

CREATE TABLE IF NOT EXISTS chat.tasks (
  id            text PRIMARY KEY,
  owner_user_id text,
  tenant_id     text,
  name          text NOT NULL,
  directory     text NOT NULL,
  status        text NOT NULL,
  stop_reason   text,
  project_id    text,
  temp          boolean NOT NULL DEFAULT false,
  last_seq      bigint NOT NULL DEFAULT 0,
  created_at    timestamptz NOT NULL,
  updated_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS chat_tasks_owner ON chat.tasks(owner_user_id, created_at DESC);
CREATE INDEX IF NOT EXISTS chat_tasks_project ON chat.tasks(project_id) WHERE project_id IS NOT NULL;

CREATE TABLE IF NOT EXISTS chat.messages (
  id         uuid PRIMARY KEY,
  task_id    text NOT NULL REFERENCES chat.tasks(id) ON DELETE CASCADE,
  seq        bigint NOT NULL,
  kind       text NOT NULL CHECK (kind IN ('user_message','assistant_message','tool_use','tool_result','meta')),
  payload    jsonb NOT NULL,
  parent_id  uuid,
  created_at timestamptz NOT NULL,
  UNIQUE (task_id, seq)
);
CREATE INDEX IF NOT EXISTS chat_messages_task_seq ON chat.messages(task_id, seq);
```

字段与现有结构一一对应：

- `chat.tasks` ↔ `task.json`：`id/name/directory/status/createdAt/projectId/temp/ownerUserId/tenantId/lastStopReason`
- `chat.messages` ↔ `transcript.jsonl` 行：`ts→created_at`、`ordinal→seq`、`kind`、`payload`、`parentUuid→parent_id`
- `sessions/index.jsonl` 的 `task_created` 直接由 `chat.tasks.created_at` 推导，不再单独存

## 5. 读写改造点

集中在 `packages/server/src/tasks.ts`，对外函数签名保持不变，调用方无需改动：

| 函数 | 改造 |
| --- | --- |
| `createTask` | 事务内 `INSERT chat.tasks`；目录创建逻辑不变 |
| `getTask` | 主键查询；可见性判断不变 |
| `listTasks` | `SELECT ... WHERE owner_user_id=$1 ORDER BY created_at DESC`；管理员分支放开 owner 条件 |
| `updateTaskStatus` | 事务内 `UPDATE chat.tasks` + `INSERT chat.messages(kind='meta')` |
| `appendTranscript` | 事务内 `UPDATE chat.tasks SET last_seq=last_seq+1 RETURNING last_seq` + `INSERT chat.messages`；`seq` 由数据库分配 |
| `readTranscript` | 分页版：`WHERE task_id=$1 AND seq<$2 ORDER BY seq DESC LIMIT $3`，默认取尾部 100 条 |
| `readHistory` / `readChatMessages` | 只取 `kind IN ('user_message','assistant_message')`，默认最近 200 条，`forModel` 语义不变 |
| `deleteTask` / `project-deletion` | 交给 `ON DELETE CASCADE`；共享引用检测改成按 `directory` 前缀查询，不再遍历全部转写 |

**顺带修掉两个现存问题**：

1. `ordinal` 用模块级自增计数器，进程重启后从 1 重来会与旧行重复；改为数据库 `last_seq`，单调且并发安全。
2. `readTranscript` 全量解析；改为分页后，`/api/tasks/:id/transcript` 支持 `before` 与 `limit`。

## 6. 并发与一致性

- 追加消息在单事务内完成“取号 + 插入”，同一任务并发写不会产生重复 `seq`。
- 前端同一任务本来就串行发送（`running` 表），跨实例并发由数据库唯一约束兜底：冲突时重试一次取号。
- 状态更新与状态事件同事务，避免“状态变了但历史没有记录”。
- 删除任务走外键级联，不依赖应用层逐条清理。

## 7. 配置与降级

```
# 运行时（读写 chat schema）
WORKPIVOT_CHAT_DATABASE_URL=postgres://workpivot_chat:***@host:5432/workpivot

# 仅建表时使用（schema owner）
WORKPIVOT_CHAT_DATABASE_ADMIN_URL=postgres://workpivot_schema:***@host:5432/workpivot
```

- 未配置 → 完全走现有 JSONL 路径，行为不变（便于灰度与回退）。
- 配置了但连不上 → **直接报错**（503 + 明确提示），不回落到文件，避免同一份对话出现两个真值。
- 建表不由应用执行：提供 `pnpm chat:install`（`scripts/chat-schema.mts`），与应用使用不同连接串；应用启动时只做 `SELECT 1 FROM chat.tasks LIMIT 0` 探测，失败则拒绝启动并提示执行建表脚本。

### 7.1 角色与权限

建表与授权用管理员连接（只在安装时使用），运行时用专用角色，**不给 DDL、不给其他 schema**：

```sql
CREATE ROLE workpivot_chat LOGIN PASSWORD '***'
  NOSUPERUSER NOCREATEDB NOCREATEROLE CONNECTION LIMIT 20;

GRANT USAGE ON SCHEMA chat TO workpivot_chat;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA chat TO workpivot_chat;
```

| 约束 | 原因 |
| --- | --- |
| 无 `CREATE` on `chat` | 应用不能建表改表，结构只能由 `chat:install` 变更 |
| 无 `workpivot` schema 任何权限 | 连接串泄露也碰不到业务表（任务、文件、记忆、知识） |
| `CONNECTION LIMIT 20` | 防止单服务实例把连接占满 |
| 不使用 `workpivot_app` | 该角色能读业务表，与“只存对话”的最小权限不符 |

密码轮换：`ALTER ROLE workpivot_chat PASSWORD '...'`，更新环境变量后重启；连接串只存在于 `stack.env`（0600），不进仓库与日志。

## 8. 分页与保留

- UI 首屏取最近 50 条，向上滚动按 `before=seq` 加载，每页 50。
- 模型上下文取最近 200 条（与现有压缩预算配合，超出交给 `compactMessages`）。
- 保留策略：默认永久保留；后续可加“超过 N 个月的转写归档到对象存储”，不在本轮。

## 9. 权限

P1 沿用应用层可见性（`taskVisibleTo`），数据库只给 `workpivot_chat` 一个最小权限角色（见 §7.1）。P2 再加 RLS：

```sql
ALTER TABLE chat.tasks ENABLE ROW LEVEL SECURITY;
-- 策略：owner_user_id = current_setting('workpivot.chat_actor', true)
```

管理员跨用户可见通过独立查询路径实现，不放开策略。

## 10. 迁移

不需要。用户确认可重新全量部署，旧 JSONL 不导入。若将来需要，可写一次性导入器：读 `task.json` 与 `transcript.jsonl`，按 `(task_id, seq)` 幂等插入。

## 11. 验收

| 项 | 判据 |
| --- | --- |
| 基本读写 | 新建任务、发消息、刷新页面历史完整；重启服务后历史仍在 |
| 长对话 | 单任务 5000 条消息时，打开任务首屏 < 300ms，发消息不做全量解析 |
| 任务列表 | 1000 个任务时列表查询走索引，`listTasks` 不再扫目录 |
| 并发 | 同一任务连续快速发送 20 条，`seq` 连续无重复 |
| 降级 | 不配 DSN 时行为与现在完全一致；配了但库不可用时报错而不是静默回退 |
| 删除 | 删除任务后消息级联清除；项目删除不影响其他项目 |
| 工具调用 | `file-policy` 每次调用不再遍历任务目录，改为一次索引查询 |

## 12. 不做什么

- 不把附件、成果文件字节写库
- 不双写（JSONL 与 PG 同时作为真值）
- 不改工作目录与 `run_code` 的行为
- 不在本轮加 RLS、归档与跨库分析
