# 事件溯源会话与中断恢复（2026-10-24）

状态：设计完成，未实现。对应 backlog R006。

## 1. 问题

当前一次运行是内存里的 `runAgentLoop`：进程崩溃、容器重启、发布滚动更新都会让运行凭空消失。用户看到的是“任务卡住/消息没回”，历史里可能留下一个**只有 tool_call、没有 tool 结果的 assistant 消息**，下次请求要么被 `replayableMessages` 丢掉（丢失上下文），要么模型协议报错。

数据库链路已有半套基础设施（`conversation_events`、`task_runs.model_messages`、fence、lease、`recover`），但只做到“标记中断”，做不到“恢复后继续”。文件链路完全没有。

目标：**崩溃后历史仍然合法、已发生的副作用不重放、用户能接着做**。

## 2. 现状盘点

| 能力 | 数据库链路 | 文件链路 |
| --- | --- | --- |
| 追加日志 | ✅ `conversation_events`（seq、turn、run） | ⚠️ JSONL 转写只存摘要 |
| 消息检查点 | ✅ `task_runs.model_messages` | ❌ 仅内存 |
| 租约与栅栏 | ✅ `lease_until` + `fence` | ❌ |
| 崩溃标记 | ✅ `recover()` → `interrupted` | ❌ |
| 权限清理 | ✅ pending/allowed → cancelled | ❌ |
| 未闭合工具对账 | ❌ 靠 `replayableMessages` 丢弃 | ❌ |
| 续跑 | ❌ 只能用户重发 | ❌ |
| 副作用去重 | ⚠️ 执行日志有 `run_id`，通用工具没有 | ❌ |

结论：**不缺表，缺的是对账与续跑**。

## 3. 事件模型

复用现有 `conversation_events`，不改 `kind` 的 CHECK 约束（避免迁移），细类型放进 content JSON 的 `type`：

| 事件 | kind | content 要点 |
| --- | --- | --- |
| 回合开始 | `meta` | `{type:'turn_started',runId,turnId}` |
| 步开始 | `meta` | `{type:'step_started',step}` |
| 助手消息 | `assistant` | 文本；工具调用见下 |
| 工具请求 | `tool_use` | `{tool,callId,argsDigest}`（不存全量参数，已有参数摘要规则） |
| 工具派发 | `tool_use` | `{type:'tool_dispatched',tool,callId,invocationDigest}` |
| 工具结果 | `tool_result` | `{ok,status,summary,resultRef?}`；超长结果落盘后只存引用 |
| 步完成 | `meta` | `{type:'step_checkpoint',step,seq}` |
| 回合结束 | `meta` | `{type:'done',stopReason}` |

原则：

1. **事件是审计与 UI 回放，不是模型上下文**。模型上下文只认检查点。
2. 不记录 token 流；`assistant_delta` 只走 SSE。
3. 单条 content 已有 200k 上限；超长工具结果必须走落盘引用（复用 `stashResult`）。

## 4. 检查点

- 在**每个 step 结束、且该 step 的全部工具结果已回填**时，同一事务内：
  1. 写 `tool_result` / `step_checkpoint` 事件；
  2. 更新 `task_runs.model_messages` 为当前完整消息数组。
- `model_messages` 是恢复的唯一事实来源；事件日志用于审计与“用户点开看过程”。
- 检查点原子性靠同一事务 + `fence` 校验；旧 fence 写不进去。

## 5. 恢复流程（启动时）

已有 `recoverExecutions` 在启动时按用户清扫，扩展为：

1. 选 `task_runs` 中 `status in ('running','stopping') and lease_until<=now()`（已有）。
2. 对每个 task 取 advisory lock（已有 `lock(c,taskId)`），保证多实例只有一个恢复者。
3. 读 `model_messages` 与最后事件 seq。
4. **对账**：
   - 末尾 assistant 带 `tool_calls`、但缺对应 `tool` 消息 → 为每个缺失 call 追加合成结果：`{"error":"上一轮执行中断，结果未知；如仍需该操作请重新调用"}`；
   - 有 `tool_dispatched` 但无 `tool_result` → 同样合成，并标记该调用 `interrupted`（**绝不重跑**）；
   - 全部闭合 → 无需合成。
5. 写 `done{stopReason:'interrupted'}` 事件，run 置 `interrupted`，task 置 `interrupted`（已有）。
6. 取消 pending/allowed 权限（已有）。
7. 若任务还有未完成计划，前端显示“已中断，可继续”。

## 6. 副作用一致性（核心约束）

- **at-most-once**：任何已 `tool_dispatched` 的调用在恢复时只补结果、不重放。宁可让模型看到“结果未知”，也不重复删文件、重复发布产物。
- 幂等分类（工具声明，不由模型决定）：
  - 可安全重试：`read` / `list_*` / `search_*` / `web_fetch`（只读）；
  - 不可重试：`write` / `edit` / `run_code` / `execute_skill` / `save_artifact` / 外部 MCP / 删除类。
- 通用工具派发记录：新增 `workpivot.tool_dispatches(run_id, call_id, tool, invocation_digest, dispatched_at, finished_at, status)`，主键 `(run_id,call_id)`；执行前后各写一次，恢复时据此对账。执行类工具已有 `skill_executions.run_id`，可并存。
- 许可复用：`run_permissions` 已存 `authorizationHash`，续跑时同一调用可复用，不重复弹卡。

## 7. 续跑策略

- **P1：手动续跑**。恢复只保证历史合法 + 标记中断；用户重发“继续”时，把 `model_messages` 作为基础上下文（而不是从转写重建），并在系统消息里追加一句“上一轮被中断，不要重复已完成的副作用”。
- **P2：一键继续**。对话里出现“继续”按钮，调用 `POST /api/tasks/:id/resume`：新 run、新 fence，继承 `model_messages` 与剩余步数预算，重放被取消的许可。
- **P3：自动续跑**。仅对“工具中断、无副作用未决”的运行自动续跑一次，需配额与次数上限（避免崩溃循环）。默认关闭。

续跑预算：步数继承剩余值（`maxSteps - usedSteps`），不重置；时长重新计时。

## 8. 文件链路

- 现状：JSONL 转写只存摘要，无法重建模型消息。
- 方案：新增 `.workpivot/runs/<runId>/messages.jsonl`（增量写完整消息，追加 + fsync 落盘），与转写分离；启动时扫描 `running` 但无心跳的 run（心跳文件 mtime + 进程 pid 校验），按同一对账逻辑补合成结果。
- 单进程假设下用进程内 Map + 文件锁；多实例不在本轮范围。
- 优先级低于数据库链路：文件链路正在被数据库链路替代，先做 P1 的“历史合法 + 标记中断”即可。

## 9. 边界与失败处理

- 重复恢复幂等：以 run 状态与 `status='interrupted'` 为条件更新，重复执行无副作用。
- 恢复失败的 run 保留 `running` 直到 lease 过期再重试，不能假报完成。
- `model_messages` 超大（>2MB）时只保留最近 N 条 + 引用，恢复后提示“历史已裁剪”。
- 续跑时模型供应商已变更：不自动续跑，提示用户“模型已变更，请重新发起”。
- 取消与恢复竞争：先取消后恢复，取消优先（`context_revoked` 已有）。

## 10. 分阶段与验收

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P1 | 未闭合工具对账 + 合成结果 + 历史合法；不自动续跑 | `kill -9` 在工具执行中 → 重启后任务显示中断、历史无悬空 tool_call、模型可继续对话；不重复执行已派发工具 |
| P2 | 一键续跑（新 run 继承检查点与剩余预算） | 点“继续”后从断点完成，已生成产物不重复、版本号不跳 |
| P3 | 文件链路对齐 | 同上，JSONL 检查点可恢复 |
| P4 | 有限自动续跑 | 崩溃循环不会无限重试；有配额与审计 |

测试建议：`eval/R006-recovery.mts` 用假 Pool 覆盖——未闭合补结果、重复恢复幂等、双恢复竞争只有一个成功、续跑继承预算、非幂等工具不重放。

## 11. 不做什么

- 不保证 exactly-once；只保证 at-most-once + 明确告知“结果未知”。
- 不重放已经流出的模型 token；恢复从下一个 step 开始。
- 不做跨模型迁移恢复。
- 不把事件日志当模型上下文（避免日志格式绑架上下文）。
