## 1. 背景与问题

用户会在同一逻辑资料上持续上传修订版本，例如合同初稿、修订稿和签署版。系统需要同时回答四类问题：

1. 哪一个是当前有效版本？
2. 历史版本和原文件是否仍可追溯？
3. 检索和模型默认使用哪一个版本？
4. 新版本出现后，由旧版本提取的记忆和业务事实如何处理？

原始文件、文件版本、解析文本、知识分片、向量、业务事实和记忆承担不同职责，不能混为同一份数据。

## 2. 目标与非目标

### 目标

- 原始文件不可变，任何更新都创建新版本。
- 文档逻辑身份稳定，版本可按用户和任务追溯。
- 默认只检索最新完成解析和索引的版本。
- 历史版本可显式查询、对比和恢复。
- 文件写入、元数据、解析和索引失败时可恢复。
- RAG 仅作为非结构化文档的派生检索层。

### 非目标

- 不把 RAG 当作记忆、业务事实或对话记录的真相库。
- 不在本期引入独立图数据库。
- 不在本期实现多人同时编辑同一文件内容的实时协作。
- 不把用户已下载到本地的副本纳入服务器撤回范围。

## 3. 数据职责

| 数据 | 是否权威 | 当前载体 | 说明 |
| --- | --- | --- | --- |
| 原始文件二进制 | 是 | 本地持久卷 `/data/files` | 按用户和不可变版本 ID 保存 |
| 文档逻辑身份 | 是 | PostgreSQL `workpivot.documents` | 保存任务、用途、当前 revision |
| 文件版本元数据 | 是 | PostgreSQL `workpivot.document_versions` | 名称、大小、SHA-256、来源和版本 |
| 解析文本/结构 | 派生 | PostgreSQL `document_processing` | 可由原文件和解析器重建 |
| 知识分片 | 派生 | PostgreSQL `knowledge_chunks` | 绑定具体文件版本 |
| 向量 | 派生 | pgvector `embedding_jobs` | 绑定分片和向量空间，可重建 |
| 对话记录 | 原始事件 | PostgreSQL `conversation_events` | 用于上下文、审计和回放，不作为项目文档 RAG 默认语料 |
| 三层记忆 | 已确认业务信息 | PostgreSQL `memories` / `memory_revisions` | 不能由 RAG 向量替代 |
| 业务事实 | 权威结构化事实 | PostgreSQL 业务事实表 | 金额、关系、合同状态等必须精确查询 |

## 4. 原始文件管理

### 4.1 存储布局

```text
/data/files/{ownerUserId}/{versionId}
```

- 目录权限 `0700`，文件权限 `0600`。
- 原始文件名只保存在数据库元数据中，不作为磁盘路径。
- 同一逻辑文件的新版本使用新的 `versionId`，不覆盖旧文件。
- 文件下载时重新校验大小和 SHA-256。

### 4.2 发布流程

```mermaid
flowchart LR
  U[上传] --> V[校验大小、文件名和读取范围]
  V --> H[计算 SHA-256]
  H --> W[写入不可变版本文件]
  W --> D[数据库提交版本记录]
  D --> P[异步解析]
  P --> C[分片]
  C --> E[可选向量索引]
  E --> A[切换当前可检索版本]
```

- 上传请求携带 requestId，重复请求不得重复创建版本。
- 新版本携带 expected revision，冲突返回 409。
- 先写文件、后提交数据库。数据库结果不确定时保留文件，等待孤儿清理，不能猜测删除。
- 单文件 10 MB、单文档 100 个版本、单任务 100 个文件为当前边界。
- 资料存储当前有 100 MB 全局上限；自助注册用户另有每日上传限额。

### 4.3 失败处理

| 失败 | 处理 |
| --- | --- |
| 文件写入失败 | 数据库不发布新版本 |
| 数据库提交失败 | 保留不可变对象为孤儿，后续校验后清理 |
| 解析失败 | 新版本保留在原件库，标记失败，不进入默认检索 |
| 索引失败 | 继续使用最近一个完整可用旧版本并明确提示 |
| 客户端超时 | 用 requestId 查询或重传，结果相同则不重复版本 |

## 5. 多版本规则

### 5.1 版本状态

```text
uploaded → parsing → indexed → current
                         ↘ failed / stale
current + 新版本完成索引 → superseded
```

逻辑文档保存当前 revision。历史 revision 只归档，不原地修改。

### 5.2 默认检索

1. 最新版本解析和索引完成时，默认使用最新版。
2. 最新版未完成时，可继续使用上一可用版，但引用和界面必须标记“旧版”。
3. 用户明确固定某版本时，只检索该版本。
4. 不得把不同版本的片段合并成同一事实答案。
5. 引用必须包含文件名、版本号和原文位置。

### 5.3 恢复历史版本

恢复不是修改当前指针到旧版本，而是以历史内容创建一个新版本并重新解析、索引、发布。这样可以保留完整操作轨迹。

### 5.4 删除

- 删除整份资料先进入回收站，并立即使所有版本退出检索。
- 回收站有引用时物理文件继续保留。
- 永久删除需要再次确认并检查派生知识、引用和回收站关系。
- 允许用户确认后删除单个版本；删除后该版本立即退出下载和检索，物理对象按回收站规则保留，永久清理时再删除。
- 单版本删除必须在同一发布流程中使分片、向量和引用失效；运行中的旧引用不得继续生成新成果。
- 仅由该版本支持的记忆和业务事实进入“来源已删除，待复核”；仍有其他来源的内容保留，但移除该版本证据关联。
- 删除当前版后不自动启用旧版，文档保持不可检索，等待用户指定其他保留版本。

## 6. RAG 使用边界

RAG 适合：

- 大量长文档及其跨任务复用。
- 需要自然语言模糊定位原文。
- 单份或合计内容超过当前上下文预算。
- 需要按版本、章节、页码、工作表或单元格给出引用。

以下场景不依赖 RAG：

- 单份短文档直接解析读取。
- 当前公开网页即时抓取分析。
- 精确金额、合同状态、收入、项目关系等业务事实。
- 用户偏好、项目约定和任务结论等三层记忆。
- 原始对话的近期上下文和审计回放。

公开网页只有被用户明确保存到项目知识库后，才进入文档解析和索引流程；即时抓取不会自动沉淀。

### 6.1 当前实例状态

2026-10-28 线上实例：

- 已配置向量空间：0。
- 原始文档、解析任务、知识分片：0。
- 三层记忆：7 条，已在 PostgreSQL 中。
- 近期 `search_project_documents` 调用存在，但因无文档内容，实际没有召回项目资料。

因此当前 RAG 属于“代码已具备、实例未启用”，不能描述为每个任务都会自动使用 RAG。

### 6.2 项目知识入库确认

项目知识库只接收文本类检索内容，并且必须由用户确认后入库：

```text
上传原始文件
  → 解析文本和结构
  → 显示待入库预览
  → 用户确认
  → 分片 / 向量索引
  → 可检索
```

- 用户不确认时，原始文件仍属于当前任务，但不进入项目知识库。
- 用户拒绝后保留来源和处理状态，不生成可检索分片。
- Word、PDF 正文以及 PPT 页面文字和备注属于文本知识。
- PPT 图表、复杂图片和扫描件需要先完成视觉解析或 OCR，识别结果仍需确认。
- Excel 的数值单元格和公式不默认转成文本知识；它们应进入结构化数据路径。只有用户明确选择的说明、备注或摘要可以作为文本知识入库。
- 公开网页只有用户执行“保存到项目知识库”并确认入库后才会持久化。
- 同一文档新版本仍单独确认，不能因为 v1 已确认就自动把 v2 发布到知识库。

## 7. 与记忆和业务事实的关系

- 新文件版本不会修改旧版本原件。
- 新版本提取出的内容先生成解析和检索候选，不直接覆盖已确认记忆。
- 业务事实引用具体文件版本和原文片段；金额、状态、日期和关系必须按结构化版本处理。
- 若新版本改变旧事实，应把相关旧记忆/事实标记为“待复核”，保留旧值及证据，等待用户逐条确认。
- 旧版本被新版本替代后，其 RAG 分片默认退出检索；历史复核和明确旧版查询仍可读取。

已确认：新版本替代旧版本时，引用旧版本的记忆和业务事实自动进入“待复核”，不静默覆盖旧值，也不自动把新值设为当前事实。该流程目前仍是目标设计，尚未完整实现。

## 8. 安全与备份

- 所有文件操作同时校验认证用户、任务归属、用途、版本和本轮授权范围。
- PostgreSQL 行级安全和文件元数据共同隔离用户，不能只依赖路径。
- 原始文件名、路径、哈希、解析文本和向量不得写入普通运行日志。
- 当前没有应用层文件加密、病毒扫描、对象锁或 WORM 合规归档。
- 数据库和文件卷必须成对备份；只恢复数据库会造成“有元数据、无原件”。
- 恢复后先校验文件存在性、大小和 SHA-256，再恢复解析和索引。

详细备份步骤见[备份与恢复](../../03-project/backup-recovery-20261016.md)。

### 8.1 当前服务器约束

当前目标服务器资源为 2 核 CPU、4 GB 内存、40 GB 磁盘。原始文件继续使用文件卷，不把二进制大对象存入 PostgreSQL：

- PostgreSQL 保存元数据、解析文本、结构化内容、分片和向量。
- `/data/files` 保存不可变原始文件和成果。
- 数据库 WAL、索引、备份和原始文件共享同一块 40 GB 磁盘，必须分别监控容量。
- 禁止把磁盘写满；达到预警阈值后停止新的文件上传和索引构建，聊天仍可降级使用已有内容。
- 不增加 MinIO/S3 容器，避免在当前 4 GB 内存下增加额外常驻服务和运维复杂度。
- 单机阶段不做多节点共享文件存储；迁移到对象存储的触发条件是增加应用节点、文件容量明显增长或需要独立备份/生命周期策略。

## 9. 可观测性

每个版本至少显示：

- 上传、解析、索引和当前状态。
- 解析器版本和向量空间。
- 版本号、大小、哈希、创建时间。
- 失败原因和可重试动作。
- 被哪些记忆、业务事实和成果引用。

审计只记录对象 ID、操作类型和结果，不复制私人正文。

## 10. 验收

| 场景 | 预期 |
| --- | --- |
| 并发上传同文档新版本 | 只有一个成功，冲突方收到 409 |
| v2 处理中检索 | 可使用 v1，但明确标记旧版 |
| v2 完成索引 | 默认切换到 v2，v1 退出默认可检索范围 |
| 显式选择 v1 | 只返回 v1 分片和引用 |
| 解析失败 | 不覆盖当前有效版本，保留失败原因 |
| 下载被篡改原件 | 哈希校验失败并拒绝 |
| 删除资料 | 所有版本立即退出检索，回收站保留期内可恢复 |
| 恢复历史版本 | 创建新版本并重新处理，不原地改写历史 |
| 跨用户访问 | 无论是否知道路径和版本 ID 都拒绝 |
| 未确认知识预览 | 原文件可访问，但不会生成项目知识分片或进入检索 |
| 已确认文本知识 | 只有确认的版本可以进入索引和默认检索 |
| 删除单个文件版本 | 原件按确认进入回收站，分片和向量同步失效 |
| 删除当前版本 | 不自动回退旧版；文档保持不可检索，等待用户指定其他版本 |

## 11. 待确认

### 已确认

| 编号 | 结论 |
| --- | --- |
| D-01 | 只有文本类信息进入项目知识库；上传后先预览，用户确认后才分片和索引；不做自动入库 |
| D-02 | 新版本改变旧事实时，关联记忆和业务事实进入待复核，不自动覆盖 |
| D-04 | 允许删除单个文件版本；删除时同步移除该版本的分片、向量、引用和仅依赖它的知识内容 |
| D-05 | 当前 2 核 4 GB / 40 GB 单机继续使用文件卷保存原始文件，不引入 MinIO/S3 |
