# 后台调度与多任务并发

日期：2026-09-14。状态：设计计划，未实现独立执行池或自动扩容。按用户最新要求，本设计的完整调度/执行池放到第二阶段，第一阶段先完成单用户全部功能，第三阶段做项目协同。后文“首版/首期”指本调度系统的首期实现，不是产品第一版；不再阻塞附件、解析和RAG开发。产品首版仅保留有界执行、任务状态隔离、停止/恢复及必要的独立解析处理进程。公网部署不变。

## 架构决定

采用统一HTTP接入、持久任务队列、独立Agent执行池、独立解析/索引执行池。Node.js实现业务调度与执行协议；容器平台负责实例生命周期、资源限制、健康检查和扩缩容，两者不能相互替代。按任务调度，不按用户、浏览器连接或标签页创建进程。一个Agent执行进程可承接多个异步模型请求；CPU密集解析使用单独受限进程。

首版继续Docker Compose单服务器部署：接入服务先1实例，Agent池从2实例、解析池从1实例开始验收，具体数量必须经CPU/内存盘点及压测调整，不作为容量承诺。固定副本数加可配置并发槽位，首期不声称具备自动容器扩缩。未来多机采用Kubernetes服务路由及HPA/KEDA，不让业务容器自行操控宿主Docker，也不挂载Docker socket。

区分三种能力：入口负载均衡分配HTTP连接；队列调度分配后台任务；自动扩缩容调整执行实例数量。已有SSE连接不会因增加接入实例而迁移；断线后用持久事件游标恢复，不依赖粘性会话。容器调度不会处理用户公平性、模型限额、重复副作用或任务上下文恢复。

## 队列及权限

首期沿用PostgreSQL，增量建设最小持久队列与运行状态机，不同时新增Redis和第二份任务状态真相。实现前核对成熟PostgreSQL队列组件是否满足事务一致性、用户隔离和租约；选用组件或受限领取实现需留ADR。BullMQ需要额外Redis，可作为吞吐量和运维评估后的替代；复杂长工作流再评估Temporal，本阶段不叠加多个调度系统。

提交消息、创建运行和入队必须同一事务，返回202及稳定runId/requestId；重复请求返回同一次运行。领取通过短事务、行锁/跳过已锁任务和原子额度更新完成；不得在模型或网络等待期间持有数据库事务。事件和最终状态持久化后才向客户端发布。通知仅唤醒订阅者，数据库才是恢复依据。

状态：queued → running → completed/failed/cancelled；waiting_user保存检查点并释放执行槽，确认后重新排队；retry_wait只供明确可重试步骤。waiting_user仍占同会话逻辑锁，不能让后续轮次越过尚未完成的轮次。

全局任务队列必须解决现有RLS限制：单独受限调度角色仅能通过窄接口领取最小运行元数据，不能读取全部用户对话或设置。worker取得服务端签发/绑定的owner、run、fence执行上下文，业务读写继续遵循RLS；禁止通过客户端指定owner或给worker开放BYPASSRLS。角色及跨用户越权测试是开发门槛。

每次领取含workerId、leaseUntil和递增/唯一fence；心跳续租，写结果核验持有权。数据库租约只能阻止过期执行器写数据库，不能保证外部调用恰好一次。解析/只读步骤可退避重试，外部写操作使用下游幂等键、操作账本；结果未知时暂停核对，不自动重复执行。

## 并发、公平与背压

同用户多任务可并行，同一会话仅一个活动轮次；后续消息拒绝或显式排队，不能静默覆盖。按用户轮转分配可用槽位，优先级配合等待时间提升，防止后台整理永久饥饿。配置全局、每worker、每用户基础/借用上限、每模型凭据RPM/TPM/同时调用数及每MCP服务上限。限额在多个实例间原子生效，不能各实例分别计数造成超卖。

资源空闲可借用用户额度；新用户进入后优先分配后续释放的名额，不强制中断正在执行的任务。对话、解析、索引/记忆分队列并预留对话资源。限制待排任务数、上传缓冲及数据库连接总数；超载明确返回排队/拒绝和可重试时间。事务连接按需取得，不能一轮模型调用长期占用连接。

## 上下文与客户端

一次运行尽量留在原worker，模型/工具循环复用内存上下文；等待确认或结束时保存检查点。缓存有字节上限、TTL/LRU，键包含owner/task/上下文修订/knowledge epoch/配置版本，删除或版本改变立即失效。恢复加载已确认摘要、近期消息及按需资料，不读取全历史或全部文件。缓存命中不是继续任务的前提。模型输入预算与客户端最近5组显示策略分开，未经确认不得使用压缩摘要。

客户端移除全局sending锁，按taskId维护草稿、附件、运行和确认状态；任务列表显示所有活动任务的摘要，当前任务订阅详细事件。用户级SSE可复用一条连接，事件带taskId/runId/sequence；重连按游标补拉，过期游标返回重建快照。切换任务、关闭页面不停止运行；取消精确作用于runId，旧取消请求不能误停新运行。客户端数据不是运行真相。

## 容器与扩容路线

Compose阶段：固定副本、手动调节容量、健康检查和restart、CPU/内存限制、优雅退出。可扩服务不写固定container_name，不绑定各副本同一宿主端口；多接入实例时由独立反向代理提供唯一入口。解析工具容器与可信Agent worker分离，受控挂载文件卷，不获得数据库管理员或宿主控制权限。

Kubernetes阶段：接入Deployment由Service/Ingress分流；Agent与解析/索引分别扩缩。按可执行积压、最老等待时间、忙碌槽位及CPU/内存综合决策，不只看CPU（模型等待时CPU可能很低）。KEDA/HPA需安装指标组件、配置最大/最小副本、稳定窗口和伸缩速率。等待用户确认或被模型限流的积压不直接触发无限扩容。

缩容先标记draining停止领取，完成或安全保存当前工作后退出；SIGTERM与宽限期必须覆盖，不能只按空队列杀死有在途任务的实例。扩Pod不等于扩机器，宿主资源不足则排队。API通常保持常驻；低优先级池以后可评估缩到零及冷启动代价。单机PostgreSQL仍是单点，多副本应用不等于系统高可用。

多机前置：目前原件在本机目录，扩到其他节点前需引入共享对象存储/可用卷方案，不能假设另一台worker能读取本机文件。数据库及模型连接预算应覆盖最大副本数。自动扩容平台部署属于后续阶段，不在首版直接引入集群。
