# 服务端集中存储与项目组协作预留

## 2026-09-16 用户确认：后续支持项目团队合作

维持第三阶段 K09 规划，不将其描述为当前 RC.1 已实现。团队合作指多位真实用户围绕同一项目协作；多个 AI 专家自动分工属于独立的多智能体能力，不作为团队合作的前置条件。

首批规划范围：

- 项目成员邀请、加入、退出和移除；项目负责人、编辑者、只读成员的权限分别定义。
- 显式共享项目资料、成果、项目记忆及所选任务；已有私人对话、个人记忆和私人专家经验不自动共享。
- 任务分派、负责人、状态、评论及交付审核；记录操作者和变更历史。
- 项目记忆更新先形成建议，由有权限的项目成员确认；采用版本校验，处理多人同时修改和相互冲突的建议。
- 服务端集中保存项目状态，成员端实时收到授权范围内的变更并支持断线补拉；撤权后停止后续读取、下载与事件推送。
- 项目成员身份不扩大模型、MCP 或 Skill 的平台权限；共享内容、来源删除及派生记忆失效继续受统一授权控制。平台管理员不自动取得项目内容访问权。

验收采用两个成员和一个非成员：验证共享范围、任务分派、记忆确认、编辑冲突、断线恢复及移除成员后的访问撤销。团队可复用的专家经验需另行显式发布与审核，不直接合并个人经验；在线共同编辑文档、离线双向合并列为后续增强。

介绍材料可表述为：“后续支持以项目为单位的团队协作，在统一后台和权限管理下共享资料与成果、分派任务，并共同维护经审核的项目记忆。”须标注为规划能力。

当前基础已是 PostgreSQL/schema25，向量 RAG 仍暂缓；以下 2026-09-14 的实现评估保留为历史设计背景。

日期：2026-09-14更新。状态：规划，前后端分离保持。第一阶段先实现单用户完整功能；第二阶段扩展多用户同时独立使用；第三阶段项目组共享与协同。PostgreSQL、pgvector/RAG、资料、聊天、记忆与任务执行全部位于后台服务器，单用户不等于客户端本地部署。

## 首版范围

- 用户端仅负责登录、交互、结果展示，通过服务 API 访问后台；不部署数据库、知识库或本地任务执行服务。
- 客户端保留必要的连接设置与会话状态；不维护长期业务数据副本。延续用户之前允许的成果下载/可选成果同步，不自动保存过程材料。
- PostgreSQL、pgvector、文件存储和知识处理作业统一在后台部署，数据库端口不暴露公网；客户端后台地址可配置。
- K08 负责服务器端服务生命周期、健康检查、升级与联合备份。撤回客户端安装 PostgreSQL/Docker/本地后台及默认强制回环地址的任务。
- 首版保留独立账号与严格私人空间；邀请成员、项目组共享、多人同步留待后续。现有远端部署不自动停止或删除。

## 当前实现评估

已有 HTTP 前后端分离、项目/任务、个人数据隔离、成果同步和版本等基础可复用。但当前项目访问只允许 ownerUserId 本人，业务目录按个人划分。虽然存在旧 memberUserIds 字段及辅助函数，它不代表有效的项目组协作能力。

已有成果同步是服务端到个人本机的单向下载，不能当作多人项目同步。当前 PostgreSQL/RAG 尚未实现，应该在新表设计时预留团队关系，避免以后将创建者字段当作永久权限边界。

## 新模型预留

| 对象 | 预留方式 |
|---|---|
| users | 后台可有多个用户，各自独立使用；不把当前用户写死为常量 |
| projects | 稳定 project_id、项目所有者、revision；所有权与记录创建者分开 |
| project_members | project_id、user_id、角色、状态、加入/撤销时间；首版仅项目所有者一条有效关系 |
| 项目资料、事实、片段、项目记忆 | 由 project_id 归属项目，created_by/updated_by 表示操作者；私人条目另有明确私有归属 |
| 个人记忆、个人设置、私人任务 | 继续 owner_user_id 隔离，加入项目组不自动共享 |
| 项目任务和对话 | private/project 可见性明确建模；后续由用户选择发布，不默认公开既有对话 |
| 文件对象 | 采用作用域对象键和授权引用，不以本机绝对路径或创建者目录决定团队权限 |
| 变更事件 | 稳定ID、修订号、事件序号、删除标记、幂等键；为后续同步提供来源 |

项目成员表可以先建表并用于本人访问策略，但首版不开放邀请、成员管理或共享接口。项目数据采用 project_id 外键；不得强制“每条资料创建者必须等于项目所有者”。个人数据仍使用 owner_user_id；按项目归属的数据采用项目一致性复合外键，防止跨项目挂接。

RLS/应用授权按资源类型区分：私人资源只有本人；项目资源由有效成员和角色授权。首版每个项目仅所有者有效，因此保持个人隔离。后续读者/编辑者/项目负责人权限扩展，平台管理员仍不获得所有私人项目访问权。

## 后续协作方式

在现有集中式后台上增加项目成员和共享权限：多位成员客户端连接同一后台，由同一 PostgreSQL 和文件存储保存团队权威数据。更新提交事务后推送变更通知，客户端按游标重新获取并断线补拉；成员身份和文件下载每次重新授权。

共同来源是服务端项目状态，不是复制多个客户端 PostgreSQL 数据目录。多人编辑通过版本检查处理冲突，原子发布知识新版本；权限撤销、删除及遗忘作为同步事件传播。成员离开后清理受控缓存并停止后续访问，但不能承诺收回已导出文件。

离线各自编辑、随后双向合并属于独立后续阶段，需要客户端变更队列、冲突解决、离线授权期限和删除协调；首版不实现完整 CRDT 或点对点数据库同步。

个人项目以后加入团队前需明确发布范围：项目资料和知识可选择共享，个人记忆始终私有，历史任务/对话不自动转为团队可见。个人项目转为团队项目需明确共享范围，无需从客户端搬运数据库；“不迁移当前旧 JSON 数据”的首版要求保持。

- K01 加入 project_members、资源作用域和操作者/所有权分离的设计；测试仅本人可访问及伪造成员无权访问。
- K02–K07 的来源、索引、版本和遗忘不写死个人目录；项目记忆支持未来共享，个人记忆不外溢。
- K08 覆盖服务器数据库/文件/作业服务的生命周期与联合备份；客户端验收包括服务器连接、断线恢复、覆盖升级和可选成果同步。
