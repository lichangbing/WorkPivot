# agent 循环：早停兜底、上下文压缩与编辑工具（2026-10-24）

状态：已实现，未部署。适用于文件链路（`app.ts`）与内核默认路径（数据库链路的 `execution.ts`、自动化的 `automation-worker.ts` 使用默认压缩）。

## 1. 问题

反馈是“不如其他智能体，遇到问题不去想办法解决”。对照 [loop.ts](../../code/packages/core/src/loop.ts) 与其它 agent 的实现，问题不在循环结构，而在三个策略：

1. **一次纯文本回复就结束**：`toolCalls` 为空即 `break`。弱模型常说“我将…/先了解需求”就停住，而成果核验闸门只检查文本里点名的文件，没点名就放行。
2. **被拒即停**：系统提示要求“访问被拒后不要改用其他工具，应告知用户并停止”，一次拒绝等于放弃。
3. **没有上下文压缩**：文件链路的消息只增不减，工具结果超过 5 万字符才落盘；长任务会撑爆窗口并逐渐遗忘目标。

（数据库链路另有“长对话压缩”摘要机制，需要用户确认才替换上下文；文件链路没有。本次的压缩是循环内的轻量兜底，两者不冲突。）

## 2. 改动

### 2.1 早停兜底（`onIdle`）

`runAgentLoop` 新增 `onIdle` 与 `idleLimit`：工具调用为空时先问一次“是不是该动手却停了”，返回非空字符串就作为用户消息继续，最多 1 次。

判定在 [continuation.ts](../../code/packages/server/src/continuation.ts)，两类触发：

- 用户请求是产出型任务（生成/整理/导出/制作…）且整轮**没有调用任何工具**；
- 助手文本自己承诺了下一步动作（我将/接下来/先…再）却没有执行。

纯咨询型问题（单句问号结尾）不追问，避免多花一轮。`idleLimit: 0` 可关闭。

### 2.2 上下文压缩（`context.ts`）

每轮采样前检查消息总字符数，超过 `contextBudget`（默认 120000）时：

1. 先把较早的工具结果替换为 `[已压缩] 早期工具结果 N 字符，内容已省略`；
2. 仍超预算时截断较早的 assistant 文本（保留 500 字符）；
3. `system` 与最近 10 条不动。

**只替换 `content`，不删除消息**，保证 `assistant(tool_calls)` 与 `tool(tool_call_id)` 的配对不被破坏（部分供应商对配对缺失直接报错）。可用 `WORKPIVOT_CONTEXT_CHARS` 覆盖，设为 0 或负数关闭。

### 2.3 流错误重试

模型流在**尚未输出任何增量**时失败，重试一次（间隔 400ms）；已有输出不重放，避免重复文本。

### 2.4 `edit` 工具

新增内置工具 `edit(path, old_string, new_string, replace_all?)`：精确文本替换，要求唯一匹配，歧义时提示补充上下文或 `replace_all`。用于修改大文件，避免整读整写。权限同时声明 read 与 write。

### 2.5 访问纪律放宽

原文“访问被用户拒绝后…应告知用户并停止”改为“不要用其他工具绕过这次拒绝去访问同一路径；但可以改用允许范围内的其他路径或其他方法完成任务”。保留“不得绕过同一路径拒绝”的安全意图，恢复行动力。

## 3. 验证

`code/eval/agent-loop.mts` 8 项通过（假客户端驱动真实循环）：

- 只表态不动手 → 追问一次并继续，追问进入下一轮请求；
- `onIdle` 返回 null → 立即结束；`idleLimit=0` → 关闭；
- 流错误且无输出 → 重试一次成功；
- 压缩：回到预算内、`tool_call_id` 配对保留、最近消息不动；预算充足不压缩；
- `edit`：唯一替换、歧义拒绝、`replace_all`、缺文件、无变化拒绝；
- 续跑判定：产出型请求与已承诺动作触发，普通问答不触发。

## 4. 已知限制

- 压缩是**字符估算**，不是精确 token 计数；预算偏保守。
- 压缩会丢失早期工具结果的细节，模型需要重新读取文件；不会破坏配对结构。
- 早停兜底只追问 1 次，模型仍可能二次表态后停下（此时按正常结束处理）。
- 流重试只在无输出时生效；已输出后中断仍以错误结束。
- `edit` 不做模糊匹配，缩进/空格不一致会报“未找到目标文本”。
- 自动化任务（`automation-worker.ts`）不启用早停兜底：它要求必须 `load_skill` 且工具零错误，模型空转会被判失败，语义已足够严格。

## 5. 决策显式化（设计，未实现）

### 5.1 目标分三层

| 层 | 含义 | 改动面 |
| --- | --- | --- |
| L1 可解释 | 每次“继续/停止”都有枚举原因，不再靠代码路径隐含 | `loop.ts` |
| L2 可审计 | 原因 + 计数 + 阈值写进事件，落盘可查 | `loop.ts` + 两条链路的事件写入 |
| L3 可重放 | 状态可序列化，能按决策序列复现 | 与 R006 合并 |

先做 L1 + L2（半天量级），L3 随 R006。

### 5.2 数据模型

```ts
export type ContinueReason =
  | 'tool_results'          // 有工具结果，继续采样
  | 'idle_nudge'            // 只表态不动手，追问一次
  | 'budget_continuation'   // token 预算未用满，nudge 继续
  | 'output_escalation'     // 输出被截断，提高上限重试
  | 'reactive_compact'      // 上下文超限，压缩后重试
  | 'retry_transient';      // 流错误无输出，重试

export type StopReason =
  | 'completed' | 'idle' | 'max_steps' | 'timeout' | 'aborted'
  | 'duplicate_calls' | 'context_overflow' | 'model_error' | 'tool_denied';

export interface StepDecision {
  step: number;
  action: 'continue' | 'stop';
  reason: ContinueReason | StopReason;
  detail?: Record<string, unknown>;  // 阈值、计数、压缩前后字符数
}
```

### 5.3 循环改造

现状是 `while (true)` 里散落 `break` 与 `continue`。改成“观察 → 决策 → 执行”三段：

```ts
for (let step = 1; step <= limits.maxSteps; step += 1) {
  const observation = await sampleOnce(...);        // 采样 + 工具执行
  const decision = decideStep(state, observation);  // 纯函数
  emit({ type: 'decision', ...decision });
  if (decision.action === 'stop') { stopReason = decision.reason; break; }
  state = applyDecision(state, decision);           // 唯一的状态变更点
}
```

`decideStep` 保持纯函数（不读环境、不发请求），决策顺序固定：

1. 中止信号 → `aborted`
2. 步数/时长超限 → `max_steps` / `timeout`
3. 上下文超限且未尝试压缩 → `continue: reactive_compact`；已尝试 → `stop: context_overflow`
4. 输出被截断且未升级 → `continue: output_escalation`；已升级 → `stop: completed`（标注截断）
5. 流错误且无输出 → `continue: retry_transient`（一次）
6. 无工具调用且有正文 → `idle_nudge`（一次）或 `stop: idle`
7. 否则 → `continue: tool_results`

顺序即优先级，避免“压缩”和“追问”同时触发时行为不确定。

### 5.4 事件与落盘

`AgentEvent` 增加一种：

```ts
{ type: 'decision'; step: number; action: 'continue' | 'stop'; reason: string; detail?: unknown }
```

- 文件链路：写进 `transcript.jsonl` 的 `meta` 行（`{event:'decision', ...}`），与现有 `usage` 事件并列；
- 数据库链路：写进 `conversation_events` 的 `meta` 行；
- 前端“过程”区展示关键决策（终止原因、压缩次数），调试面板展示全部。

### 5.5 守卫计数器

放在 `state` 里，随决策更新，恢复/重试时清零或保留：

| 计数器 | 作用 |
| --- | --- |
| `idleNudged` | 早停追问只一次 |
| `reactiveCompactAttempted` | 压缩重试只一次（否则死循环） |
| `outputEscalated` | 输出升级只一次 |
| `transientRetries` | 流错误重试次数上限 |

### 5.6 阈值集中

新建 `packages/core/src/limits.ts`：

```ts
export const LOOP_LIMITS = {
  maxSteps: 200, maxDurationMs: 30 * 60_000,
  idleNudge: 1, transientRetries: 1,
  reactiveCompact: 1, outputEscalation: 1,
  contextChars: 120_000,
};
```

现状这些值散落在 `loop.ts` 常量与 `app.ts` 环境变量里，集中后便于测试与审计。

### 5.7 与 R006 的关系

`decision` 事件就是恢复对账的依据：恢复时读最后一条 `decision`，能判断上一轮停在“采样中”还是“工具执行中”，从而决定补合成结果还是直接续跑。没有它，R006 只能靠消息数组反推。

### 5.8 测试

`eval/agent-loop-decisions.mts`，用脚本化假客户端断言决策序列：

- 正常三步：`tool_results → tool_results → completed`
- 只表态：`idle_nudge → completed`
- 截断：`output_escalation → completed`
- 超限：`reactive_compact → completed`
- 超限且压缩后仍超：`reactive_compact → context_overflow`（只压缩一次）
- 重复调用：`duplicate_calls`
- 中止：`aborted`（在途工具标记 stopped）

### 5.9 迁移顺序

1. 只加 `reason` 字段与事件，行为不变（可单独合并）；
2. 把判断抽成 `decideStep` 纯函数，保持决策顺序一致；
3. 接入 O-20/O-21 的恢复分支（此时守卫已就位）；
4. R006 复用 `decision` 事件做恢复对账。

### 5.10 与 Claude Code 的一致与差异

**一致的（同一原理）**：显式状态机、每次续转/终止有枚举原因、单一状态对象、纯决策函数、守卫计数器（对应 `hasAttemptedReactiveCompact`）、决策事件化。

**刻意的差异（不追平）**：

| 项 | Claude Code | 我们 | 原因 |
| --- | --- | --- | --- |
| 压缩 | 五层 + 缓存意识 | 单层字符预算 | 规模与窗口不同，五层的状态与缓存耦合成本大于收益 |
| 工具并发 | 安全性谓词按入参判定 + 流式执行 | kind 分批、执行后置 | 流式执行与授权卡冲突（需先确认才执行） |
| 持久化 | parentUuid 链 + 先落盘 + sidechain | `model_messages` 检查点 + JSONL | R006 的 at-most-once + 合成结果已能覆盖恢复需求 |
| 恢复语义 | resume 到断点 | 合成“结果未知”后从检查点续跑 | 服务端多用户场景下，宁可保守也不重放副作用 |
| 预算续跑 | token 预算 + 边际收益递减 | 仅 idle nudge | 先合并两套 nudge，避免互相干扰 |
| 模型 fallback | `fallbackModel` | 无 | 我们是多供应商可选，fallback 由部署配置决定，不在循环内做 |

**结论**：原理一致的是“决策显式化”这一层；其余按真实问题取舍，不以“和 Claude Code 一样”为目标。Claude Code 的 loop 承载了 resume/rewind/多端/dream 等大量特性，我们的循环简单得多，为形式引入复杂度不划算。
