# Office 处理开发参考：WorkBuddy 分析

日期：2026-10-17。状态：研究转开发参考。后续用户已确认将职责划分和三阶段改造记录到[统一开发计划](单用户正式发布补强方案.md)的SU-R2-03A至C；实施状态与排期以主计划为准。下文保留研究当时的证据和建议边界，不表示竞品全部能力都纳入开发或已在WorkPivot实现。

本记录汇总 WorkBuddy 5.8.3 的静态分析及用户配合完成的 Word、Excel 基础运行样本，供后续恢复 Office 功能开发时使用。本次只整理文档，不修改 WorkPivot 业务代码，不改变[总开发计划](../../03-project/tasks-postgresql-knowledge.md)的优先级与暂停范围。

## 1. 证据与复现边界

- [Office 总报告](../../01-research/competitors/workbuddy-office-static-20261017.md)包含工具入口、各格式路径、证据身份及运行结果矩阵。
- 静态分析覆盖安装包脚本、Skill、工具包装及部分实际运行依赖；REA 未完成原生编辑器内部算法反编译。不能据此宣称已还原 DOCX/XLSX 导入导出、排版或公式计算引擎。
- 运行分析覆盖用户操作的六项基础任务，具体工具调用来自对应测试时间窗的会话记录，产物由文件结构、公式缓存及哈希独立核对。REA 被动页面观察不等于完整调用级抓包。
- PPT 只有静态证据，本轮没有实际生成、读取、修改验收。复杂格式、宏、外链、并发编辑、撤销及完整故障恢复均未覆盖。
- 所有结论限定于记录中的样本与版本；WorkBuddy 更新后应重新核对包版本、文件哈希和关键行为。

## 2. 已观察到的处理流程

| 操作 | 实际路径 | 结果及限制 | 证据 |
|---|---|---|---|
| Word 新建 | 路由 Skill → brief-compose 生成 HTML → convert_doc.py → 本地编辑引擎导入并保存 DOCX | 标题、正文、表格正确；使用了跳过 preflight/verify 的参数，独立 XML 检查不代表视觉验收 | [生成实测](../../01-research/competitors/workbuddy-word-runtime-20261017.md) |
| Word 读取 | 复用打开实例 → 查询文档结构及表格 | 确实调用工具读取，源文件哈希未变；结构预览有长度与分页限制 | [读取实测](../../01-research/competitors/workbuddy-word-read-runtime-20261017.md) |
| Word 修改 | 打开副本 → 查询结构 → 查找替换与表格单元格修改 → 保存 → 读回 | 内容正确、源文件未变；保存重写部分样式、字体和节属性，视觉保真未验收 | [修改实测](../../01-research/competitors/workbuddy-word-edit-runtime-20261017.md) |
| Excel 新建 | 生成 openpyxl 脚本 → 独立 Python 环境执行 → LibreOffice 重算 → 核对公式和缓存 | 存在真实公式及缓存；结果符合实际收到的输入，但收到的合计公式与原拟测试要求不同 | [生成实测](../../01-research/competitors/workbuddy-excel-create-runtime-20261017.md) |
| Excel 核算读取 | 主代理委派 sheet-agent → read_table/get_cell_ranges | 读出公式及数据并指出合计遗漏；路径解析工具连续失败，改用有效文件及工作表标识后成功，原文件未变 | [读取实测](../../01-research/competitors/workbuddy-excel-read-runtime-20261017.md) |
| Excel 修改 | 直接单元格工具 → 保存 → 两次重算超时 → Agent 修补公式 XML → 第三次重算成功 | 最终结果 70、20、90，原件和 Word 样本未变；不能算作原生保存直接通过 | [修改实测](../../01-research/competitors/workbuddy-excel-edit-runtime-20261017.md) |
| PPT 生成/读取/修改 | SlideDSL 布局及 mutation → 编码 revision → 原生引擎 commitrevision/save；读取经 keyframe 转结构，改稿使用对象工具 | 实际 slidep 版本 6.6.1，最终序列化依赖原生引擎；没有本轮运行验收 | [PPT 深入分析](../../01-research/competitors/workbuddy-office-deep-ppt-20261017.md) |

关键认识：WorkBuddy 按任务选择路线。新建、读取、修改不是同一套流程；也不是所有操作都通过 Python 或子代理完成。短 Word 样本没有观察到完整长文编排，不能把 Skill 描述当作每次实际执行步骤。

## 3. 可供 WorkPivot 借鉴的实现原则

以下是后续方案评审的输入，尚未表示这些能力已实现或已排期。

### 按任务选择最小路径

新建文件可以采用模板或成熟文档库；修改已有文件应先评估结构和格式保留需求，不能默认重建整份文件。只在实际需要交互编辑与保真时评估编辑器集成，不因竞品使用原生引擎就引入同等复杂度。

读取与确定性单元格修改通常可直接调用工具；只有需要多步理解、核算或独立上下文时再考虑委派。无需机械复制竞品的多代理编排。

具体依赖仍须结合当前 WorkPivot 执行环境、许可证、部署和官方资料选型；本记录不确定采用腾讯引擎、LangChain 或新的编辑平台。

### 文件身份、定位与保存

- 复用真实文件会话，让预览、修改和保存对应同一文档。工具返回的 file_id 应按接口契约作为不透明标识使用：实测既有 UUID，也有有效路径形式，不能强制假设只有一种格式。
- 工作表显示名称不能代替 sheet_id；本轮实际 ID 为 `000001`。Word 段落和表格对象标识不能假设跨重新打开仍稳定，重新打开或结构变化后重新查询。
- Word 位置按 UTF-16 单元计数，结构占位也参与位置；表格范围的结束位置为包含式。Excel 修改工具本轮使用从 0 开始的行列索引。实现时逐接口核对，不能统一猜测。
- 保存后重新读取目标内容，并检查实际磁盘产物。工具成功、磁盘保存成功、公式已重算、结构正确、视觉已检查应分别记录。
- 原件保护优先复用现有文件版本与成果发布机制。失败时保留可用旧版本，不因外部工具已部分写入就发布成功；具体机制开发前核对现有实现，不另造重复版本系统。

### 读取完整性与 Windows 路径

WorkBuddy 的 resolve_local_excel 实际代码无条件要求路径以 `/` 开头，导致正确 Windows 绝对路径失败；伪造 POSIX 路径又在文件检查阶段失败。后续应在文件访问边界按操作系统处理路径，避免让模型反复猜盘符写法。WorkPivot 当前文件在服务端，应传递已授权文件版本标识，由执行层映射沙箱路径，不能把客户端盘符直接当作服务端路径。

完整读取不能只依据工具名称中的 full 或表头摘要。本轮 Word 文本预览有长度上限，Excel 的 header_rows 未包含首行全部内容。应记录已读范围、分页和截断情况；无法完整读取时说明覆盖边界，再按需分段。

### 公式、重算与错误判断

1. 同时核对实际收到的用户要求、公式表达式和业务预期。Excel 新建样本实际收到 `=SUM(D2)`，因此缓存为 30；这不同于原拟 `=SUM(D2:D3)` 的 50。输入发生变化的原因未定位，不能归因于重算引擎。
2. 区分 API 公式输入与文件序列化。本轮修改 API 要求公式以 `=` 开头，传入裸公式被拒绝；OOXML 的 `<f>` 存公式表达式、`<v>` 存缓存，二者都要独立核对，详见修改报告中的官方规范链接。
3. 本轮异常文件的 `<f>` 内出现前导 `=`，openpyxl 读成双等号；Agent 去除后重算成功。但首次 SDK 保存与首次重算之间没有磁盘快照，不能确定异常来自哪个组件，也不能证明它是超时的唯一原因。
4. 不将模型临时修补 ZIP/XML 作为常规保存方案。应先定位兼容性问题；确需格式修复时，限定变更范围、保留旧版并重新验证，另行形成实现方案。
5. 解析工具的应用状态和底层进程退出结果。本轮存在外层 completed 但内部失败，以及管道使重算失败的退出码被掩盖；不得因此显示成功。
6. 重算要有时间预算、明确失败提示和可取消边界。缓存数值存在不等于本轮重算成功，零公式错误也不等于业务公式正确。

### 保真、视觉与隐私

Word 修改后文本和单元格属性的部分比较一致，但样式 ID 重编号、字体归并、节属性补齐等已经发生。没有渲染对比，既不能宣布完全保真，也不能断言视觉损坏。后续按承诺的格式范围验收，不用简单文本样本代替复杂文档。

PPT 的视觉检查可退化为布局检查；Word 本轮跳过内置检查。检查未执行或不可用应明确记录，不能合并成“已验证”。

文件只读不等于整个 Agent 无写入副作用：本轮读取任务仍追加项目记忆。WorkPivot 后续应沿用用户的记忆控制及权限约定，区分文件读取与记忆更新；项目共享不应把私人聊天、个人记忆或私人专家经验自动公开。

## 4. 后续开发与验收如何使用本记录

恢复文档增强开发时，先核对当前代码与验收记录，再围绕用户确认的读、改或新建场景选方案。本次研究不替代 WorkPivot 的实现检查，也不撤销暂停文档增强的既有安排。

| 检查项 | 需要证明的结果 |
|---|---|
| 基础闭环 | Word、Excel 分别读取、新建、修改；目标内容与真实文件一致，源文件/无关文件未改 |
| 输入与完整性 | 实际收到的范围和公式可核对；长文、分页、超限表格不会被静默当作完整内容 |
| 文件身份 | Windows 服务端/沙箱映射正确；错工作表 ID、过期对象或版本冲突能解释并停止错误写入 |
| Excel 结果 | 公式表达式、缓存、业务预期分别正确；覆盖本轮 30/20/30 与修改后的 70/20/90，并解释前一组合计范围遗漏 |
| 失败处理 | 重算超时、内部错误及保存失败不冒充成功；取消或失败不发布未验证的新版本 |
| 格式与视觉 | 含样式、图片和复杂表格的样本按约定保留；结构检查与渲染检查分别记结果 |
| PPT | 独立补运行样本，再讨论动态结论；静态 DSL/revision 证据不能作为运行通过证明 |

已有 WorkPivot 记录可从[联合验收](../../03-project/memory-expert-office-acceptance-20260919.md)、[模型恢复验收](../../03-project/model-recovery-20260919.md)及[浏览器工作流验收](../../03-project/browser-workflow-20261016.md)进入，按日期和后续修正理解。不能用 WorkBuddy 的成功样本补记 WorkPivot 的验收状态。

## 5. 留存与证据使用

详细步骤、工具参数、文件哈希、异常与各自 JSON 证据保存在[竞品总报告及专项链接](../../01-research/competitors/workbuddy-office-static-20261017.md)。研究记录不携带专有原始源码或整个私人会话。

非敏感测试产物位于工作区 `tmp/rea-office-test`，临时目录不作为长期唯一证据。后续复测应按专项报告重建样本，重新保存输入、实际调用、输出和验证结果，不能使用历史哈希冒充新版本检查。
