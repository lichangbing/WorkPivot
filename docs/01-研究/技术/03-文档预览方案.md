- **调研人**：开发代理（与产品负责人共同确认结论）
- **日期**：2026-11-03
- **课题编号**：03
- **结论状态**：🔄 已有倾向（A 已上线，增量方案待产品负责人确认后落 ADR）

## 1. 背景与目标

- **为什么调研这个课题**：竞品 WorkBuddy 用内嵌专有文档引擎做可编辑预览，需判断其路线能否复用；同时核对本项目现有预览能力与“成果核验”要求（不下载也能判断版式）之间的差距。
- **现有实现（2026-11-03 核对）**：
  - 服务端 `code/packages/server/src/database/document-preview.ts` 的 `DocumentPreview.officePdf()` 已在使用：把 `.docx/.xlsx/.pptx` 交给既有隔离执行器 `runSandbox`，在沙箱内执行 `python3 /skills/office-preview/convert.py --source … --output /workspace/preview.pdf --mode render`（LibreOffice 转换），派生 PDF 走进程内 LRU 缓存 `CACHE_ITEMS=12` / `CACHE_BYTES=64MB`，不落盘、不改原件。
  - 接口 `GET /api/tasks/:id/file-versions/:versionId/preview`（`code/packages/server/src/database/app.ts:369-398`）先按扩展名直出（pdf/png/jpg/gif/webp/svg/md/txt/csv/json/html），Office 三类走转换，`AbortSignal.timeout(145000)`，响应带 `Content-Security-Policy: default-src 'none'; sandbox`。
  - 前端 `code/apps/web/src/WorkspaceRightPanel.tsx` 的 `PreviewSurface` 拉取该接口成 blob，PDF 用 `<iframe>` 交给浏览器内置阅读器；`4c8c6bc 修复 Chrome PDF 预览被沙箱拦截` 去掉了 PDF iframe 的 `sandbox=""`（Chrome 内置阅读器在任意 sandbox 下报 “This page has been blocked by Chrome”），HTML 预览仍保留 sandbox。
  - 首次打开有等待文案“正在转换为 PDF，首次打开可能需要一些时间…”，失败可重试；没有 docxjs，也没有“快速预览 / 版式验收”的区分。

## 2. 候选方案

| 候选 | 一句话简介 | 成熟度 | 许可证 |
| --- | --- | --- | --- |
| A. Office → PDF → 浏览器阅读器 | 服务端隔离执行器 + LibreOffice 转 PDF，前端 iframe 渲染 | **已上线（A 现状）** | LibreOffice MPL-2.0；渲染用浏览器内置阅读器 |
| B. docx-preview（docxjs） | 纯前端解析 OOXML 直接渲染 DOM，不依赖服务端 | 成熟（WorkBuddy 的兜底实现） | Apache-2.0 |
| C. 本地软件打开 | 下载或 `shell.openPath` 交给系统 Office/WPS | 成熟 | 无新增依赖 |
| D. 专有文档引擎 | 腾讯文档 WebOffice / WPS WebOffice / PageOffice | 成熟 | 商业授权，不可随产品分发 |
| E. 开源自托管编辑器 | OnlyOffice Docs / Collabora Online / Univer | 成熟度不一 | OnlyOffice AGPL-3.0；Collabora MPL-2.0；Univer Apache-2.0 |

## 4. 关键验证（PoC）

- **验证内容**：LibreOffice 转换出的 PDF 与 Word 原稿在中文段落、表格、页眉页脚、分页位置上的差异（字体缺失导致的换行/分页漂移是主要风险）；docxjs 在同样版面上的失真范围。
- **验证方式**：选 3 份真实复杂样版（含页眉页脚、合并单元格、中文字体、图表），走 A 逐页比对，必要时与 B 对照。
- **验证结果**：未执行。本轮只完成竞品机制取证、现状核对与路线判断；样版比对待确认范围后启动。

## 5. 结论与建议

- **推荐方案**：以 A 为主路径（已上线，保持“转换 → PDF → 浏览器阅读器”不变），做三件增量：
  1. **版式验收闭环**：明确“这是派生 PDF，原件未变”，把版式检查结果记在预览/验收状态上，而不是让用户凭截图判断。
  2. **失败与字体治理**：转换镜像固定中文字体集；把“引擎未启用”“转换失败”“文件过大/超时”分开提示，给下载与“本地打开”（C）两条退路，不把半成品当成功。
  3. **可选 B**：只有出现“要求秒开、服务端转换不可用”的实际场景再评估 docxjs，作为快速内容预览，并在界面上与“版式验收”明确区分。
- **理由**：
  1. A 已跑通并被验收脚本覆盖（`code/eval/workspace-right-panel-ui.mjs` 断言 PDF iframe 无 sandbox 且必须由 Chrome 阅读器真实渲染），增量成本低，且“所见即交付物”的保真度符合验收诉求。
  2. D 路线不可采纳——WorkBuddy 的引擎是 214 MB 专有二进制，随产品分发无授权、无法逆向、自身还缺 iframe `sandbox`，照搬等于引入不可控的本地 HTTP 编辑器。取证见[文字预览](../竞品/证据/腾讯办公智能体/文字预览运行-20261103.md)。
  3. WYSIWYG 编辑与“Agent 产出 → 用户核验 → 版本发布”的定位冲突：修改应由 Agent 走结构化变更产生新 revision，而不是让用户在预览器里直接改原件。
- **风险与缓解**：
  - 字体缺失导致分页漂移 → 转换镜像固定字体集，样版比对纳入发布前检查。
  - 首次转换延迟（复杂样版不可忽略）→ 保留现有 LRU 缓存，界面给进度与可重试，失败不阻塞任务主流程。
  - 浏览器差异（Chrome 内置阅读器可用，Firefox/Safari 行为不同）→ 桌面端以 Electron/Chromium 为准，Web 端降级为下载。
- **是否需要落 ADR**：✅ 是。方案定稿后写架构决策，明确“A 为唯一版式预览路径、B 仅作可选快速预览、不做应用内编辑、派生 PDF 不入库”。
