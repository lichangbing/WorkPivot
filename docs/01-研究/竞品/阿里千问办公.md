## 1. 产品概述

- **厂商与背景**：阿里巴巴。主程序 `QwenWorkCN.exe` PE 版本信息 `CompanyName = DingTalk`；Launcher/Updater/helper 等外围组件为 `Qoder`（阿里 AI 团队，即 Qoder 编程工具同源团队）；CLI 工具为 `Alibaba Cloud`。品牌名"千问办公"（zh_CN）/ "QwenWork"（en），协议头 `qoderwork://`。
- **产品定位**：面向个人与团队的全能 AI 工作台——对话、Agent 任务执行、文档/表格/PPT 生成、浏览器自动化、技能市场，形态上接近"WorkBuddy + 扣子空间"的合体，但执行引擎是本地 CLI + VM 沙箱。
- **目标客户**：先 C 后 B。工作区实测显示它已被用于承接真实企业咨询项目（AI 直接产出可交付的 docx/xlsx），插件示例覆盖 1688 买家助手、企业法务、投研分析等中文行业场景。
- **发展状态**：🧪 非常早期。本机存在 `1.0.1-26082607` 与 `1.0.2-26082817` 两个共存版本——版本号内嵌构建时间戳（`yyyyMMddHH`），两版相隔仅 2 天，`buildChannel=website` 公网渠道直发，快速迭代期。

## 3. 架构与技术观察

### 3.1 总体形态（推断）

```
┌─────────────────────────────────────────────────┐
│ Electron 37 壳（React 前端，asar 207MB）          │
│   主进程 index.js + build/ + node_modules        │
├─────────────────────────────────────────────────┤
│ qwenworkhelper.exe（Rust）  ← HelperConfig JSON  │  本机辅助
├─────────────────────────────────────────────────┤
│ qoderclicn.exe（agent CLI）  ← 任务执行引擎       │
│   └─ VM 沙箱（vm-boot 0.1.9 + vm-elevator 提权） │  隔离执行
├─────────────────────────────────────────────────┤
│ Chrome MV3 扩展 ←→ native-messaging-host         │  浏览器操控
└─────────────────────────────────────────────────┘
```

### 3.2 桌面壳与前端

- **React 系前端**：asar 内 `node_modules/react` 字符串存在、`vue` 为 0 次；含 vite/webpack 字符串，打包器不确定。
- **原生模块**（`app.asar.unpacked/node_modules`）：`better-sqlite3`（本地库）、`keytar`（凭据）、`node-pty`（终端）、`sharp`（图像）、`uiohook-napi`（全局键鼠钩子）、`@nut-tree-fork`（桌面 GUI 自动化）、`zstd-napi`、`clipboardy`、`jszip`。
- 崩溃上报为 Chromium 内嵌 crashpad（`--type=crashpad-handler` 字符串），未见 Sentry 运行时。

### 3.3 Agent 执行：CLI + VM 沙箱

- 执行引擎外置为独立 CLI（`bin/qoderclicn.exe`，162MB，与 Qoder 编程工具同源），主应用更像"编排壳 + 会话管理"。这与 MyAgents 的 sidecar 模式、WorkBuddy 的引擎外置思路殊途同归（见 [myagents.md](开源个人智能体工作台.md) §2.1）。
- **VM 沙箱是最大亮点**：`vm-boot/`（hvkit.exe、install/uninstall.sh、VM_VERSION 0.1.9）+ `vm-elevator.exe` 提权链，为 agent 任务提供硬件级隔离执行环境——在同类产品中目前只有它做了 VM 级隔离。
- 另有 `open-with-helper.exe`、`toast-activator-bridge.exe` 等系统集成小件。

### 3.4 浏览器自动化

- `chrome-extension/`（MV3 v1.5.8）权限含 `debugger`、`nativeMessaging`、`<all_urls>`，即通过 Chrome DevTools 协议全权操控浏览器。
- `native-messaging-host/`（Node 编写）负责扩展与桌面端通信。与 WorkBuddy 的浏览器扩展思路一致，但权限更激进。

### 3.5 安全与厂商组件

- `@qoder/security-guard` 内含 **AliSafeProxy.dll** 等 Alibaba 安全 SDK（反滥用/内容安全）。
- `qoder-auth-wasm/`：登录流程 WASM 化。
- `@qoder/windows-input-hook`、`@qoder/dji-mic-win`（DJI 麦克风支持，面向语音输入场景）。
- ⚠️ `uiohook-napi`（全局键鼠钩子）+ `@nut-tree-fork`（桌面自动化）组合意味着"AI 替你操作电脑"能力，权限敏感度高。

### 3.6 Claude Code 架构沿袭证据

`resources/migrations/` 共 44 个 SQL 迁移文件，其中：

- `0006_anthropic_multi_account.sql` —— Anthropic 多账号支持；
- `0010_remove_claude_code_credentials.sql` —— **曾经内嵌 Claude Code 凭据、后移除**。

结合内置 ripgrep（`@qoder-ai/qoder-agent-sdk`）与 SKILL.md 技能格式，可判断其 agent 内核沿 Claude Code 类架构改造（（推断，asar 未解包待验证））。⚠️ 凭据"先内嵌后移除"是一次典型的合规回调。

## 4. 技能与插件生态

生态分四层，全部采用 **AgentSkills/SKILL.md** 格式（Anthropic 发起的技能事实标准）：

| 层 | 位置 | 内容 |
|---|---|---|
| 内置技能 | `resources/skills/` | docx / pptx / xlsx / pdf / media-generation / qw-pages 等 |
| 技能市场 | `resources/skills-market/` | baoyu 系列、deep-research 等（清单：`skill-market-data.json`） |
| legokits | `resources/legokits/` | ai-slides（含 `ai-slides-mcp.cjs` **MCP server**）、canvas、writing——能力以 MCP 形式暴露 |
| 行业插件示例 | `resources/plugins-example/` | 1688 买家助手、企业法务、投研分析等中文行业模板 |

配套机制：

- **connectors**：`wecom-cli`（企业微信）——IM 接入起点。
- **awareness-templates**：`AGENTS.md` / `SOUL.md` / `HEARTBEAT.md` 人格与心跳模板，与 OpenClaw 的事实标准格式对齐（见 [openclaw.md](开源个人助理框架.md)）。
- **dynamic-text/qwenwork.json**：云端下发的动态文案，协议头 `qoderwork://`。

对照结论：WorkBuddy 的"专家/技能/连接器/插件"四概念在此收敛为"技能(SKILL.md) + 插件(行业包) + 连接器(IM)"三层，概念更少、格式更统一——SKILL.md + MCP 的组合几乎可以确定是未来一年的行业收敛方向。

## 5. 工作目录实测：任务产物的组织方式

### 5.1 定性：项目工作区，不是应用数据目录

`E:\workspace\qwenwork`（14MB，98 文件）内 **没有任何** json/db/sqlite/log/隐藏文件——不是应用配置或会话存储，而是 AI 执行真实咨询项目时的**文件工作区**。项目自述文件显示：编制方为"千问办公（客户名略）AI Native 咨询项目组"，源材料为用户 OneDrive 中 421 个文件（842MB），AI 逐份提取后产出岗位 SOP 汇编、审批配置手册等正式交付物。这说明该产品已被用于**重交付型的真实生产场景**。

### 5.2 产物五层结构

| 层 | 位置 | 格式 | 机制 |
|---|---|---|---|
| 知识提取层 | `用户发送材料-核心内容提取/`（00-总索引 ~ 10-索引，11 件） | Markdown | AI 通读源材料后的结构化笔记；**每条标注源文件绝对路径**；重复副本用 MD5+大小+首页结构比对去重 |
| 结构化数据层 | `sop_build/sop_data_p1-p3.py`、`sop_reqs.py` | Python dict | 37 个岗位的职责/KPI/工作项作为数据存储，角色名为主键 |
| 渲染生成层 | `doc_build/`、`sop_build/build_sop_all.py` | python-docx 脚本 | 数据与排版分离，共享排版库 `docx_lib.py`（字体/配色/表格样式固化） |
| 交付物层 | 项目根目录（26 件 docx/xlsx/pdf） | docx/xlsx/pdf | **文件名内嵌版本号+日期**（v1.0→v1.8 全程留痕），不用 git |
| 临时/抓取层 | `_tmp_oa/`、`_work/` | py/txt/png | 一次性抽取脚本、全文 txt（按 `<<<PAGE n>>>` 分页）、扫描件 140dpi 渲染 png |

### 5.3 值得记录的工程纪律

- **AI 生成内容可信度分级**：无源材料支撑、由 AI 反推拟稿的内容（如任职要求），统一渲染为红字"(拟稿待确认)"；提取层用 `<<待确认>>` 标记，全项目约 110 项待确认清单挂在总索引里等人工消化。★ 这是企业交付场景的关键信任机制。
- **数据/渲染分离**：内容当数据存（Python dict），排版规则进共享库——改内容不动排版，改排版不动内容。
- **过程痕迹保留**：报错残留（Traceback）、`__pycache__`、源文档副本都留在工作区不清理；总索引还有"提取方法备忘"（python-docx/PyMuPDF 文本抽取 + 扫描页视觉直读；弃用整册渲染图片——曾导致上一会话 60 秒流式超时）。AI 在跨会话地**自我总结工程教训**。
- ⚠️ 工作区卫生问题同样真实存在：一次性脚本、临时 png、报错残留混在交付目录里，无自动归档/清理机制。

### 5.4 记忆机制的位置（推断）

总索引明确出现"未重复提取（此前已读，**见台账/记忆**）"字样——说明 QwenWork 有跨会话记忆/台账机制，且存储在**应用自身数据目录**（本机应在 `%APPDATA%` 下，本次未探查），工作区只承接文件级中间产物。与 WorkBuddy"记忆在应用侧、工作区在文件侧"的双区模型一致。

## 6. 对 WorkPivot 的启示

### 6.1 值得借鉴

1. **AgentSkills/SKILL.md 兼容**（→ PRD-03）：QwenWork、WorkBuddy、OpenClaw 已全部收敛到该格式，WorkPivot 技能市场应原生兼容 SKILL.md 导入，零成本接入生态存量。
2. **产物五层结构 + 溯源纪律**（→ PRD-02 过程主线/产物管理）：知识提取层"每条带源路径 + 待确认标注"的纪律，可直接搬进 WorkPivot 的任务产物规约与文档生成技能模板。
3. **生成内容可信度分级**（→ PRD-02 授权卡/PRD-04 审计）：红字"(拟稿待确认)"是极低成本的信任机制，值得作为文档类产物的内建规范。
4. **数据/渲染分离的文档生成**（→ PRD-03 文档生成）：WorkPivot 的 docx/pptx 生成技能应采用同样的"内容数据 + 共享排版库"流水线，而非每次内联排版。
5. **VM 级沙箱方向**（→ PRD-02 执行隔离）：QwenWork 用 VM 沙箱 + 提权器解决"AI 动系统"的信任问题；WorkPivot MVP 虽不做 VM，但授权卡粒度设计应预留向沙箱执行的演进空间。
6. **多版本 Launcher/Updater**（→ 桌面端工程）：版本号内嵌构建时间戳 + 双版本共存 + 激活式切换，比 Squirrel 更可控，桌面端自更新可参考。

### 6.2 应当规避

1. **体量失控**：主 exe 204MB + asar 207MB + CLI 162MB + 多版本共存，装机占用 GB 级。WorkPivot 已定 Electron，须以 MyAgents（95MB）为体量标尺做预算。
2. **凭据合规回调**：migration 显示曾内嵌 Claude Code 凭据后移除——第三方凭据/模型接入从第一天就应走合规通道。
3. **权限敏感能力无感开启**：全局键鼠钩子 + 桌面自动化 + `<all_urls>` 调试扩展默认随包安装；WorkPivot 对等能力必须逐项显式授权并可在审计中追溯。
4. **工作区卫生**：临时脚本/报错残留/缓存混在交付目录。WorkPivot 工作区应有产物目录规约与自动归档。

### 6.3 差异化机会

1. **生态绑定 vs 模型中立**：QwenWork 深度绑定阿里云/Qoder（WASM 登录、qoderwork:// 协议、AliSafeProxy）；WorkPivot 可主打私有化部署与模型中立（PRD-04 多模型管理）。
2. **记忆可审计**：QwenWork 的记忆/台账是应用侧黑盒；WorkPivot PRD-05 的双层记忆（可视化、可编辑、晋升确认）是明确的差异化点。
3. **过程透明**：其交付物只见结果版本（v1.0→v1.8），过程主线藏在会话里；WorkPivot 的"过程主线"（PRD-02）把中间步骤、授权节点做成一等公民，面向"要看过程"的企业场景更有说服力。
