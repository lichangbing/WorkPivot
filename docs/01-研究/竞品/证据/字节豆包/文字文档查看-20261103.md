# 证据：豆包桌面端文字文档的查看与编辑（2026-11-03）

> 状态：✅ 已确认（运行实测 + 安装包静态分析）
> 样本：豆包 Windows 桌面端 2.34.6（Chromium 147.0.7727.149）
> 证据等级：运行观测与安装包文件清单为 A；内部模块分工与加载顺序为 B（静态推断，未逐条断点验证）
> 边界：只对一份真实 `.docx`（含标题/多级编号/表格，共 2 页）做了一次只读浏览与一次 CDP DOM 采样；未覆盖超大文件、协同编辑、离线断网、表格/幻灯片。

## 1. 结论

1. 豆包桌面端打开 `.docx` 不是“客户端解析 OOXML 后直接渲染”：**默认视图是服务端转好的 PDF，由 pdf.js（react-pdf）在标签页面板里渲染**，文字层可选中、按页容器排版。
2. 与此同时，窗口里常驻一个**空壳的办公画布 iframe**（`/partner/ccm-office/preheat`，`wiki-office-multi-tab-canvas`），所在面板被标记为“保留但隐藏”（`tabPanelRetainedHidden`，`opacity: 0`），即编辑态的热备容器。
3. 编辑能力的实现体是**内置的飞书 Bear 文档引擎** `@ccm-vmok/office-word`（buildVersion `1.0.0.1893`，构建名 `lark/ccm/office/docx`），以 vmok 模块联邦 + Garfish 挂载，资源全部随客户端落地。
4. `.docx` 与引擎内部模型之间靠 **ttoffice** 转换：`ttoffice_docx_converter.wasm` 提供 `Docx → clientVars` 与反向导出，大文件走原生 `lark_export.dll` 的流式导入接口。
5. 因此豆包的能力形状是“**云端转 PDF 做保真浏览 + 本地打包的云文档引擎做编辑**”，两条路径并存，不是单一渲染器。

## 3. 运行观测

### 3.1 窗口与目标

- `/json/version` 返回 `Chrome/147.0.7727.149`、`Protocol-Version 1.3`。
- `/json/list` 共 6 个目标，与文档有关的只有两个：
  - `page`：`doubao://doubao-chat/chat/<会话号>`（主窗口）；
  - `iframe`：`https://www.doubao.com/partner/ccm-office/preheat?...&preheat=1&preheatBiz=docx&multiTabCanvas=1&officeBasePreheat=1`。
- 主窗口 `Page.getFrameTree` 只有主 frame；文档没有独立顶层窗口、也不是 OOPIF。

### 3.2 文档标签页的真实渲染体

在主窗口内命中测试（`document.elementFromPoint`，窗口 1966×1636）得到同一祖先链：

```
tagPanel / tabContent
  └ instanceContainer      (964×1580)
     └ container / inter
        └ pdf-content
           └ scroll-view
              └ content
                 └ .react-pdf__Document      (949×2592)
                    └ .react-pdf__Page       (908×1284，2 页)
                       └ .react-pdf__Page__textContent.textLayer
```

- `.react-pdf__Document` 存在，`.react-pdf__Page` 计数 **2**，每个页容器内 `<canvas>` 实际像素 **1135×1605**（A4 比例）；
- 两个页面都有 `textLayer` 节点，正文可选中；标签标题与 `aria-label` 均为 `<文件名>.docx`；
- 页面没有 `contenteditable`、没有 `.docx-page-block` 之类的引擎节点。

即：**这一份 `.docx` 的浏览视图由 pdf.js 渲染的是 PDF，不是 docx 引擎的排版结果。**

### 3.3 PDF 的来源

同一次会话的资源请求里出现：

| 请求 | 说明 |
| --- | --- |
| `https://www.doubao.com/samantha/preview/mget_meta?...` | 预览元数据 |
| `https://www.doubao.com/samantha/pdf/ocr?...` | PDF/OCR 通道 |
| `https://p26-flow-sign.byteimg.com/tos-cn-.../samantha_server/<hash>.pdf?...x-expires=...&x-signature=...` | **带签名的派生 PDF**，即 pdf.js 实际加载的文档 |
| `https://lf-package-cn.feishucdn.com/obj/feishu-static/ccm-vmok/web/space-v2/...` | 文档面板前端 chunk |

派生物是服务端生成、限时签名的 PDF；客户端只做下载与渲染。签名参数与文档内容不在本证据中保留。

### 3.4 常驻的编辑画布

- `ccm-office/preheat` 这个 iframe 的 `body` class 为 `ccm-scope wiki-office-multi-tab-canvas layout-column`，`#root` 为 964×1580；
- 内部只有一个 0×0 的隐藏 iframe（`feishu.doubao.com/.../customize_cookie/set/?...LARK_SUITE_ACCESS_TOKEN...`，用于种 cookie），**没有** `contenteditable`、没有 `canvas`、正文为空；
- 它的祖先节点 class 含 `tabPanelRetainedHidden`，计算样式 `opacity: 0` —— 属于“保留但隐藏”的面板，与可见的 PDF 面板并存。

结论：这是**热备的编辑容器**，进入编辑时切换可见性即可，不必重新加载引擎。

## 5. 两条路径对照

| 维度 | 浏览路径（实测） | 编辑路径（静态证据） |
| --- | --- | --- |
| 渲染器 | pdf.js（react-pdf） | 飞书 Bear docx 引擎 `@ccm-vmok/office-word` |
| 数据来源 | 服务端转 PDF（签名 URL） | 本地 `.docx` → `ttoffice` → clientVars |
| 排版模型 | PDF 固定页 | 块模型 + `BLOCKTYPE.PAGE` + 页边距/分页属性 + 宽度档位 |
| 文本 | PDF textLayer（可选中，不可编辑） | `contenteditable` + 块编辑服务 |
| 载体 | 可见标签页面板 | `ccm-office` iframe（`tabPanelRetainedHidden` 热备） |
| 离线 | 依赖服务端转换 | 引擎本地可用，但导入/导出依赖本地 wasm/dll |
| 许可 | 闭源 | 闭源（`lark/ccm/office/docx`） |

## 7. 对 WorkPivot 的启示

1. **不要照搬“云端转 PDF + 本地引擎”的双轨**：它把保真浏览绑在服务端转换上，与私有化/离线的产品前提冲突，且引擎闭源不可分发。
2. **只读浏览与编辑要分开设计**：豆包把“看”和“改”拆成两条路径、两套资源，UI 上却是一个标签页。WorkPivot 若只做浏览，就不必引入 200 MB 级编辑器，也不需要 contenteditable/协同/撤销那一整套。
3. **PDF 作为保真基线是业界共识**：豆包（服务端）、WorkBuddy（本地专有引擎）、WorkPivot（隔离执行器 + LibreOffice）最终都落到“页”这一层；差别只在转换发生在哪一侧、谁承担字体与版式风险。
4. **隐藏热备容器代价高**：常驻 iframe + 预载引擎换来切换速度，同时带来内存占用与加载竞态；只读场景没有这个必要。

## 8. 复现步骤

1. 关闭豆包全部进程，以 `--remote-debugging-port=9333` 启动，访问 `http://127.0.0.1:9333/json/version` 确认 `Chrome/147.*`。
2. 在主窗口打开一份 `.docx`，`/json/list` 应看到 `ccm-office/preheat` iframe。
3. 对 `doubao://doubao-chat/chat/*` 目标执行 `Runtime.evaluate`，用 `document.elementFromPoint` 取右栏元素链，观察 `.react-pdf__Document` 与页面数。
4. 在同一页面 `performance.getEntriesByType('resource')` 过滤 `pdf`，可见 `samantha_server/*.pdf` 签名地址与 `samantha/preview/mget_meta`。
5. 静态侧：解压 `doubao_office.pak`，读 `static/v/w/vmok-manifest.json` 与 `current_revision`，再按 manifest 取 `module/*.js` 检索 `BLOCKTYPE.PAGE`、`docx-page-block`。
