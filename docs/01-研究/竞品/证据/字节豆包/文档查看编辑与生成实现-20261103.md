# 豆包文档查看、编辑与生成实现

日期：2026-11-03。样本：豆包 Windows 桌面端 2.34.6（Chromium 147.0.7727.149，飞书同源 Lark 壳）。类型：安装包静态分析 + CDP 运行观测。本文合并"预览/查看、读取、生成"三条链；配套的进程与 DOM 观测见 [文字文档查看与编辑](文字文档查看-20261103.md)。

## 1. 结论

1. 豆包桌面端把 Office 相关工作拆给了**两套互不相同的实现**：
   - 用户看到的"浏览"：服务端把 docx 转成 PDF，前端用 pdf.js（`react-pdf`）渲染，客户端**不解析 OOXML**。
   - 用户点"编辑"后的"编辑"：本地飞书 Bear 文档引擎（`@ccm-vmok/office-word`，vmok 联邦 + Garfish 微前端），以分页块模型渲染，可 `contenteditable` 编辑。
2. 本地 `.docx` 进入编辑器时，由 `ttoffice` 把 docx 转成 `clientVars`（`ttoffice_docx_converter.wasm`），编辑后再序列化回 docx；大文件导入走 native `lark_export.dll` 的流式通道（`TTOfficeLarkImport`）。
3. 生成（Word/Excel/PPT）**不在客户端发生**：客户端调用云端接口创建云文档产物、按阶段生成，再由导出接口把 `docx/xlsx/pptx` 下载下来；本地只负责渲染与另存。
4. 因此"豆包解析 Office 的能力"实质在**服务端**；客户端几乎没有 Office 解析库（校正后的扫描结果：mammoth/openxml 命中均为假阳性，pdf.js 为真）。

## 3. 预览 / 查看

### 3.1 实测路径：PDF + pdf.js

CDP 命中测试（主窗口 1966×1636）得到的右栏祖先链：

```
tabContent → tabPanel → instanceContainer(964×1580) → container → inter
→ pdf-content → scroll-view → content
→ .react-pdf__Document(949×2592) → .react-pdf__Page(908×1284)
```

- 两页 `.react-pdf__Page`，页内 `.react-pdf__Page__textContent.textLayer`（可选中文本层），每页 canvas 1135×1605。
- 该面板无 `contenteditable`、无 `.docx-page-block`，说明这里是**纯 PDF 浏览**，不是文档引擎。
- 网络侧请求：`https://www.doubao.com/samantha/preview/mget_meta?...`（取元信息）、`https://www.doubao.com/samantha/pdf/ocr?...`（PDF 文本层/OCR），以及带签名的派生 PDF（`p26-flow-sign.byteimg.com/.../samantha_server/<hash>.pdf?x-expires=…&x-signature=…`）。签名参数属用户数据，本文不记录。
- `.react-pdf__Document` 的 React props 只有 `className/style/children`，取不到文件 URL，故"文件 → PDF"的转换在服务端完成。

### 3.2 并存的编辑容器

同一个窗口里还有一个 `ccm-office/preheat` iframe（`preheatBiz=docx&multiTabCanvas=1&officeBasePreheat=1`）：

- `body` class = `ccm-scope wiki-office-multi-tab-canvas layout-column`，`#root` 964×1580。
- 内部只有一个 iframe，是 0×0 的 cookie 同步页（`feishu.doubao.com/.../customize_cookie/set/?...LARK_SUITE_ACCESS_TOKEN...`）。
- `contenteditable` 0 个、`canvas` 0 个、正文为空。
- 其祖先 `tabPanel-XC6WZ4 tabPanelRetainedHidden-EJpikI` 的计算样式是 `opacity: 0`。

即：**编辑器是预热的、保留但隐藏的热备容器**；当前浏览没有占用它。切换到编辑时才把文档塞进这个引擎（本报告未实测切换过程，属推断，标记 D）。

## 4. 读取：客户端不解析，服务端产出

校正后的 `biz.pak` 扫描（10,566 条目，gunzip 后按关键字统计）：

| 关键字 | 结果 | 判断 |
| --- | --- | --- |
| `mammoth` | 命中若干 | **假阳性**：命中在 emoji 名称列表中 |
| `openxml` | 命中若干 | **假阳性**：命中在 MIME 类型表中 |
| `pdfjs` | 命中且是完整库（条目 `7476`，339,420 B） | 真：服务端 PDF 的前端渲染器 |
| `clientVars` | 命中（条目 `8302`） | 真：`clientVarsToMerge`、分页游标等 |
| `docx2txt` / `SheetJS` / `pptxgenjs` / `toMarkdown` / `extractText` | 0 | 客户端无现成解析库 |
| `ocr` | 10 个文件 | 与 PDF 文本层/OCR 相关的前端代码 |

聊天侧读文档的桥在 `biz.pak` 的 `s2-office-chat-docx-rpc-bridge`（69,949 B）：内含 `samanthaApiService.SkillPack({skill_type: SkillType.WriteAssistant})` 与按 `resourceId` 的 RPC 客户端；另有 `canvas-docx-panel`（62,726 B）、`standalone-office-docx-canvas-definition`（188,214 B）负责画布挂载。

已知边界：本报告能确认"读文档由服务端接口完成"（`samantha/*` 请求 + 客户端无解析库 + chat bridge），但**没有抓到"聊天里读 docx 内容"的具体请求体与响应**，接口语义仍属 B/D 级。

## 5. 编辑：本地飞书 Bear 引擎

### 5.1 引擎包

`static/v/w/vmok-manifest.json`：

- `id = @ccm-vmok/office-word`，`buildVersion 1.0.0.1893`，`buildName lark/ccm/office/docx`，`pluginVersion 1.9.0`。
- `publicPath /static/v/w/`，shared 依赖 `react/react-dom 17.0.2`。
- 只暴露一个 `core` 远程模块，拆成 26 个同步 chunk + 192 个异步 chunk。
- `current_revision`：`revision:acb0975f…`、`pub date:2026-10-29 15:36:41`、`repo name:lark/ccm/office/docx`。

主 chunk `module/6db087afdec603a7.js` 15,603,733 B，内有 `BLOCKTYPE.PAGE`、`page_config`、`pageSize`、`margins`、`pdfA4Width/pdfA4Height`、`.docx-page-block`、`pagination.pageBreakBefore/keepNext`、`BlankPage/PageBreak` 命令、`docx-image-block/docx-diagram-block`、`contenteditable` 选区逻辑、`insert-chart/insert-text-box`。

渲染方式：**DOM 为主**（contenteditable + 块级结构），canvas 只做辅助（图表/图形/测量）。扫描 218 个模块文件（42.7 MB）：`canvas` 937 次、`getContext(` 244 次、`OffscreenCanvas` 57 次，但 `autoPageLayout`、`BLOCKTYPE.PAGE`、`docx-page-block` 等分页块证据更多。

版式模型：`docx_switch_wide_mode` 有 `STANDARD/LARGE/FULL` 三档（`wide-mode-standard|large|full` → `standard_width/wider_width/full_width`），是**流式宽度**而非固定 A4 分页。

### 5.2 docx 互转

`apps/doubao-office` 里的 `main.js`（997,742 B）包含：

- TypeScript 源路径 `domain/ttoffice/async-lark-import.ts`、`domain/ttoffice/word-stream-import-adapter.ts`。
- `11574.js` 导出 `convertDocxToClientVars`、`convertClientVarsToDocx`、`convertDocxWithFallback`、`isRetryableConvertError`、`withModuleFactory`、`withRemoteUrl`、`analysis` 等；默认 `optionsJson = '{"deterministic_seed":"docx-body","author":"0"}'`，临时目录 `/tmp/ttoffice-docx-converter`。
- `11659.js`（70,553 B）是 `ttoffice_docx_converter.wasm` 的 Emscripten 加载器，模块名 `@ccm-vmok/office-word:1.0.0.1893`，编译源路径可见 `code.byted.org/ee/bear-web-x/.../@ccme+docx-converter`。
- native：`TTOfficeLarkImport` / `TTOfficeLarkCancelImport`（`lark_export.dll`，45,768,592 B）；错误类 `LarkImportSessionDisposedError`、`WordStreamAbiUnavailableError`；会话字段 `docToken/last_seq`。
- 依赖下载：`https://tosv.byted.org/obj/lynx/ttoffice/v0.11.5/ttoffice-v0.11.5-win32-x64.zip`。

## 6. 生成：云端产物 + 异步导出

### 6.1 Word

- 创建：`create_docx({pageToken, title, scene, parentNodeId})`，失败埋点 `create_docx_error`。
- 模板：`AGWInsertTemplateContent({page_token, template_token, base_ver})`。
- 导出：`POST {base}/space/api/export/create/`，参数 `export_type`、`token`、`version`、`vc_tab`、`time_zone_offset`、`is_doubao_enterprise`；完成后 `GET {base}/space/api/box/stream/download/all/{token}?token=…&type=docx`。

### 6.2 Excel / PPT

- 表格产物同样是云文档：`NodeType.Spreadsheet=12`，导出走同一套 export API，下载埋点 `AI_SHEET_XLSX_DOWNLOAD=ai_sheet_export_xlsx_download`。
- PPT 是**分阶段产物**：`async-canvas-ai-ppt` + `ai-ppt-outline`（大纲）+ `ai-ppt-template`（模板）+ `ai-ppt-slide`（逐页），`NodeType.SlidePPT=9`；下载埋点 `AI_PPT_PPTX_DOWNLOAD=ai_ppt_export_pptx_download`、`AI_PPT_PDF_DOWNLOAD`。
- 资源模型：`content_blocks_v2` 里的 `BLOCK_ARTIFACT`，字段 `artifact_block.resource_id`、`resource_version`、`minor_version`、`snapshot_page_minor_version`；产物带版本号与快照，便于回放。
- 引擎与预热由 AB 开关控制：`ab_config.ab_results.enable_docx_canvas_preheat`、`enable_slide_canvas_preheat`；渲染走 `static/v/{w,s,p}/…/vmok/vmok-manifest.json`。

### 6.3 与本地文件的关系

- 本地 `.docx` 的"编辑"是把文件导入成云文档（`clientVars`），不是原地改字节；保存/导出才落回 docx。
- 本地文件身份靠 `openFile` 消息的 `filePath` 与 `tempDocxPath`，宿主侧有 `prepare-local-office-canvas`、`sync-local-office-canvas-sessions`、`close-local-office-canvas-session`、`list-opened-local-office-documents` 等 IPC 通道，说明画布会话是被宿主显式管理的多标签生命周期。

## 7. 安装包结构（复现用）

- pak v5 头 6 字节：`u32@0=5`（version）、`u8@4`（encoding）、`u32@8`（count）；条目表自偏移 12 起，每条 6 B = `u16 id` + `u32 offset`（**offset 在 +2**；按 +4 读会整表错位，这是本报告修正过的坑）。
- 长度 = 下一 offset − 本 offset；绝大多数条目是 gzip（`1f 8b`）。
- `apps\doubao-office\doubao_office.pak` 11,925 条目（office 运行时 + 引擎）；`biz\biz.pak` 10,566 条目（主 Web + 聊天 + 部分 office chunk）。两者内容不同，不能混用。

## 9. 对 WorkPivot 的启示

1. **查看与编辑分离**是降低风险的工程选择：查看用服务端 PDF 保证保真，编辑才引入重引擎；WorkPivot 若只做浏览，等价于"服务端 PDF + 前端 pdf.js"这一条链。
2. 服务端转换接口要自带文本层/OCR（豆包用 `/samantha/pdf/ocr` 补可选中文本），否则浏览体验退化。
3. 云产物 + 版本快照（`BLOCK_ARTIFACT` + `minor_version`）值得借鉴：每次生成都有可追溯的资源版本，而不是覆盖同一文件。
4. 生成分阶段（大纲 → 模板 → 逐页）比一次性生成整本更可控，也更容易中断恢复。
5. 不应照搬：专有引擎不可获取；`opacity: 0` 的热备容器会空耗内存与端口；客户端与服务端双份渲染逻辑带来一致性问题。
