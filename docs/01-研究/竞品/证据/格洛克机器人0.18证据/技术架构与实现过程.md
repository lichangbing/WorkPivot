## 1. 先厘清“泄露”的真实形态

### 1.1 发生在发行物，不在 source map

2026-08-23，社区作者发布 Grok Bot 0.18.0 的“源码导向重建”。传播过程中最常见的错误解释是“Electron bundle 中残留 source map”。原样运行时归档的字节级核查给出了不同结论：

| 检查 | 结果 |
| --- | --- |
| macOS DMG 完整文件树 | 1,296 个文件，`.map` 文件数为 0 |
| Windows `app.asar` | 726 个文件，`.map` 文件数为 0 |
| Runtime bundle 中 `sourceMappingURL` | 0 |
| Renderer chunk 中 `sourceMappingURL` | 0 |
| bundle 中出现的 `sourceMap` 文本 | 属于 OpenTelemetry/protobuf 字段，不是 JS source map 引用 |

实际原因是 Electron 主进程、Host、Coordinator、本地执行守护等 bundle 以 esbuild **未压缩产物** 发布。产物保留了：

- 原始类名和函数名；
- 可读注释；
- 声明模块来源的 `// ../../packages/...` 路径；
- 构建机路径和 pnpm 依赖位置；
- 字符串、RPC 契约、工具描述和部分调试语义。

Renderer 则是压缩后的生产 JavaScript/CSS，且没有 source map。因此同一个安装包里，后端运行时接近可读源码，前端却不能完整还原。

### 1.2 社群如何得到可读源码

原样归档没有改写代码，而是做确定性切片：

```text
官方安装器
  → 提取 app.asar
  → 读取 13 个 runtime bundle
  → 在 esbuild module-path 注释边界切分
  → 保存声明路径、offset、length
  → 按 manifest 重拼并与原 bundle 做逐字节比较
```

原样归档自报的规模是：

```text
13 个 bundle
6,561 个模块切片
2,357 个首方模块
32 个可识别首方包
4,204 个第三方依赖切片
```

它只包含运行时，不包含 renderer、native 二进制和完整 deps 树。这样重建后的 bundle 可以无损还原，但原始作者 monorepo 的文件边界仍不能仅凭包路径确定。

### 1.3 安装包与平台差异

| 层 | 产物 | SHA-256 |
| --- | --- | --- |
| macOS arm64 安装器 | `Grok_Bot_0.18.0.dmg` | `a253ccd8aab01e083f9812a0264354c5034d8ba7f0610bbb557e82ae77d203eb` |
| Windows x64 安装器 | `Grok_Bot_0.18.0_Setup.exe` | `464079a15ef5fa8b61ccea8fffcc78f63cfcf6df65fb0ad5e725d8b95f7e437e` |
| macOS `app.asar` | 从 DMG 提取 | `6665408168466f9cacc6087e917890c17f59d2e2e9c2404a5c4a59ad79c1de58` |
| Windows `app.asar` | 从 NSIS 安装器提取 | `38e85c0e5042c0257db7925e1e55709d6d155d90d92fe26ad654127d509766e0` |

macOS 与 Windows 的 13 个同名 runtime bundle 都存在字节差异。例如同一个 `preload.cjs`，Windows 版开头多出两个字节。该差异不一定改变业务语义，但足以说明：

- 不能把 macOS 重建文件直接称为跨平台官方源码；
- 平台路径、native bridge、文件系统与窗口行为必须分别验证；
- “版本号相同”不等于“构建产物相同”。

## 2. 仓库谱系

### 2.1 主谱系

```text
Anysphere 官方 0.18.0 macOS / Windows 安装包
        │
        ├─ 原样运行时归档
        │    ChHsiching/grok-bot-0.18-original
        │    逐字节 bundle + 模块切片，无产品功能新增
        │
        └─ 主流可读重建
             b-nnett/grok-bot-0.18-reconstructed
             保留原厂 renderer + 窄补丁 + 可读 TS runtime
                    │
                    ├─ 大量 fork/镜像
                    ├─ Windows / 离线 / 代理网关分支
                    ├─ 中文 / SwiftUI / Intel 平台派生
                    └─ GrokNode 等持续扩展分支
```

### 2.2 为什么会出现多个“版本”

这里的“多个版本”至少有五种不同含义：

1. **官方平台构建：** macOS arm64 与 Windows x64 都是 0.18.0，但字节不同。
2. **证据整理版本：** 原样运行时归档与可读 TypeScript 重建整理同一构建输入的方式不同。
3. **社区重建修订号：** `0.18.0-reconstructed.1` 等表示重建项目自己的修订，不是上游 0.18.1。
4. **后续功能派生：** GrokNode 以 0.18.0 为输入，但把产品版本标成 `0.78.1-reconstructed.1`，又移植了 0.66、0.78.1 等版本的界面或行为。
5. **真假混杂的后续泄露传闻：** 出现 0.77 等重建仓库不能反证存在同等完整的 0.77 官方源码泄露；必须以固定产物和 provenance 单独核验。

### 2.3 各仓库的证词强度

| 仓库 | 版本改变什么 | 不应误读 |
| --- | --- | --- |
| `ChHsiching/grok-bot-0.18-original` | 提供可验证的官方 runtime bytes | 无 renderer、无许可证，只适合研究 |
| `b-nnett/grok-bot-0.18-reconstructed` | 把可读 runtime 重组成 TS，并加入路由、Docker、本地用量等演示功能 | 不是官方 monorepo；新增功能不属于 0.18 |
| `GeniusTDY/grok-bot-0.18` | Windows x64、离线 node_modules、OpenAI-compatible gateway | Windows 行为需要独立验收 |
| `tyonger-stack/GrokNode` | 本地 Docker、Node Agent API、多 Bot UI、后续版本界面移植 | 包版本 0.78.1 不是官方 0.78.1 源码 |
| 中文版、SwiftUI、Intel 包装仓库 | 本地化或产品行为再实现 | 设计相似不等于代码同源 |
| 同时间大批 fork | 通常与原仓库同一 commit/tree | 仓库数量不是独立实现数量 |

### 2.4 供应链与权利边界

- 原样归档写明运行时代码版权归 Anysphere，仓库不授予任何代码权利。
- 主流重建的 `NOTICE.md` 明确不主张也不授予上游源码许可，并要求分发者独立审查版权和商标。
- 个别派生仓库自行标注 MIT/Apache，不会追溯改变它们包含的上游代码、提示、图标、CSS 或资源的权利。
- 热度最高的事件也是恶意软件伪装高峰。研究只读取 GitHub 源码和说明，不执行第三方构建产物。

## 3. 进程与部署架构

### 3.1 总体拓扑

```text
┌──────────────────────────────────────────────────────────────┐
│ User host                                                     │
│                                                              │
│ Electron Renderer                                            │
│   UI / transcript / composer / agent roster / VNC viewer      │
│            │ preload RPC + transferred MessagePort            │
│            ▼                                                  │
│ Electron Main                                                │
│   window / account / settings / secrets / plugin / Box link   │
│            │ utilityProcess.fork                              │
│            ▼                                                  │
│ Node Agent Coordinator                                       │
│   command dispatch / events / reconnect / local-exec daemon   │
│            │ HTTP /api/* + SSE /events                        │
└────────────┼─────────────────────────────────────────────────┘
             │ Brokered gateway descriptor or local port map
┌────────────▼─────────────────────────────────────────────────┐
│ Box / Agent computer                                         │
│                                                              │
│ Host                                                         │
│   gateway server / transcripts / sessions / inference / turns │
│   tools / MCP / approvals / memory / automation / audit       │
│                                                              │
│ Execution plane                                              │
│   shell / file / browser / desktop / noVNC / exec daemon      │
│   persistent files, apps, login sessions and Agent windows    │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 Electron Renderer

Renderer 负责产品体验和输入：

- 消息、附件、富文本和 Agent/Group 选择；
- 实时 transcript、工具活动、Widget、审批卡；
- Box 状态、VNC 画面、桌面接管；
- 设置、插件、Routine、Workflow 和用量界面。

源码中的窗口配置为：

```ts
contextIsolation: true
nodeIntegration: false
preload: deps.preloadPath
sandbox: false
```

这说明 Renderer 不直接拿 Node 权限，具备上下文隔离；但 Electron 的 Chromium sandbox 被关闭，不能把这个配置直接当作 WorkPivot 的安全基线。Main 代码还显式配置了 `--no-sandbox`。

### 3.3 Preload

Preload 不是通用 Node 通道，而是白名单桥：

- 暴露固定的 `desktop`/main RPC 方法表；
- 为 Renderer 申请 Coordinator 数据端口；
- 用 `MessageChannelMain` 把端口转移给 Coordinator；
- 复核请求来源是受信任 Renderer；
- 将事件从主进程或 Coordinator 转成前端可消费的数据；
- 对协议违例 fail closed，而不是自动降权执行。

Coordinator 与 Renderer 分离后，后端协议、stream 和恢复逻辑不需要经过 Electron IPC 的每次请求往返。

### 3.4 Node Agent Coordinator

Coordinator 运行在 Electron `utilityProcess`，承担：

- main RPC 与 coordinator RPC 的分发；
- 连接 Box gateway；
- 将业务命令 POST 到 `/api/<method>`；
- 持续消费 `/events` SSE；
- 管理 SSE 重连、stall watchdog 和连接代次；
- 路由 transcript、Agent roster、transport 状态和审批事件；
- 托管本地执行守护进程的连接和恢复；
- 在社区扩展中承接模型路由和 MCP bridge。

它不是 Agent loop 本身。真正的推理、会话、工具循环和审批在 Host。

### 3.5 Host 与 Box

Host 在 Box 中监听 gateway，并拥有：

- Agent manager 与 transcript；
- 模型 provider 和 turn runner；
- 动态工具集；
- MCP 生命周期和授权；
- 本地执行桥；
- memory、profile、routine、workflow；
- action audit；
- Box 状态、窗口、文件与环境。

Box 是持久机器，不是每次工具调用临时创建的容器。产品在语义上区分：

- 一台共享 Box 文件系统；
- 每个 Agent 的私有窗口/桌面；
- 用户自己的电脑；
- 客户端主机的文件系统。

## 4. Gateway 协议

### 4.1 路径与鉴权

固定契约来自 `source/shared/gateway-wire.ts`：

```ts
export const GATEWAY_API_PREFIX = "/api";
export const GATEWAY_EVENTS_PATH = "/events";
export const GATEWAY_HEALTH_PATH = "/health";
export const GATEWAY_AUTH_SCHEME = "Bearer";
export const GATEWAY_TRACEPARENT_HEADER = "traceparent";
export const GATEWAY_NETWORK_TOKEN_HEADER = "x-anyrun-network-token";
```

命令请求形态：

```http
POST /api/sendPrompt HTTP/1.1
Authorization: Bearer <gateway-token>
Content-Type: application/json
traceparent: 00-<trace-id>-<span-id>-01

{"agentId":"...","prompt":"...","clientNonce":"..."}
```

Host 使用 timing-safe compare 校验 Bearer token；远端 Pod 还可能要求 network token。健康接口只公开 `ok`、`pid`、`isBusy`、活动 Agent、启动时间和最近忙碌时间，不把完整会话内容当健康状态。

### 4.2 命令方法族

完整命令表在 `source/host/gateway-protocol.ts`。按业务分组：

| 方法族 | 代表命令 |
| --- | --- |
| Transcript | `getTranscript`、`getAgentTranscript*`、`getAgentThread`、`getConversationOutline` |
| 用户输入 | `sendPrompt`、`promptAcceptanceStatus`、`respondToWidget`、`dismissWidget`、`submitSecret` |
| 审批 | `resolveAutoReviewApproval`、`resolveLocalToolPermission` |
| Agent/Group | `listAgents`、`createAgent`、`updateAgent`、`createGroup`、`setGroupMembers`、`broadcastToAgents` |
| Memory | `getAgentMemories`、`deleteAgentMemory`、`clearAgentMemories` |
| Routine | `listAllAutomations`、`createAgentAutomation`、`updateAgentAutomation`、`runAgentAutomationNow` |
| Workflow/Skill | `getAgentWorkflows`、`importAgentWorkflow*`、`skillsCatalog`、`publishSkill` |
| MCP/连接器 | `refreshMcp`、`listRoutedMcpTools`、`executeRoutedMcpTool`、`completeMcpOAuth` |
| Box | `getForeverBoxStatus`、`ensureForeverBox`、`resetForeverBox`、`updateForeverBox`、`prepareBoxForRecreate`、`resumeBoxAfterRecreate` |
| 附件 | `uploadAttachment`、`readAttachmentImage`、`readAttachmentText`、`readAttachmentChunk` |

这是“少数通用传输 + 方法分发”的设计，不是每个业务对象一个独立 HTTP 服务。优点是 Renderer/Coordinator 的协议统一，缺点是方法面很大，必须有严格 schema、权限和版本治理。

### 4.3 事件流

Host 打开 SSE：

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache, no-transform
Connection: keep-alive
```

事件格式是 `data: <json>\n\n`，并每 15s 发送 `:ping`。Host 支持 gzip，但保持 flush，避免流式内容积压。Coordinator 自己解析块边界，不能依赖浏览器 EventSource 自动重连。

Coordinator 使用：

```text
连接超时       15s
初始重连       1s
重连上限       10s，指数退避
无数据 stall   35s
传输心跳       15s
重连代次       防止旧连接覆盖新连接
```

Renderer 最终收到的是归一化事件，而不是直接连接 Host。因此 Box URL、token、network token 和 VNC 代理信息不会暴露给 Renderer。

### 4.4 `sendPrompt` 的完整接收链

```text
Renderer
  │ RPC sendPrompt({ agentId, prompt, clientNonce, traceparent, ... })
  ▼
Coordinator dispatchRequest
  │ 记录 send stage；可走推理路由
  ▼
POST /api/sendPrompt
  │ Authorization + traceparent
  ▼
HostGatewayApi.sendPrompt
  │ 解析 agentId，补默认 Agent
  │ telemetry.reportMessageSent
  │ manager.sendPrompt(prompt, options)
  ▼
Transcript/session manager
  │ 接收消息、写入 session、唤醒 turn
  ▼
{ accepted: true }
```

转发字段包含：

- `agentId`；
- `attachmentPaths`、`attachmentNames`；
- `richText`；
- `replyToId`；
- `clientNonce`；
- `isFork`；
- `traceparent`；
- 客户端进入时间和组稿时间。

`accepted` 是接收确认，不是推理完成、工具执行完成或用户已看到结果。把三者混为一个响应会在超时和重试时产生重复执行或“假完成”。

### 4.5 重试与幂等条件

Coordinator 对 `sendPrompt` 只做一次追加尝试，条件非常克制：

```text
POST 从未发出                    → 可以重试
POST 已发出 + endpoint 已证明去重  → 可以重试
POST 已发出 + 去重能力未知         → 不重试
endpoint 在重试中发生改变          → 放弃
被取消、已关闭或收到业务 4xx         → 不重试
```

去重证明来自 Host 响应头 `x-sand-mint-dedupe: 1`，并与具体 base URL 绑定。`createAgent` 也预置 `clientNonce`，最多 3 次，退避 1s、2s、4s；若请求已发出但目标 URL 未被证明可去重，也不盲目重放。

这类策略比“网络错误就重试三次”更适合有副作用的消息和 Agent 创建。WorkPivot 可以复用原则，但不能把响应头名称或具体实现当作公共标准。

## 5. Box 获取与生命周期

### 5.1 官方远端模式

```text
Electron Main
  → ConnectRPC GrokBotService.ensureSandBox({})
  → Broker
  → {
      gatewayUrl,
      gatewayToken,
      networkToken,
      vncUrl,
      forkVncBaseUrl
    }
  → buildConnection(...)
  → Coordinator
```

Broker 的返回除了 gateway 地址和 token，还给出 VNC 主窗口与 fork 桌面代理。连接器对以下错误有明确处理：

- 认证失败映射为访问被拒；
- Box 被阻塞时带 title/detail/reason 和 `retry-after`；
- 后端要求升级时设置更新提示；
- Pod 代理需要 network token；
- gateway URL 为空时立即报配置/版本错误，而不是继续空连接。

### 5.2 本地 Docker 模式

社区派生用 Docker 启动本地 Box：

- 镜像按 digest 固定；
- Host 和 exec daemon runtime 按内容哈希保存；
- `SAND_GATEWAY_BIND_HOST=0.0.0.0` 只用于容器内；
- 宿主机发布 `127.0.0.1:1337`、`1339`、`1340` 等端口；
- Coordinator 访问 `127.0.0.1:1340`；
- gateway token 通过容器环境注入；
- Browser、桌面和 Host 使用同一持久卷；
- 选择 local-docker 失败时回滚设置并重启 Coordinator。

本地模式解决“没有官方账号和远端 Box”时的研究/使用问题，但不能据此认为官方支持自带本地执行面。

### 5.3 重建、迁移和数据保留

Box 命令面支持：

- `prepareBoxForRecreate`：停止或准备旧机；
- `setBoxMigrating`：标记迁移状态；
- `resetForeverBox` / `recreateSandBox`：是否保留数据可选；
- `resumeBoxAfterRecreate`：恢复会话和连接；
- `updateForeverBox`：更新执行环境；
- `snapshotBoxStoreNow` / `clearBoxStoreNow`：快照或清理持久状态；
- `handBackForeverBox`：人工接管后归还。

重建是一个有操作 ID 的迁移流程，不是直接把 URL 换成新容器。Agent 身份、transcript 和持久文件与 Host 进程生命周期分离，这是它能长期常驻的关键。

## 6. Turn 执行

### 6.1 每轮重新组装

Host 每次运行 Turn 都重新构建 executor 和工具，不缓存上一轮状态：

```text
用户消息 / routine wake / agent message
  → account and model选择
  → base system/tool prompt
  → Agent profile + memory
  → MCP discovery
  → Box/browser/desktop capability
  → dynamic tool set
  → model stream
  → tool calls / approvals
  → transcript events
  → visible SendMessage
  → checkpoint and idle
```

`turn-agent-composition.ts` 的注释强调 per-turn executor order 和“不跨 turn 缓存 executor/state”。这对长期 Agent 很重要，因为工具集、MCP schema、模型、Box 可用性和用户策略都可能改变。

### 6.2 工具面

观察到的主要能力：

| 类别 | 工具 |
| --- | --- |
| 用户交流 | `SendMessage`、`ReactToMessage` |
| Agent 管理 | `SendToAgent`、`CreateAgent`、`UpdateAgent` |
| 子代理 | `Task`、`CheckSubagent`、`MessageSubagent`、`StopSubagent` |
| Box 文件/终端 | `Read`、`Shell`、后台 shell、`Await`、`CopyToBox`、`CopyFromBox` |
| 用户电脑 | `ExternalRead`、`ExternalShell`、外部后台 shell |
| 浏览器 | navigate、snapshot、click、type、fill、select、key、scroll、drag、screenshot、tabs、受限 CDP |
| 桌面 | `Computer`、`Screenshot`、`request_box_help` |
| MCP | 发现、调用、授权、安装/卸载、账号和指令管理 |
| 持久状态 | `update_state`：profile、memory、routine、workflow |

工具描述本身承载行为约束，例如优先使用 DOM snapshot 而非坐标、先查 connector 而不是直接开浏览器、MCP mutation 重试前先读回。但这些长描述不是可复制资产；WorkPivot 应把其中稳定规则转成明确的执行协议。

### 6.3 浏览器子代理

`browserUse` 任务特点：

- 在 Box 的浏览器中运行；
- 先获取结构化 page snapshot；
- 用 snapshot 中的 `ref` 定位元素；
- 支持 navigate、click、type、fill、select、drag、key、scroll、screenshot；
- 优先 DOM 层，失败后才考虑 GUI；
- 后台执行，完成后自动唤醒父 Agent；
- 不能向用户追问；
- 遇到密码、2FA、captcha、payment 时停下并回交父 Agent。

受限 CDP 明确禁止 `Input.*`、browser-wide、storage、cookie、cache、permission 和 target-management 命令，避免模型绕过专用浏览器工具。

### 6.4 桌面子代理

`computerUse` 任务特点：

- 截图并用像素坐标、键鼠和拖动操作；
- 适用于 GUI 应用、文件对话框、拖拽和 DOM 自动化失效的站点；
- 与 browserUse 一样是后台 Task，不要求父 Agent 等待；
- 因共享同一桌面，同一时刻只允许一个 computerUse；
- 父 Agent 可读取 live transcript、注入纠偏消息或停止；
- 完成时由宿主通知父 Agent，父 Agent 不轮询完成。

子代理结束时释放桌面窗口；如果 steer 在运行中到达，子代理在下一步中断读取消息，但保留上下文。这是“任务作用域隔离 + 可纠偏”的典型实现。

### 6.5 可见交付

`SendMessage` 是 Agent 对用户唯一可见的出口。普通 assistant text 只是内部 scratchpad，原因不是 UI 偏好，而是：

- 工具执行状态需要单独动画和持久化；
- 消息类型需要支持文本、附件、Widget、secret、cloud-agent card；
- 宿主需要知道“用户是否已经收到进展/结果”；
- 崩溃恢复必须识别是否有交付债务；
- 审计需要区分模型内部推理和实际产品输出。

相关 middleware：

| 机制 | 触发 | 动作 |
| --- | --- | --- |
| StartOfTurnAck | 本轮先调用工具、尚无文本 SendMessage | 注入提醒，要求先发一行可见确认 |
| SendMessageReminder | 连续 6 次非 SendMessage 工具调用 | 提醒用户正看到沉默，要求发送当前进展 |
| EarlyResultReminder | 有确认但长时间继续执行 | 提醒尽快交付已经产生的真实结果 |
| AckObligations | 用户消息已 accepted 但未可见回复，遇到中断/重启 | 恢复后最多重投 3 次，要求确认/继续/请求重发 |

`ack != delivery` 是这里最重要的产品语义：一句“收到”不能作为“任务完成”的证明。

### 6.6 消息、Peer Agent 与 Group

- `SendMessage`：只给当前用户发可见消息，结束等待状态或交付结果；
- `SendToAgent`：给另一个命名 Agent 或 Group，异步、fire-and-forget、立即返回投递确认；
- `CreateAgent`：创建长期命名 Bot，返回其 id；
- `UpdateAgent`：合并更新名字/描述；
- Group：多个 Agent 和用户在共享房间交流，受提及和轮次约束；
- Broadcast：用户向多个 Bot 发送同一消息。

## 7. 权限、审批与人工接管

### 7.1 Local Tool Permission

用户电脑上的本地工具权限有三种：

```ts
type SandLocalToolPermission = "always" | "ask" | "never";
```

默认是 `ask`。实际动作至少包括 read、list、write、send-input 和 run-command。待审批状态包括 pending、allowed、denied、always、never、expired；用户可选允许一次、拒绝、始终允许或始终拒绝。

审批 key 不是工具名，而是至少组合：

```text
agentId + toolCallId + action + target
```

另外保存 Agent 的 direction epoch。新用户消息 `beginTurn` 后 epoch 增加，旧 pending 与 approval 过期；同样 action+target 的拒绝也会被记住，旧方向上的 Agent 不能通过改写提示立即绕过。审批 TTL 为 10 分钟，隐藏目标长度受限，取消会清理等待者。

`always` 也不是绝对全局：实现记录 standing grant 的 epoch，防止审批前已经存在、后来才恢复的旧任务借用新授权。

### 7.2 Auto-review

Auto-review 有三个模式：

```text
off     不检查
shadow  调用分类/策略并记录潜在阻断，但真实动作继续
enforce 阻断动作并创建用户审批
```

可按 surface 分别设置：

- Host shell；
- Box shell；
- MCP；
- computer use；
- cloud agent；
- subagent launch。

自动化写入默认保持 `off`，不会因为开启通用 enforce 就自动允许模型改写 Routine。审批 key 包含 `agentId + toolCallId + action + target`，并附策略原因、命令/URL/操作摘要、tool call id 和显示信息。

审批规则：

- 单 Agent 最多 4 个待审批；
- TTL 10 分钟；
- 一个 pending 存在时阻止新的副作用；
- 用户新消息、设置变化、取消、会话结束或宿主退出会使旧审批失效；
- 后台中断与用户拒绝必须区分，不能把“没人回复”写成“用户拒绝”；
- 拒绝后模型应报告阻塞，不应拆分/编码命令绕过；
- 对同一动作的再次审批必须显式 escalate，而不是换一种执行工具。

### 7.3 人工桌面接管

`request_box_help` 用于登录、SSO、passkey、2FA、captcha 和 payment 等只有用户能完成的步骤：

```text
Agent 发现需要人工
  → request_box_help({ instruction, domain, idp_domain })
  → Host 激活 Box 桌面并交还控制
  → Agent turn 结束
  → 用户操作并在界面点击“交还”
  → Host 恢复 Agent turn
  → Agent 先 Screenshot 读取变化，再继续
```

如果用户没有显式“交还”而是关闭查看器，恢复提示会区分不确定状态：Agent 先截图判断；无法确定时询问用户是否完成，而不是假设登录成功。

### 7.4 凭证输入

`SendMessage` 支持 `secret-request`：

- 聊天中只显示 label/description；
- 用户使用 masked secure input；
- 值直接写入目标连接器凭证文件；
- Agent 不接收明文 secret；
- secret request 结束当前 turn，提交后恢复。

目标创建、登录和支付不使用 secret-request；这类操作必须通过桌面 handoff 由用户亲自完成。

### 7.5 动作审计

审计对象包括：

```text
mcpToolCall
shellCommand
browserNavigation
computerUseSession
```

记录字段至少包括 Agent、turn、Box、时间、动作目标和结果元数据。本地文件为每个 Agent 的 `audit.jsonl`；可远端转发的事件进入 outbox。

本地 flush 参数：

```text
flush 周期        5s
单批最大           50 条
outbox 上限       2,000 条
失败退避          30s；rate limit 时取 Retry-After 与 30s 较大值
```

outbox 使用临时文件 + rename 原子替换；远端发送成功后再移除投递事件。stdio MCP 事件可转发，HTTP/SSE MCP 事件默认不转发，避免把服务商侧已经可审计的调用再复制一份。

## 8. Routine、Workflow 与 Memory

### 8.1 Routine 数据模型

```ts
interface AutomationConfig {
  name: string
  prompt: string
  trigger: AutomationTrigger
  isEnabled: boolean
  createdAt: number
  lastRunAt: number | null
  raisedNotices: string[]
}
```

运行时记录增加 `id`、`schedule`、`nextRunAt`、`runs` 和 `filePath`。每个 Routine 存在一个目录的 `automation.json` 中，运行结果保留最多 20 条；每个 Agent 最多 50 个 Routine，UI 上限 100，一次事件唤醒最多合并 25 个事件。

Routine 触发类型：

- cron；
- Slack channel/DM，mention/keyword/message/reaction；
- GitHub PR、review、comment、issue、CI；
- Microsoft Teams tenant/team/channel/message filter；
- Linear issue/status/cycle；
- Sentry issue event；
- PagerDuty incident event；
- 上述 listener 的 group。

### 8.2 调度业务规则

系统提示和 trigger 实现体现以下业务设计：

1. 如果服务提供事件，优先 listener，不用 cron 频繁轮询。
2. 对 “每天、定期、每半小时” 等模糊表达，默认工作日的合理时段，不自动解释成 7×24。
3. 如果必须兜底 deadline，创建定时任务并在 prompt 中写入截止时间。
4. 有限期监视在完成条件后删除；持续订阅只有在用户明确需要时保留。
5. 创建/修改会在用户离开后执行，因此可要求一次确认卡。
6. 同一个 Routine 连续遇到鉴权失败时暂停，避免反复失败和重复提醒。
7. Routine 明确要求“无变化不通知”时，允许一次运行不调用 SendMessage；用户等待的普通任务不允许静默结束。
8. 外部事件转换成带源标签的上下文块，事件内容是数据，不是高优先级指令。

### 8.3 Workflow / Skill

Workflow 文件统一为 `SKILL.md`：

```ts
const WORKFLOW_MAX_BODY_LENGTH = 100_000
const WORKFLOW_INJECTED_BODY_LIMIT = 8_000
const WORKFLOW_MAX_PER_AGENT = 100
const WORKFLOW_UI_LIMIT = 100
```

来源包括：

- managed；
- plugin；
- user workflow；
- automation；
- source reference。

正文、名称、描述、trigger、helper scripts 和 sourceRef 分离。全局库让多个 Agent 共用技能，但每个 Agent 单独启用；plugin/managed 来源和用户来源在 UI 排序上分开。

### 8.4 Memory 与 Profile

`update_state` 处理：

- profile：Agent 自己的名字、描述/人格；
- memory：保存、修改、遗忘；
- routine：创建、更新、暂停、恢复、删除、立即运行；
- workflow：创建、修改、删除、导入和运行。

技能/例程是方法，记忆是事实或偏好，profile 是角色身份，三者不共用一段随意拼接的 Prompt。这个边界适合 WorkPivot 把“记忆”与“工作流知识”分开授权和治理。

## 9. 失败、恢复与运行状态

### 9.1 连接失败

产品把 gateway 错误分层：

- 业务 4xx：不重试，向用户解释；
- 5xx/网络/超时：标记 unreachable；
- Box 被配额或后端阻塞：显示可读 title/detail/reason，并保持 retry-after；
- 鉴权失败：提示重新登录/更换账号，不创建新 Box 循环；
- 升级要求：提示客户端版本过旧；
- SSE stall：终止旧 reader，进入有界重连；
- endpoint 在 send retry 中改变：放弃重放。

### 9.2 Host 与执行守护分离

Host 有独立进程、lock 和 discovery 文件；本地执行守护有自己的 discovery、PID、启动时间和 generation token。Coordinator 发现 daemon 时不仅看 PID，还验证：

- 可执行路径；
- 启动时间；
- generation token；
- command line 是否携带同一 generation；
- discovery 与 live process 是否一致。

这样可避免“PID 被别的进程复用”导致错误终止或错误认领。Host 退出也有 5s shutdown watchdog，gateway、Host、exec daemon 分层关闭。

### 9.3 用户消息中断

用户消息接收后若 Turn 被打断，恢复不是简单重新执行 prompt。AckObligations 会：

1. 检查是否已有用户可见 SendMessage；
2. 若没有，读取持久 obligation；
3. 在空闲或启动后重投一次恢复任务；
4. 恢复任务绑定新的 ack token，只有当前 token 发出的可见消息才能兑现债务；
5. 最多 3 次；成功、Agent 删除或达到上限后清除并记录原因；
6. 恢复 Prompt 明确允许“看不到最新消息就请用户重发”，禁止编造完成。

这比普通重试更接近业务流程恢复：不重放整个工具链，只恢复“必须给用户一个真实答复”的义务。

### 9.4 后台子代理

后台子代理有注册表和生命周期：

- 捕获启动错误并转为失败结果；
- 运行时保存近期工具活动、轮次终止数量和 live transcript；
- 完成时通知父 Agent 并可 resume 父 turn；
- 停止时释放桌面窗口并清理 session/meta；
- 运行中 steer 保留上下文，只把消息插入下一步；
- computerUse 完成或中止都释放窗口；
- 父 Agent 不轮询完成，只按需检查。

## 10. 从架构到实现的建议顺序

以下不是复制 Grok Bot，而是把技术原则映射为 WorkPivot 可独立实现的最小顺序：

### 阶段 1：交付与确认协议

1. 给用户消息增加 `accepted_at`、`visible_ack_at`、`delivered_at`、`failed_at`。
2. 把 Agent 可见输出限制为结构化 `send_message` 事件；内部 reasoning 和 tool text 不进入用户消息表。
3. 为中断的用户消息建立 `delivery_obligation`，重启后由后台恢复器补发，而不是无成本重放所有工具。
4. 增加文本 ack middleware，但最终以数据库 obligation 为准。
5. 新增 clarify、plan approval、action permission、manual handoff、artifact review 五种独立交互类型。

### 阶段 2：动作级授权

1. 审批键改为 `work_item + run + agent + tool_call + action + target + policy_version`。
2. 对 shell、MCP、browser navigation、computer use 和文件外发记录 action metadata。
3. 实现 allow-once/deny/always/never 和 10 分钟过期；用户新指令使旧审批失效。
4. 先以 `shadow` 记录策略命中；人工复核后按执行面开启 `enforce`。
5. 审计先写本地 append-only 文件/对象，再以有界 outbox 写中心审计；把失败与用户拒绝分开记录。

### 阶段 3：任务型子代理

1. 子代理至少有 `parent_run`、`task_scope`、`deadline`、`budget`、`status` 和 `completion_callback`。
2. 只开放任务需要的工具；browser 子代理与 desktop 子代理分别授权。
3. 父任务不轮询完成，由宿主投递 completion event。
4. 增加观察、steer、stop；steer 只发消息，不重建上下文。
5. desktop 资源建立单屏租约，避免多个 GUI 子代理互相抢鼠标。

### 阶段 4：持久执行面

1. 把 Agent 业务身份、Run/Turn 状态、Host 进程和沙箱容器分开建模。
2. 为执行环境建立 prepare/recreate/migrate/resume/health/lease 状态，而不是只在失败时 `docker restart`。
3. 把凭据、网络 token、VNC URL 和 endpoint 留在服务端控制面，客户端只拿短期会话能力。
4. 页面自动化优先 DOM snapshot；GUI 自动化作为受控兜底。

### 阶段 5：事件化自动化

1. 用持久 WorkItem/Job 承载 Routine，不在模型进程里 sleep。
2. trigger、run、event、delivery、approval、outbox 分开持久化。
3. 实现事件源幂等键、时区、安静时段、业务事件优先、自过期和运行历史。
4. 连续鉴权失败自动暂停；恢复由用户重新授权触发。
5. 通知按“有意义变化/完成/失败/需人工”发送，不把过程性心跳当业务消息。

### 完成判据

- 客户端断开后消息仍可恢复，且不会因重试产生重复副作用；
- 用户能看到每个 accepted 消息最终处于 acknowledged、delivered 或明确失败状态；
- 拒绝动作后模型不会无提示原样重试；
- 子代理中断不会遗留桌面租约和孤儿任务；
- 执行环境重建不会改变 WorkItem 身份或丢失成果版本；
- Routine 在同一个事件重复投递时只产生一次业务执行；
- 审计可以回答“谁在哪个任务、哪次运行、对哪个目标做了什么、由哪条策略允许或阻止”。
