## 3. 重算失败与公式兼容性异常

随后执行 recalc.py，两次 LibreOffice 重算分别触及 60 秒和 180 秒预算。返回 JSON 明确包含 error、engine=static、total_formulas=3；Python formulas 降级依赖未安装。调用记录外层 Exit Code 却是 0。

同哈希 recalc.py 的 CLI 在 error 存在时执行 sys.exit(1)，而本次命令尾接 `tail`，未观察到 pipefail 设置。因此外层退出成功不能证明重算成功；应以结构化 error/status 为准。后续尝试中，失败的 edsdk 调用经 head 管道也继续执行了后面的 save，进一步说明不能把带管道的 `&&` 当成可靠业务成功门禁。

两次失败重算后的磁盘诊断显示：

```xml
<f aca="0">=B2*C2</f>
<f aca="0">=B3*C3</f>
<f>=SUM(D2,D3)</f>
```

openpyxl 公式视图因而返回 `==B2*C2`、`==B3*C3`、`==SUM(D2,D3)`，但缓存视图已为 70、20、90。缓存正确不代表公式序列化正确。

SpreadsheetML 用 f 保存公式文本、v 保存缓存值；Microsoft 示例为 `<f>SUM(A1:A5)</f>`，不带输入界面使用的前导等号，公式语法的 prefix-operator 也不含等号。参考：[Microsoft 公式说明](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/working-with-formulas)、[MS-XLSX 公式语法](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-xlsx/3d025add-118d-4413-9856-ab65712ec1b0)。

Agent 尝试将 API 入参改为不带等号的 SUM(D2,D3)，服务直接返回 `SheetEditor::SetCellValueInFormula: not a valid formula string`。因此 API 输入格式与 OOXML 保存格式不能混为一谈；简单在 API 层去掉等号不是本例的解决办法。

上述异常发生在 SDK 编辑保存及两次失败重算之后。没有保留第一次 save 与第一次 recalc 之间的磁盘快照，也未在干净副本上单独隔离 SDK 和 LibreOffice。因此异常和接口约束已观察到，但不能声称已定位原生导出函数，或完全证明超时的唯一原因就是等号。

## 4. Agent 实际修复与最终验证

WorkBuddy 最后没有继续仅靠编辑工具重试，而是自行编写 Python ZIP/XML 修补逻辑：移除每个 f 标签文本开头的一个等号，保留原缓存与其他条目，通过临时 ZIP 和 os.replace 替换副本。实际修改 3 处。

修补后 openpyxl 公式视图恢复单等号表示，OOXML f 文本为 B2*C2、B3*C3、SUM(D2,D3)。随后第三次 recalc（预算 240 秒）实际返回 status=success、engine=libreoffice、total_errors=0、total_formulas=3，最终独立磁盘核对得到 70、20、90。

这验证“模型诊断→直接格式修补→外部重算→读回”的纠错能力，不等于原生保存接口已经可靠。该正则修补只验证当前简单文件，不能当作复杂共享公式、数组公式、外链或签名文件的通用修复器。既有编辑器内存状态与外部修补后的磁盘是否实时一致，也未做完整的再次保存实验。

## 5. 结论与实现启示

脱敏命令、实际输出、前后文件身份和 ZIP 成员变化见 [编辑证据](表格修改证据-20261017.json)。未执行测试会话中的代码，也未修改 WorkBuddy 安装产物；文件修改由用户操作的 WorkBuddy 完成。

现在可说明本例的数值/公式编辑、保存、重算降级、错误传播及纠错流程。仍未知：原生公式解析和导出算法、复杂表格保真、并发、回滚及撤销。版本递增和最终结果正确不足以覆盖这些能力。

对 WorkPivot 的建议是明确区分 API 公式字符串和文件格式公式文本；结构化业务状态优先于 shell 退出码；分别核对公式、缓存、业务期望和原文件保护。不要让通用 Agent 的临时 ZIP 正则修补成为常规保存链。以上为研究建议，未据此开发业务代码或增加已确认需求。
