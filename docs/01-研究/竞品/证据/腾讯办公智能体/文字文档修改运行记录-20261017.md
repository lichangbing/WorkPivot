## 2. 实际编辑流程

记录包含 13 次工具调用：目录检查→get_pool_status→open_file→文档结构查询及替换 schema→正文替换及表格 schema→表格写入→save_file→重新查询结构及磁盘核对→项目记忆更新→present_files。

没有观察到重新生成 HTML、调用 convert_doc.py 或新建整份 DOCX。实际编辑工具为：

1. `doc_find_and_replace(old_text=REA-WORD-001,new_text=REA-WORD-002)`，返回 find_and_replace ok、version=1、last_edit_index=53。
2. `doc_set_table_cells(table_id=...,cells=[{row:2,col:2,text:7}])`，返回 set_table_cells ok、version=2、last_edit_index=70；实际参数中的 text 为字符串 "7"。
3. `save_file`，返回 File saved to 目标路径，随后从磁盘 XML 再核对内容。

这里验证的是两个依次执行的编辑和一次保存，没有事务失败、取消、并发或撤销实验。version 递增不能单独证明冲突控制、事务或持久化版本历史。

## 3. file_id 规则的实测修正

本例 open_file 返回 `open started (doc), chunks streaming via /stream for file_id=E:/project/WorkPivot/tmp/rea-office-test/rea-word-edit.docx`。后续查询、两次写入和保存都使用这个路径形式的 file_id，并实际成功。

因此此前“file_id 必须是 UUID、路径一定不可用”的绝对描述不成立。技能要求优先复用用户可见编辑器实例，是保持会话一致性的操作纪律；不能把它等同于底层接口永远只接受 UUID。本例使用后台 open_file，编辑后再 present_files，没有证明期间与用户预览实时同步，也未还原路径 ID 与 UUID 的内部映射规则。

## 4. 保存重序列化与格式边界

与未修改副本的源文件相比，7 个 ZIP 成员的内容哈希改变：正文、样式、字体表、核心属性、两份关系文件及 Content_Types。保存并不是对两个原始文本字节做补丁。

独立 XML 比较显示：

- 10 组 rPr 文字格式、1 组 tblPr 和 6 组 tcPr 表格/单元格属性规范化后相同。
- 正文的目标文本确实只改了上述两处；同时增加若干空 pPr。
- 标题样式 ID 有重编号，需结合 styles.xml 的定义解释，不能只按 ID 变化判样式丢失。
- latentStyles 条目有重排；字体表合并重复 DengXian 定义，并新增 characterSet 属性。
- 原来的空 sectPr 被补为显式 A4 页面尺寸与页边距。

这些变化支持“引擎在保存时重序列化/规范化文档”，但不能据此认定视觉完全相同或已经发生视觉损坏。本次未在 Word/WPS 渲染比对，复杂版式、分页、图片、修订与批注保真仍需专项样本。
