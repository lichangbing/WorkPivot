# WorkBuddy 文档读取、预览与生成实现

日期：2026-11-03。样本：WorkBuddy 5.9.3（Windows，Electron 37.10.3 / Chromium 138）。类型：安装包静态分析 + 既有受控运行记录交叉引用。本文把"读 / 预览 / 生成"三条链合并成一份实现说明，替换此前散落在 Office 场景表里的简写；运行细节仍以 2026-10-17 的三份运行记录与 2026-11-03 的预览运行记录为准。

## 1. 结论

1. WorkBuddy 不自己解析 OOXML，也不自己序列化 OOXML。三种能力都建立在**本地编辑器内核**（腾讯文档 `editor_sdk` / 本地 MCP）之上，Agent 只是调用方。
2. 读、写、预览是三条不同通道，入口技能不同、失败语义不同，不能合并成"抽出正文再整份重写"：
   - 读：向已打开实例查询结构化对象（段落/表格/单元格/公式）。
   - 预览：宿主展示（引擎 iframe 或 docxjs 兜底），不是内容通道。
   - 生成：本地中间表示（HTML / SlideDSL / openpyxl 脚本）→ 引擎或 Python 落盘 → 独立校验。
3. 生成链的共同形状是"**中间表示 + 一次性落盘 + 事后校验**"，并且把校验结果（退出码 + JSON）与 AIGC 标识写进交付物，而不是靠 Agent 自称成功。
4. 三条链都显式记录过失败教训（自拉服务、公式无缓存值、XML 修补），这些教训写进了技能文档，属于可参考的工程化经验。

## 2. 分层与入口

以下路径均相对于安装包的插件根 `resources\app.asar.unpacked\resources\plugins\workbuddy-builtin\`（`skills\` 与 `builtin-plugins\` 两个子目录）。
| 层 | 组件 | 作用 |
| --- | --- | --- |
| 路由门 | `skills/workbuddy-office-routing/SKILL.md` | 按文件类型 × 任务性质决定读/改/新建走哪个技能，避免一个万能工具 |
| 读改 | `skills/workbuddy-local-office-edit/`（`edsdk.py`） | 通过本地 MCP 调 `doc_*` / `sheet_*` / `slide_*` 工具 |
| 生成 | `builtin-plugins/workbuddy-docx`、`workbuddy-pptx`、`workbuddy-sheetagent` | 三个格式各自的生成编排 |
| 转换 | `html-to-doc/scripts/convert_doc.py`、`@tencent/slidep`、`openpyxl + recalc.py` | 中间表示落盘 |
| 内核 | `editor_sdk.exe`（`@tencent/tencent-docs-ai-engine`） | 排版、分页、公式、文件读写 |
| 展示 | `media-preview` / `DocxPreview` | 预览与兜底 |

路由门的硬规则（对实现理解最关键的一条）：本地 PPT 一律走 `workbuddy-pptx`；docx 从零创建或整体美化走 `workbuddy-docx`；新建工作簿走 `workbuddy-sheet-generation`，既有工作簿的小改走 `local-office-edit`、其余走 `sheet-agent`；PDF 阅读走 `workbuddy-pdf`。**纯预览不算内容工作**，不进这套路由。

## 3. 读取

### 3.1 Word

调用约定（`doc.md`，129 行）：

- `python3 edsdk.py list doc` 列工具、`schema <tool>` 取实时参数、`call <tool> file_id=<id> …` 执行。
- 调用任何 `doc_*` 之前必须先 `schema`，参数以服务端 `tools/list` 返回为准，不硬编码。

读取入口是结构查询，不是文本抽取：

- `doc_resolve_document_structure`（`mode=full`、`text_preview_length=100`、`include_table_cells=true`）返回顶层节点、`paragraph_id/paragraph_index/start_index/end_index`、表格 `cells` 的行列、`pagination.has_more` 与 `version`。
- `doc_get_outline`、`doc_get_last_operable_pos`、`doc_get_images`、`doc_list_tables`、`doc_get_table_info`、`doc_get_section_property`、`doc_get_comments` 补充大纲、末尾可操作位置、图片、表格、节与批注。
- 位置模型是**全文 UTF-16 code unit 偏移**，区间左闭右开；`paragraph_index` 不能当索引用；编辑后旧索引立即失效，多处替换用 `doc_find_and_replace`，按旧索引批量改要从后往前。

已验证的返回规模（2026-10-17 受控样本）：5 个顶层节点、`version=0`、`has_more=false`，表格单元带 row/col。长文会截断，需要翻页游标。

### 3.2 Excel

两条通道：

- 简单表：`sheet_get_cell_data`、`sheet_get_used_range`、`sheet_get_merged_cells`、`sheet_get_charts`、`sheet_get_pivot_table_detail`、`sheet_get_conditional_format`、`sheet_get_cell_style`、`sheet_get_dimension_size`、`sheet_get_object_list`。
- 公式与核算：`sheet_calculate_formulas`、`sheet_calculate_single_formula`、`sheet_audit_formula_consistency`（把公式归一化成 R1C1 后按结构分组，找同构不一致）。

读表返回 `orientation=MATRIX`、`structured=true`，并按请求带回 `values` 与 `formulas`（例如 `=B2*C2`）。已知缺陷：`resolve_local_excel` 里 Windows 盘符路径会被 `startsWith("/")` 判成非法，返回 `INVALID_LOCAL_PATH`；自动表头识别在部分样本上会漏列。

### 3.3 PPT

读取走本地引擎，不走 python-pptx：`slidep inspect` 请求 `/localapi/open` + `/localapi/keyframe`，把 keyframe 解码成结构化模型，再经归一化转 Markdown；`EUe` 会校验扩展名 `.ppt/.pptx` 与源 SHA-256，`NLe` 转换后再比一次 hash，发现变化就拒绝输出成功。所以"读出来的内容"与"读的文件版本"是绑定的。

### 3.4 PDF

`workbuddy-pdf` 技能自带抽取与页级视觉检查，技能文档明确禁止 Agent 自行用别的库抽取。PDF 生成/编辑在本版不支持。

## 4. 预览

预览与读取是两条独立通道，默认路径也不是"DOCX → HTML"：

1. 宿主在主窗口右侧画布里放一个 iframe，加载 `http://127.0.0.1:39099/static/doc/pc.html`，参数含 `localFilePath`、`title`、`globalPadId`（= 文件绝对路径的 md5）、`local_edit=1`、`client=sdk_local`、`mode=edit`、`toolbar/outline/statusbar=show`、`editorSdkUrl`。
2. 页面里是腾讯文档引擎的完整编辑器（分页、大纲、状态栏、字数），文档身份由 `globalPadId` 绑定；同一文件跨窗口共用一个 pad，避免多实例互相覆盖。
3. iframe 与宿主用 postMessage 通信：`workbuddy:themeChanged`、`workbuddy:localeChanged`、`EXTENSION_READY`、`SHORTCUT` 等；宿主只接受本 iframe 且 origin 匹配的消息。
4. 兜底：只有 `getPreviewUrl` 不可用或引擎报告 `file_not_found / file_not_accessible / engineUnavailable / previewTooLarge` 时，docx 才降到 `docx-preview`（docxjs）本地渲染；`docx-preview-component` 里 `renderAsync(file, body, undefined, H)`，`H={className:'docx-preview',inWrapper:true,breakPages:true}`，并用 `ResizeObserver` 按 816px 基准做 zoom。
5. PDF 走浏览器内置阅读器（`<iframe>`，不带 `sandbox`，否则 Chrome 直接拦成 "This page has been blocked by Chrome"）；HTML 预览仍保留 `sandbox=""`。

证据细节见 [Word 预览运行实测](文字预览运行-20261103.md)。

## 5. 生成

### 5.1 Word：HTML → convert_doc.py → 引擎

- 编排：`workbuddy-docx/SKILL.md` 强制先读 `skills/tdoc-orchestrator/SKILL.md`，禁止绕过编排直接调编辑工具（例外只允许 `open_file/close_file/save_file/get_pool_status`），并明确禁止 `Bash python-docx`。
- 中间表示：先产出完整 HTML（设计资产来自 `skills/design-token/` 五套主题 + 三份国标规则 `gb-t-9704` / `gb-t-7713` / `gb-t-7714`；版式组件在 `skills/doc-typeset/`）。
- 落盘：`python3 convert_doc.py --html x.html --output y.docx [--no-preflight --no-verify] [--require-page-furniture] [--require-toc]`，内部顺序 `create_doc → open_file → doc_insert_html_content(idx=0) → save_file`，直接写交付路径，不产生中间副本。
- 结果契约：退出码 0 且 stdout 末行 JSON `success=true`；退出码 1 输出 `error` 并标注失败阶段（preflight / convert / verify）与 issues。
- 已记录的坑：文档明确禁止 `subprocess.Popen` 自拉文档服务——曾因此拉起 21 次、每次等 60 秒、空耗 18 分钟，而真实插入只要 22 秒。

### 5.2 Excel：openpyxl 脚本 → 重算 → 标识

- 编排：`workbuddy-sheet-generation` 规定**主代理自己写 openpyxl 脚本生成整本**，不委派子代理；这与"修改既有工作簿走 sheet-agent"形成分流。
- 参考料：`scripts/extract.py` 用 mammoth（docx）、pymupdf（pdf）、python-pptx（pptx）、openpyxl（xlsx）、csv 把输入转 Markdown，并抽原图与缩略图供视觉兜底。
- 重算：`scripts/recalc.py` 记录的核心事实是 openpyxl 写入的公式只有字符串、没有缓存值，`data_only=True` / pandas / 预览器读到的都是 `None`；因此做三层兜底：LibreOffice 隔离 profile 重算 → 纯 Python formulas 引擎回填 `<v>` → 静态结构分析。
- 标识：`scripts/aigc_label.py` 往 `docProps/custom.xml` 写 `AIGC` 自定义属性（按 GB 45438-2025 与《人工智能生成合成内容标识办法》，字段 `Label/ContentProducer/ProduceID/ReservedCode1/ContentPropagator/PropagateID/ReservedCode2`）。

### 5.3 PPT：SlideDSL → revision → 引擎

- 目录约定：`<workspace>/<project>/{assets/, slides/NN.slide, <name>.pptx}`；风格路由 `references/scenarios/{general,academic,investment-analysis,redgold,personal-introduction}.md` + `references/design-principle.md`；生成与改稿分文档（改稿走 `edit-existing.md`）。
- CLI：`slidep create` 建空稿并返回 `file_id`；`slidep lint --dsl-file --page-index` 只做本地布局检查；`slidep upsert-dsl` 写页面。
- 落盘链（静态审阅确认）：`xHe`/`rLe` → POST `/localapi/keyframe` 解码 → `evaluateJsxInput` 得 JSX tree → `createSlideManagerJsx` → `insert(tree,{jsxCode:dsl})` → `layout(0,{validateOverflow:validateDsl??false})` → `fromValidMutationData` → codec 8237 编码成 revision → POST `/localapi/commitrevision`（`revision_id = SHA1(path|newPageId|index|baseVersion|SHA1(revision))`、`from_third_party:true`）→ POST `/localapi/save`。
- 视觉检查：`slidep screenshot` 子进程出图，再交给视觉模型；子进程环境会清掉 `WORKBUDDY_VLM_*`。

## 6. 校验、失败处理与可借鉴做法

| 关注点 | WorkBuddy 的做法 | 评价 |
| --- | --- | --- |
| 成功判定 | 转换器退出码 + JSON（含阶段与 issues），不靠 Agent 解读日志 | 可借鉴：把成功定义成机器可判 |
| 校验独立性 | Word 侧另有独立 XML 核对；PPT 侧 lint 与 screenshot 分离 | 可借鉴：生成器自检与独立核对分开 |
| 公式正确性 | LibreOffice 重算 + `<v>` 回填 + 结构分析三层 | 可借鉴：不信任写入库的缓存值 |
| 内容标识 | 产物内写 AIGC 自定义属性 | 可借鉴：合规信息随文件走 |
| 失败边界 | 引擎不可用降级 docxjs；文件不存在/过大不算失败 | 可借鉴：区分"能力缺失"与"执行失败" |
| 已知坏味道 | 曾用临时 XML 修补掩盖兼容问题；`--no-preflight --no-verify` 让校验变空 | 应避免 |

## 7. 对 WorkPivot 的启示

1. 读取用**结构化对象查询**（结构/表格/单元格/公式），不要做纯文本抽取再猜结构；定位模型要写进接口契约（UTF-16 偏移、左闭右开、编辑后索引失效）。
2. 把"预览"和"读取"建成两条通道：预览只对用户负责，读取只对 Agent 负责，互不将就。
3. 生成侧采用"中间表示 + 一次性落盘 + 独立校验 + 机器可判结果"，并给每次交付留可复核的校验记录。
4. 用路由表（文件类型 × 意图）替代万能解析器，避免同一文件在不同路径下产生不同结果。
5. 不要复制专有引擎；WorkPivot 的定位是"可解释的交付"，用 LibreOffice/PDF 与自研校验把这条链走通即可。

## 9. 边界

- 本文的"实现"以技能文档、安装包代码与运行日志为准，未反编译原生 `editor_sdk`，排版/分页/序列化算法仍属未知（D 级）。
- 生成链的视觉保真未逐页验收；运行样本是短文与单表，不能代表复杂版式。
- 版本升级可能改变路径与默认行为。
