> 证据日期：2026-11-01  
> 上游版本：提交 `6337fc823ce20251c8de8085948165c81aaa701e`（2026-10-31）  
> 许可证：MIT  
> 证据边界：官方源码、官方文档与本地构建验证；未连接真实 GitHub/飞书账号完成端到端业务验收。

## 1. 结论

该项目的技术重点是把 Agent 从“一次会话中的工具循环”提升为“长期运行的系统工作流”：

```text
Source → Trigger → Thread → Eval/Decision
                               │
                               ├─ accept → Mandate + Ticket
                               │               │
                               │               ▼
                               │         Assignment
                               │               │
                               │               ▼
                               │        Worker Session
                               │
                               └─ ignore / stop / unavailable
```

模型出现在两个位置：

1. 主 Session 对候选请求进行研判和路由；
2. Worker Session 执行具体技术工作。

模型不拥有核心状态。状态、授权、幂等、队列、恢复和外部消息回执由确定性代码管理。

## 3. 核心状态机

### 3.1 Trigger 和 Thread

Trigger 是一个来源声明的不可变事实：

```ts
interface Trigger {
  id: string
  source: string
  threads: ThreadRef[]
  actor: ActorRef
  human: boolean
  addressed?: 'mention' | 'direct'
  at: string
  text: string
  channel?: ChannelRef
  url?: string
  meta: Record<string, unknown>
}
```

设计约束：

- `id` 稳定，可做跨轮询去重；
- `text` 与 `meta` 被视为外部数据；
- Source 声明事件是否来自人、是否明确指向 Agent；
- 同一 Thread 同时只允许一个 Eval；
- Eval 运行期间新到 Trigger 合并到下一批；
- 同一 Trigger 即使再次被接受也只能产生一个 Ticket。

### 3.2 Decision 和 Mandate

Decision 记录“为什么接/不接”，Mandate 记录“如果接，凭什么、能做什么、依据哪版规则”。

```ts
interface Mandate {
  strength: 'explicit' | 'inferred'
  policyVersion: string
  basis: MandateBasis
  actor: ActorRef
  scope: string
}
```

Mandate 的关键性质：

- 创建后不可变；
- 扩大范围需要新 Ticket；
- 恢复已结束 Ticket 时重新检查当前 Policy；
- 策略变化不会直接撤销正在执行的 Mandate，但会把变化作为 Input 通知 Worker；
- `observe` 下的推断工作记录为 `would_accept`，不创建 Ticket。

### 3.3 Ticket、Assignment 和 Report

Ticket 是业务工作单元，Assignment 是 Ticket 与一次执行实例的绑定。

```text
Ticket:      open ───────────────────────────────→ ended
Assignment:  pending → running → ended
Report:      progress / waiting / ready / blocked / failed / dropped
```

Ticket 不从 Session 直接推导状态。一个人工后续消息可以在原 Mandate 下恢复已经结束、但未被人工停止的 Ticket。

## 4. 多 Agent 与子代理边界

### 4.1 主架构是多 Agent

`DshExecutor` 为每个 Ticket 创建：

```ts
export const workerSessionId = (ticketId: string) =>
  `worker-${ticketId}`
```

每个 Worker 拥有：

- 独立 Session ID；
- 独立工作目录；
- 独立上下文；
- 独立并发槽；
- 跨主 Session 回合的持久生命周期；
- 可重新启动、恢复和结束的 Assignment。

主 Session 不拥有 Worker 的内部目标。它通过 Engine 创建 Ticket/Assignment，由宿主调度 Worker。

### 4.2 Worker 内可以使用子代理

`cordis.patch.yml` 在 Worker preset 中加入：

```yaml
- id: tool-subagent
  name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: spawn
    toolName: subagent
    modelSelection: true
    modelDiscovery: true
    agentPreset: standard
```

主 Router preset 明确不启用 Subagent。

因此：

- Worker 是系统级多 Agent 角色；
- Subagent 是 Worker 回合内按需派生的临时助手；
- Subagent 适合局部并行工作，Worker 仍对 Ticket 结果负责；
- 不能把两者混成“主 Agent 的聊天子任务”。

## 5. 授权与评估实现

### 5.1 三种接受模式

```ts
export type AcceptMode = 'off' | 'observe' | 'auto'
```

| 模式 | 推断工作的行为 |
| --- | --- |
| `off` | 不成为候选 |
| `observe` | 进入评估；正结论只记录 `would_accept` |
| `auto` | 匹配规则并满足方向、意图证据后创建 Ticket |

显式授权工作在所有模式都可用，但仍需通过允许列表和来源范围。

### 5.2 接受评估的确定性检查

模型返回结构化评估，但宿主校验：

- 每个启用规则必须且只能判断一次；
- 至少一个规则匹配；
- `implementation_requested === true`；
- 目标不是 `undetermined`；
- 没有未决设计决策；
- 必须提供 `intent_evidence`；
- 若授权强度为推断，仅在 `auto` 模式真正接单。

这意味着 Prompt 不能绕过 Policy，模型结论也不能绕过结构化校验。

### 5.3 工单恢复

恢复不是简单重新打开 Session，而是检查：

- Source 是否仍监听原 Thread；
- 允许列表是否仍包含原身份；
- 准入表是否仍授予至少原有强度；
- 推断规则是否仍启用；
- 当前 accept mode 是否仍允许推断工单；
- Bot 是否仍在来源 Bot 列表中。

检查失败时 Ticket 保持结束，等待消息回到 Eval 或产生新的授权。

## 6. 执行与并发

### 6.1 Worker Slot

`WorkerSlots` 同时计算已经运行的 Worker 和正在启动的 Worker：

```ts
used(): number {
  return new Set([...this.running(), ...this.starting.keys()]).size
}
```

规则：

- 普通新任务受 `maxWorkers` 限制；
- 人工后续消息可使用额外一个槽位；
- 人工唤醒优先于新任务启动；
- 启动预留同步完成，避免并发请求同时抢到最后一个槽；
- Assignment 从准备目录开始占用槽位；
- 回合结束但仍有后台任务时继续占槽。

### 6.2 每工单目录

准备命令收到变量：

```text
DSH_SUPERAGENT_DIR
DSH_SUPERAGENT_NAME
DSH_SUPERAGENT_TICKET
DSH_SUPERAGENT_BLOCKED_COMMANDS
DSH_SUPERAGENT_GITHUB_REPOSITORY
DSH_SUPERAGENT_GITHUB_NUMBER
DSH_SUPERAGENT_GITHUB_PR_HEAD
DSH_SUPERAGENT_FEISHU_BOT
DSH_SUPERAGENT_FEISHU_CHAT
```

典型准备步骤：

```sh
git fetch <repo> <base-or-pr-head>:refs/dsh-superagent/$DSH_SUPERAGENT_TICKET
git worktree add -b agent/$DSH_SUPERAGENT_NAME \
  $DSH_SUPERAGENT_DIR \
  refs/dsh-superagent/$DSH_SUPERAGENT_TICKET
```

准备命令最多运行 10 分钟。失败会保留非空目录以便诊断，但不会自动重试，以免把残留目录误判为已准备。

### 6.3 后台任务

- 新任务 foreground shell 超过 5 秒转入后台；
- 主 Agent 的 job wait 上限为 5 秒；
- Worker 回合结束仍有后台任务时，最多再给 30 分钟；
- 到期后终止 shell job，Subagent 可继续；
- Ticket 结束时回收该 Assignment 的 Job 和 Subagent；
- 进程关闭最多等待每个 Worker 10 秒处理后台任务。

## 7. 持久化和可靠性

### 7.1 单一事务入口

`Engine` 是核心状态的单一写入口：

```text
Sources / Tools / HTTP
          │
          ▼
        Engine
          │ transaction
          ├─ Intake
          ├─ Evals
          ├─ Tickets
          ├─ Assignments
          └─ Replies
```

每类状态有唯一 Writer。外部事件只能通过 `SourceContext` 进入领域层。

### 7.2 Effects

Effects 是 SQLite 支持的持久副作用队列：

- 在领域事务内 enqueue；
- 事务提交后才执行；
- `(kind, key)` 唯一，可合并重复待执行任务；
- 支持每类并发上限；
- 支持顺序、指数退避和健康状态；
- 暂停时不消费；
- 停机时保留未执行任务；
- 更新 payload 会使旧运行结果无法覆盖新任务。

主要 kind：

```text
assessment  候选送主 Session
launch      启动 Assignment
delivery    向 Worker 投递输入
relay       向主 Session 转发报告
notice      注入不唤醒主 Session 的通知
reply       通过 Source 发送消息
```

### 7.3 Outbox 和幂等

- 同一个消息 ID 只记录一次；
- 发送前先持久化 receipt；
- 发送成功后标记 sent；
- 会话消失时标记 dropped 及原因；
- 与同一 Ticket、同一会话的早期消息保持顺序；
- 失败重试不会再次创建同一业务消息。

### 7.4 恢复

进程重启后：

- 未完成 Assignment 根据 Report 和输入恢复；
- 已投递但未读的 Input 重新对账；
- 待执行 Effects 继续处理；
- 待发 Outbox 继续发送；
- 已结束 Ticket 可被人工后续消息恢复；
- 恢复提示要求 Worker 先检查目录、git 历史和外部 PR 状态，避免重复副作用。

## 8. 监督面板与提示词治理

面板按工作流组织：

```text
Overview → Source → Trigger → Eval → Execution → Settings
```

它回答三个问题：

1. 现在是否有人需要处理；
2. 系统是否健康、行为是否符合规则；
3. 一项工作如何从 Trigger 走到最终成果。

Prompt 治理要点：

- 团队可编辑 Communication、Ticket Scope、Delivery Requirements 和 Team Skills；
- 可覆盖内置 Prompt Part；
- 每次保存形成不可变版本；
- Session 记录它使用过的版本；
- 默认 Prompt 更新时，团队覆盖内容会显示差异；
- 模型读取最新版本，但并发保存存在 revision 冲突保护。

## 9. 它如何“分析和优化 Agent”

项目体现的是系统级 Agent 工程优化，不是自动自我优化：

### 已经实现

| Agent 问题 | 对应设计 |
| --- | --- |
| 上下文污染 | Router 不深入技术细节，Worker 使用独立 Session |
| 长任务阻塞 | 命令和等待自动转后台，事件驱动唤醒 |
| 新任务挤占人工追问 | 人工消息享额外 Worker Slot |
| 重复执行 | Trigger 稳定 ID、Mandate 幂等、Effects key 唯一 |
| 进程崩溃丢工作 | SQLite 状态、持久队列和 Assignment 恢复 |
| 模型自报完成 | Ticket 生命周期与 PR/Thread 结果绑定 |
| 越权执行 | Gate、Mandate、规则校验和 Prompt 不可授权 |
| 通知噪音 | 结构化 Report，只在完成/失败/需人行动时通知 |
| 提示词难以运维 | 版本、覆盖、默认差异和 Session 使用记录 |
| Agent 失败难排查 | Trigger → Decision → Ticket → Assignment → Result 全链路 |

### 没有实现

| 自动优化能力 | 状态 |
| --- | --- |
| 历史轨迹自动评分 | 未发现 |
| 自动比较角色/模型表现 | 未发现 |
| 按成功率动态路由模型 | 未发现 |
| 自动重写 Prompt/Policy | 未发现 |
| 训练、微调、RL | 未发现 |
| 自动生成并发布 Skill | 未发现 |

所以更准确的表述是：**项目基于对 Agent 失败模式的人工分析，做出了宿主级约束与工作流优化；不是会自我分析、自我训练或自我优化的 Agent。**

## 10. WorkPivot 的实现步骤

建议分阶段吸收，不要一次复制整套领域模型。

### 阶段 0：先确认现有 WorkPivot 边界

实施前核对：

- 当前 Task/Run/Artifact 的持久模型；
- 任务授权快照和项目成员权限入口；
- 模型回合与工具副作用如何提交；
- 执行面是否已有队列、幂等键和回执；
- 成果验收与文件版本如何表达；
- 多 Agent/Subagent 是否已有调度层。

完成标准：形成一张从外部事件到成果发布的现有链路图，并标出缺少的持久化节点。

### 阶段 1：最小事件—授权—工作项模型

新增或映射：

```text
event
- id / source / actor / thread / payload / received_at

grant
- id / event_id / subject / scope / strength
- policy_version / matched_rules / created_at

work_item
- id / grant_id / state / owner / created_at / ended_at
```

最低要求：

- Event ID 幂等；
- Grant 不可变；
- WorkItem 有明确状态机；
- 外部文本不能直接写 Grant；
- 状态变化和审计记录同事务写入。

不要在此阶段引入 Source、Subscription、Correlation 等全部抽象。

### 阶段 2：`observe` 影子运行

在真正执行前增加三种策略：

```text
off       不接收推断工作
observe   只记录拟接单和拟动作
auto      允许创建 WorkItem 并执行
```

影子记录至少包含：

- 原始事件；
- 命中规则；
- 评估结论与证据；
- 拟授权范围；
- 拟调用工具；
- 拟回复或生成成果摘要。

完成标准：管理员可以在真实流量上比较“Agent 会做什么”和“人工认为应该做什么”。

### 阶段 3：把 Agent Session 从 WorkItem 中解耦

- WorkItem 持久存在；
- 每次执行创建独立 Assignment；
- Session 可失败、替换和重启；
- WorkItem 状态根据 Report 和成果更新，而不是根据进程是否存活更新；
- 人工后续消息可以恢复到原 WorkItem，但必须校验 Grant。

### 阶段 4：持久副作用队列与 Outbox

先实现一个通用 Job 表和外部消息回执，不要一次拆出六个 Effects kind：

```text
job
- id / kind / business_key / payload
- status / attempts / next_attempt_at
- last_error / created_at / updated_at

outbox
- id / channel / destination / payload
- status / attempts / sent_at / dropped_reason
```

最低约束：

- 业务事务内写 Job/Outbox；
- 提交后由 Worker 消费；
- `business_key` 保证重复任务合并；
- 外部写成功记录回执；
- 至少支持暂停、重试、死信和重启恢复。

### 阶段 5：人工优先调度

在调度器增加输入类别：

```text
new_work
human_followup
bot_event
ci_event
system_retry
```

建议：

- 人工对已有 WorkItem 的追问优先唤醒；
- 新任务不能永远挤占现有任务；
- 人工追问可保留一个额外槽位；
- 每个 WorkItem 只允许一个活动执行器；
- 同一用户连续消息按 Thread 批处理，避免多次触发。

### 阶段 6：多 Agent 与 Subagent 分工

先定义职责，再决定是否需要多个模型：

| 角色 | 目标 | 不应拥有的能力 |
| --- | --- | --- |
| Router | 分类、授权、路由、停止 | 深入实现、直接提交代码 |
| Worker | 完成单个 WorkItem | 修改策略、扩权、跨租户访问 |
| Subagent | 临时局部任务 | 独立改变目标、发布成果、持久拥有任务 |

只有在以下条件同时满足时才使用多 Agent：

- 多个任务可以独立执行；
- 生命周期或权限确实不同；
- 有宿主级协调器；
- 状态可持久化；
- 可追溯谁拥有最终结果。

Subagent 适合搜索、审查、局部测试等结果可回交父任务的工作。不要用 Subagent 模拟业务任务所有权。

### 阶段 7：可观测与治理面板

最小溯源页应展示：

```text
外部事件 → 授权快照 → 工作项 → 执行尝试
         → 工具/成果 → 验收 → 发布/回复
```

必须能按以下键检索：

- Event ID；
- WorkItem ID；
- 用户/项目；
- 来源链接；
- Policy/Prompt 版本；
- 失败原因；
- 外部消息回执。

### 阶段 8：验证与放权

上线顺序：

1. 只用 `observe` 收集样本；
2. 人工复核分类和拟动作；
3. 开放只读工具；
4. 开放草稿产物，不自动发布；
5. 开放受控工作区修改；
6. 开放外部提交或消息；
7. 最后才评估自动发布或合并。

每一级都需要独立的错误率、回退开关、审计记录和人工接管路径。

## 11. 借鉴映射

| 上游机制 | WorkPivot 最小实现 | 不建议照搬 |
| --- | --- | --- |
| Trigger/Thread/Eval | Event + 状态机 + 研判记录 | 完整 Thread/Correlation 体系 |
| Mandate | Grant 快照 | 将所有来源身份映射逻辑放入 Prompt |
| Ticket/Assignment | WorkItem + ExecutionAttempt | 让 DSH Session 直接充当业务对象 |
| Effects | Job 表 | 第一版拆成大量 kind 和处理器 |
| Outbox | 消息回执表 | 只依赖“调用成功”返回值 |
| Worker Slots | 服务端执行槽与优先级 | 单进程内 Worker 全权限 |
| Router/Worker/Subagent | 角色化工具面和执行生命周期 | 让每个角色都拥有完整工具面 |

## 13. 审核要点

如果 WorkPivot 进入实现阶段，评审应优先检查：

1. Grant 是否能被外部文本影响；
2. 同一 Event 是否可能创建两个 WorkItem；
3. 外部写是否可能被重试两次；
4. Worker 是否可能越权访问其他用户文件或其他项目；
5. 人工追问是否会被新任务长期阻塞；
6. 进程重启是否留下“运行中但无人负责”的任务；
7. 成果是否由验收器确认，而不是模型自报；
8. Policy/Prompt 更新后，旧任务是否能解释和重新校验；
9. 用户是否能看到 Agent 将做什么，并在执行前拒绝；
10. 高权限动作是否有独立授权，而不是继承普通对话权限。
