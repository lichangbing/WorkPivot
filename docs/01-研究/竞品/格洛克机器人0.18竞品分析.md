## 1. 产品与用户

- **厂商/作者：** Anysphere，处于 Cursor 产品生态；部分社区材料把它与 xAI/SpaceX 关联，但重建仓库明确声明与三者均无官方关系。
- **产品标识：** Grok Bot 0.18.0，上游 bundle ID `com.anysphere.sand`，Electron 42.1.0，固定构建日期为 2026-08-13。
- **定位：** 面向个人知识工作者的长期桌面 Agent。每个 Bot 是一个有名字、人格、记忆、会话和桌面的“常驻队友”，通过连接器、文件、终端、浏览器、GUI 和例程完成跨应用工作。
- **目标用户：** 希望用自然语言驱动机器完成信息检索、跨应用操作、文件处理、网页/GUI 自动化和周期任务的个人用户；证据显示也包含团队共享房间、云端 Worker 和同架构项目 Agent 的产品方向。
- **产品形态：** Electron 桌面客户端 + 主进程 + Node Agent Coordinator + Host + 持久 Box（远程或本地 Docker）+ 连接器/MCP + Routine/Workflow/Skill。
- **场景边界：** 它是通用个人/工作 Agent，不是只写代码的 Coding Agent，也不是以 Office 成果版本和验收为中心的办公工作台。它可能创建表格、文档或脚本，但核心抽象仍是“让一个常驻 Agent 使用一台电脑和若干服务”。

## 2. 暴露过程与版本谱系

### 2.1 为什么 0.18 的运行时非常可读

2026-08-23，社区作者 `b-nnett` 发布 `grok-bot-0.18-reconstructed`，把公开 macOS 安装包整理成可读 TypeScript，并在热度中迅速出现大量镜像。早期转述把原因写成“运行时 source map 未关闭”，但字节级复核支持另一个结论：

1. 官方安装器公开分发，属于任何人可下载的产物，但不等于源码或代码使用许可。
2. Electron 主进程、Host、Coordinator、本地执行守护进程等 esbuild bundle 没有压缩，保留原始类名、函数名、注释和 `// ../../packages/...` 模块路径标记。
3. 社区工具按这些模块路径标记做纯字节切片，重组后与官方 bundle 逐字节一致。
4. macOS DMG 全树与 Windows `app.asar` 均未发现 `.map`，运行 bundle 和 renderer 分块也没有 `sourceMappingURL`。
5. Renderer 本身经过压缩且无 source map；公开重建只能依据打包后的 DOM、字符串、CSS、RPC 契约和行为信号做部分恢复，不能还原作者原始前端。

macOS DMG 的精确结果是 13 个运行时 bundle、6,561 个模块切片，其中 2,357 个首方模块分属 32 个可识别包，另有 4,204 个第三方依赖切片。它不是把某个 source map 展开，而是把本来就可读的运行时 bundle 机械整理成树。

macOS 与 Windows 的 13 个同名 bundle 均存在字节差异，连 `preload.cjs` 也并非完全相同；因此不能把某一平台的重建结果无条件当成另一平台的官方行为。

2026-11-04 在 GitHub 以精确短语检索返回几十个相关或误命中仓库。绝大多数高相似仓库是同一重建树的 fork、镜像或平台分支，不能把仓库数量当成产品版本数量；判断谱系应看固定安装包哈希、构建输入、notice/provenance、目录差异和功能来源。

### 2.3 事件复盘

- **暴露窗口：** 官方 0.18.0 安装包公开下载后，社区在 2026-08-23 快速发布重建，8 月 27 日出现更严格的运行时原样归档，随后派生仓库扩散。
- **技术根因：** 可读的未压缩后端 bundle 加上模块路径注释；前端压缩和缺失 source map 使恢复范围不对称。
- **边界失真：** “可读”被传播成“官方源码泄露”；“重建仓库有 MIT/Apache 标签”也可能被误解为上游代码被合法再许可。
- **后续变化：** 官方下载 URL 后来出现 HTTP 403，社区通过 Git LFS 保存固定 DMG/安装器。派生项目继续新增本地模型、Docker、API、Windows 和 UI 功能，已不再适合作为单一版本证据。
- **对 WorkPivot 的发布教训：** release artifact 必须检查 source map、未压缩内部 bundle、调试注释、构建机路径、令牌、`.env` 和符号文件；公开可见不产生复用许可；热点泄露仓库是供应链攻击高风险入口，不应下载或运行来源不明的二进制。

## 4. 部署、模型与数据

- **客户端：** Electron 42.1.0。Renderer 开启 `contextIsolation`、关闭 `nodeIntegration`，通过 preload 暴露窄桥。
- **执行面：** 官方模式由 Broker `ensureSandBox` 返回 Host gateway URL、Bearer token、network token 和 VNC 描述；社区本地模式由 Docker 启动固定镜像，端口只发布到回环地址。
- **服务拓扑：** 桌面 Main 管理生命周期、设置、认证和 Box 连接；Coordinator 作为 `utilityProcess` 负责命令转发、SSE、转录路由和恢复；Host 位于 Box 中，负责会话、推理、工具、MCP、审批、记忆和 Routine。
- **模型接入：** 原始产物中可观察到 `cursor-*`、Claude、Grok、GPT、Gemini 等模型标识；社区重建增加 Cursor/Claude Code/Codex/OpenRouter 推理路由。不能把社区新增路由写成官方 0.18 功能。
- **数据边界：** 至少存在三层文件位置：Agent 自己的 Box、用户电脑、客户端主机。Box 是跨 Agent 共享的一台 Linux 机器；桌面窗口按 Agent 隔离。连接器凭证、secret-request、桌面交接和动作审计都有独立处理路径。
- **私有化：** 原生产品依赖 Cursor 账号、Broker 和云端 Box；本地 Docker 与自带模型路由是社区派生能力，不是原始 0.18 的默认部署方式。

## 5. 技术架构

### 5.1 四层控制面

```text
┌─────────────────────────────────────────────────────┐
│ Electron Renderer                                   │
│ 会话、消息、Agent/Group、Widget、文件预览、VNC        │
└──────────────────────┬──────────────────────────────┘
                       │ preload：受控 RPC + MessagePort
┌──────────────────────▼──────────────────────────────┐
│ Electron Main                                       │
│ 窗口/生命周期、设置、账号、凭证、插件/更新、Box 连接   │
└──────────────────────┬──────────────────────────────┘
                       │ utilityProcess.fork
┌──────────────────────▼──────────────────────────────┐
│ Node Agent Coordinator                              │
│ 命令派发、HTTP 网关、SSE、转录路由、本地执行守护、重连  │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP /api/* + SSE /events
┌──────────────────────▼──────────────────────────────┐
│ Box 内 Host                                         │
│ Agent sessions、模型推理、Turn、工具、MCP、审批、例程  │
├─────────────────────────────────────────────────────┤
│ Box 执行面                                          │
│ shell、文件、browser、desktop/VNC、exec daemon       │
└─────────────────────────────────────────────────────┘
```

这种拆分让 Renderer 只拥有产品交互，不直接拥有文件系统或 Node 权限；Coordinator 可以替换渲染器、独立重连；Host 与用户消息生命周期绑定；Box 可以重建而不销毁 Agent 的业务身份。

### 5.2 命令链路与事件链路

Gateway 固定契约：

```text
API:     POST <baseUrl>/api/<method>
EVENTS:  GET  <baseUrl>/events
HEALTH:  GET  <baseUrl>/health
AUTH:    Authorization: Bearer <gateway token>
TRACE:   traceparent
```

命令请求顺序：

```text
Renderer RPC
  → preload 白名单桥
  → Coordinator dispatchRequest
  → 可选推理路由 / MCP 路由
  → POST /api/<method>
  → HostGatewayApi
  → transcript / session / Box / extension
  → JSON 结果
```

事件顺序：

```text
Host SSE /events
  → Coordinator SSE decoder
  → 通道归并、VNC 代理信息补全
  → renderer MessagePort
  → 消息流、工具活动、审批、Agent roster、Box 状态
```

Gateway 暴露的方法覆盖 transcript、sendPrompt、widget/secret、Agent/Group、memory、automation/routine、workflow/skill、MCP、Box 获取/重建/迁移、附件和设置。它不是为每个 UI 页面另开私有 IPC，而是把业务能力收敛到 Host 命令面。

### 5.3 `sendPrompt`：接收、幂等与恢复

`HostGatewayApi.sendPrompt` 等待 transcript manager 接收消息后返回 `{ accepted: true }`。它传递 `agentId`、附件、rich text、回复关系、`clientNonce`、fork、trace 和时间信息。这个返回只证明“消息被接收”，不证明 Agent 已完成任务或已经向用户可见回复。

Coordinator 的重试规则刻意保守：

- 请求未真正发出时，可以重试；
- 请求已经发出时，只允许在相同 gateway base URL 已被证明支持 `sendPrompt` 去重时重试；
- Host 在响应头声明 mint-dedupe 能力后，Coordinator 才把该 endpoint 加入可信重试集合；
- 重试必须固定原 endpoint，期间 endpoint 改变则放弃；
- `createAgent` 使用 `clientNonce` 去重，最多 3 次、1s 起始、4s 上限的退避；
- 对未知 gateway 方法、鉴权失败和永久拒绝不做盲目重试。

SSE 连接也有独立恢复策略：1s 起始、最大 10s 指数退避，15s 连接超时，35s 无数据视为 stall；Host 每 15s 发心跳；重连代次防止旧连接事件覆盖新连接状态。

### 5.4 Box 是持久执行身份，不是一次工具调用

官方连接器通过 `GrokBotService.ensureSandBox` 获取 Box 描述。社区本地 Docker 连接器以内容寻址方式保存 Host/daemon runtime，启动容器并发布 `1337`、`1339`、`1340` 等回环端口。Host 在 Box 内启动 gateway 并写发现文件。

Box 支持：

- 文件、shell、后台 shell、浏览器、桌面和 noVNC；
- 多 Agent 共享一台 Box 文件系统，但按 Agent 分配桌面窗口；
- Box 更新、重建、迁移、保留或放弃数据；
- VNC 存活探针、桌面窗口租约和失败回滚；
- Host 与执行守护分离，Host 重启不必销毁整个 Box。

## 6. 业务流程

### 6.1 一次用户请求

```text
用户输入
  → Renderer 生成 clientNonce/时间/trace
  → Coordinator POST /api/sendPrompt
  → Host 接收消息并返回 accepted
  → 唤醒对应 Agent Session
  → 组建本 Turn 的静态工具与动态 MCP 工具
  → Agent 先发送可见确认，再调用工具
  → Box 执行 / 子代理后台执行 / Host 等待审批
  → 工具事件经 SSE 持续回到界面
  → Agent 用 SendMessage 交付可见结果
  → transcript 持久化；未完成交付形成 ack obligation
```

模型原始 assistant 文本在这个产品中是私有 scratchpad；用户只能看到 `SendMessage` 工具产生的消息。这个约束把“模型想过什么”和“用户实际收到什么”分开，也给宿主提供了可检查的交付点。

### 6.2 可见确认与交付债务

实现不只依赖 Prompt：

- 每轮开始时若模型先调用工具而没有文本 `SendMessage`，middleware 注入一条强提醒；
- 连续多次工具调用仍无可见消息时，`SendMessageReminderMiddleware` 再次注入提醒；
- `accepted` 用户消息如果因中断、崩溃或重启没有得到可见回复，会记录 ack obligation；
- 恢复时 Agent 必须实际调用 `SendMessage`，可以确认结果、说明仍在处理，或坦白可能漏掉用户最新消息并请其重发；
- 不允许把看不见的内部工作说成已完成；最多重投 3 次，空闲或启动时触发；
- 开场 ack 不等于最终交付，用户等待的结果仍必须通过另一个 `SendMessage` 返回。

这一机制直接解决 WorkPivot 中“消息已入库但用户没有看到响应”和“重启后模型自认完成”的典型故障。

### 6.3 多 Agent 与子代理是两个层次

这是**长期多 Agent 系统，内部再使用任务型子代理**：

| 层次 | 生命周期 | 责任 | 典型工具 |
| --- | --- | --- | --- |
| 命名 Agent / Bot | 长期，有独立会话、profile、memory、工具和桌面 | 持续服务用户、与其他 Agent/Group 协作、发起任务 | `SendMessage`、`SendToAgent`、`CreateAgent`、`UpdateAgent` |
| 任务型 Subagent | 单次 Task 范围，后台运行，父 Agent 被完成事件唤醒 | 隔离浏览器或桌面任务，向父 Agent 回交结果 | `Task`、`CheckSubagent`、`MessageSubagent`、`StopSubagent` |

`SendToAgent` 是 fire-and-forget：消息投递和目标 Agent 唤醒后立即返回，不等待回复；对方回复在后续新 Turn 唤醒发送方。这样避免 Agent 在同一个 Turn 里轮询另一个 Agent。

`browserUse` 在页面/DOM 层工作，使用结构化 snapshot 的 `ref`，比像素点击稳定；`computerUse` 用截图和坐标/键鼠操作 GUI。多个普通子代理可以并行，但共享同一桌面时只允许一个 `computerUse`，因为桌面只有一个屏幕。父 Agent 在子代理完成时自动被唤醒；`CheckSubagent` 用于观察卡住/循环，不承担完成轮询。

### 6.4 权限不是一张“是否继续”卡

至少存在三类不同机制：

| 机制 | 控制对象 | 关键语义 |
| --- | --- | --- |
| Local Tool Permission | 用户电脑上的 read/list/write/send-input/run-command | `always / ask / never`，默认 `ask` |
| Auto-review | Host shell、Box shell、MCP、Computer、Subagent launch 等 surface | `off / shadow / enforce`，可按执行面独立配置 |
| Human handoff | 登录、SSO、2FA、captcha、payment | 把 Box 桌面交给用户，办完 handback 后恢复 Agent |

Local permission 的审批绑定 Agent、tool call、action、target 和方向 epoch，不是只记忆“某个工具允许”。一次允许、始终允许、拒绝和始终拒绝有不同状态；新用户消息使旧方向上的审批过期。拒绝过的具体 action+target 会被记住，避免 Agent 换个措辞立即重试。

Auto-review 的 `shadow` 只记录“按策略本应阻止什么”，不阻止真实动作，适合新 Agent 或新规则先评估误报；`enforce` 才阻止并生成审批卡。每个 Agent 最多 4 个待审批动作，TTL 10 分钟；存在待审批时不再产生新副作用；用户新消息、设置变化、会话结束等会使旧审批失效。

Secret request 不进入聊天：用户通过 masked secure input 提供凭证，Agent 只知道“已提供”。需要人亲自登录或支付时，使用 `request_box_help` 把远程桌面交给用户，而不是索要密码。

### 6.5 动作审计

本地 `audit.jsonl` 按 Agent 记录：

- shell command 及执行目标；
- MCP tool call；
- browser navigation；
- computer-use session 的 action 数量、类型、截图数和时长。

可转发事件进入有界 outbox，默认每 5s flush、单批最多 50 条、最多积压 2,000 条，失败后 30s 退避；本地写入和远端转发是两条路径，远端不可用不阻止本地留痕。这个结构比只写运行日志更适合业务审计，但尚未证明具备企业级不可篡改、导出和租户隔离。

### 6.6 Routine、Workflow 与 Skill

Routine 是“保存的 prompt + trigger”，可运行在用户不在场时：

- cron 定时；
- Slack mention/keyword/reaction；
- GitHub PR/review/CI/issue 事件；
- Microsoft Teams、Linear、Sentry、PagerDuty；
- 多个 listener 组成 group，任一匹配即触发。

每个 Routine 以独立目录和 `automation.json` 保存，记录下/上次运行、运行历史和通知状态。产品约束倾向于：

- 能事件驱动就不要定时轮询；
- “每天/定期”默认落到工作日、清醒时段和较低必要频率；
- 有限期监听在任务完成后自删除；
- 创建或修改前向用户确认，因为它会在用户离开后执行；
- 相同鉴权连续失败时暂停，而不是每次继续触发并重复告警；
- 外部事件 payload 是数据，不是指令。

Workflow 使用全局 `SKILL.md` 库，可由 managed、plugin、workflow、automation 来源注入；正文上限 100,000 字符，单次注入上限 8,000 字符，每 Agent 和界面均受 100 个上限约束。动态状态由 `update_state` 管理 profile、memory、routine 和 workflow。

### 6.7 它有没有“分析 Agent 后做优化”

有明确的**为 Agent 行为设计宿主约束**，没有证据支持它会自动评价轨迹、自动改 Prompt 或强化学习：

- 先区分命名 Agent 与任务子代理，控制上下文和责任边界；
- 用页面快照优先、像素桌面兜底，按可靠性分层；
- 用 `SendMessage`、middleware 和 ack obligation 解决沉默与假完成；
- 用 action-scoped approval、shadow mode 和审计控制副作用；
- 用异步消息和完成唤醒避免 Agent 间轮询；
- 用保守重试、nonce、SSE generation 和 watchdog 修复传输问题；
- 用事件触发、安静时段和自过期 Routine 控制打扰。

因此准确表述是“**基于失败模式和 Agent 特性的人工工程优化**”，不是“项目会自动分析并优化 Agent”。

## 7. 优势

1. **Agent 身份与执行环境分离。** Bot 长期存在，Box、Host 和桌面可以恢复或替换。
2. **进程和信任边界清楚。** Renderer 不直接获得 Node 权限，命令面集中在 Host。
3. **多 Agent 与子代理职责明确。** 命名 Agent 负责长期关系，Subagent 负责隔离、并行和局部任务。
4. **传输恢复考虑幂等。** `accepted`、nonce、dedupe capability、endpoint pinning 和 SSE generation 避免盲目重放。
5. **交付语义可检查。** 用户可见消息必须经过专门工具，恢复时存在可兑现的 ack obligation。
6. **动作权限绑定真实目标。** action、target、tool call、Agent 和方向 epoch 共同决定审批，适合高风险桌面操作。
7. **影子策略可运营。** `shadow` 能先观察误报，再决定是否 `enforce`。
8. **桌面操作回交自然。** 登录/2FA/支付由用户亲自完成，Agent 在 handback 后从截图恢复。
9. **Routine 产品化程度高。** 事件、时区、运行历史、权限失败暂停和低噪音通知语义都有明确规则。
10. **架构证据可追溯。** 原样 bundle 哈希、模块拆分、重建 provenance 和固定安装包使大部分行为可复核。

## 8. 限制、风险与未验证项

- **不是官方源码。** 代码组织、注释和类型是社区推导结果，不能据此断言作者 monorepo 的原始包结构。
- **前端恢复不完整。** Renderer 压缩且无 map，公开 `frontend/` 是部分重建，打包时甚至继续使用经校验的原厂 renderer。
- **版本混杂。** 主流重建虽以 0.18.0 为基线，但部分模块和提示文本来自后续版本移植；GrokNode 的 `0.78.1` 是社区派生版本号。
- **未运行真实产品。** 本轮未下载/执行安装器、未创建真实账号、未连接真实 Box 或 SaaS，也没有验证云端 Host 与开源重建在所有细节上一致。
- **许可风险高。** 上游专有；原样归档明确不授予权利；MIT/Apache 标签不能覆盖派生前已有的 Anysphere 代码和 prompt。
- **供应链风险高。** 泄露热点会吸引恶意镜像和带毒安装器；不能把“stars 多”当成安全认证。
- **桌面安全并非生产基线。** Electron Main 代码中可见 `sandbox:false` 和 `--no-sandbox`；VNC、共享桌面和用户电脑操作需要额外隔离。
- **企业能力未闭环。** 未确认多租户 RLS、组织成员同步、Office 文件版本、成果发布审批、DLP 和完整审计导出。
- **Routine 状态模型偏轻。** 以目录和 JSON 为主，适合单机研究，不等于 WorkPivot 需要的持久 Job、Outbox、租约和跨实例调度。
- **Prompt 复制风险。** 部分行为约束写在非常长的工具描述和系统提示中；WorkPivot 应重写为协议、状态机和短规则，不能复制上游文本。

## 9. 对 WorkPivot 的启示

### 值得借鉴

1. **控制面 / 协调器 / Host / 执行面分层。** UI、连接恢复、Agent 执行和 Box 生命周期分开部署和恢复。
2. **长期 Agent 与任务 Subagent 分开。** 命名 Agent 是业务关系；Subagent 是带父任务、超时、可停止、可注入反馈的执行单元。
3. **收到消息与完成交付分开。** `accepted` 只表示宿主已接管，必须再有可见进展和最终结果。
4. **把“交付债务”做成持久状态。** 中断、崩溃、重启后检查是否存在未兑现的用户消息，并让 Agent 明确重发、确认或请求用户重发。
5. **用户提示采用结构化 Widget。** 只在破坏性 go/no-go、无法检索的真实歧义和用户独有信息上提问；选项必须真实、有限、可回传。
6. **审批绑定动作目标。** 记录 action、target、Agent、tool call、任务方向和策略版本；拒绝原因进入下一轮，不能原样循环。
7. **先 shadow 再 enforce。** 新 Agent、连接器和风险规则先在真实任务中记录拟阻止动作，人工校准后开放硬阻止。
8. **人工接管是正常流程。** 登录、2FA、captcha、支付、审批等步骤把可控桌面或运行交给用户，完成后从当前状态恢复。
9. **事件优先于轮询。** Routine 和后台任务优先监听业务事件；时间任务使用有界窗口、时区和自过期定义。
10. **子代理完成由宿主唤醒父 Agent。** 父 Agent 不轮询完成；检查工具只用于诊断卡顿，注入工具用于纠偏但不重开上下文。
11. **任务作用域动态工具。** 普通 Agent 不一次性拿到浏览器、桌面、云 Agent、MCP 全部能力；由任务和环境决定工具面。
12. **审计先本地成功。** 本地 JSONL 不应因远端审计服务短暂不可用而丢失；远端用有界 outbox 异步补发。

### 应当规避

- 不复制 Grok Bot 代码、系统提示、工具描述、前端资源或派生项目功能。
- 不把“未压缩发行 bundle”当成官方源码质量或稳定 API。
- 不为所有任务都创建 Agent 或子代理；只有长期身份、隔离上下文或不同执行面确有收益时才拆分。
- 不让多个 Agent 通过无幂等聊天消息直接承担关键业务写操作。
- 不用长 Prompt 代替确定性审批、幂等、状态机和恢复代码。
- 不让 Renderer、模型或第三方 Skill 直接持有 Box token、平台 token 或用户电脑权限。
- 不把远程 VNC 当作企业执行隔离；共享桌面仍需要账号边界、剪贴板策略、网络策略和水印/审计。
- 不把社区重建的“可运行”当作与官方云服务兼容或未来版本兼容的承诺。

### 与 WorkPivot 的结合机会

| WorkPivot 现有方向 | 可叠加的借鉴 |
| --- | --- |
| 项目 → 任务 → 运行 → 成果 | 增加 `accepted / acknowledged / delivered / failed` 交付状态，不以运行结束代替用户可见交付 |
| 多 Agent / 任务执行 | 长期工作角色与临时执行子代理分层；子代理必须绑定父任务、预算、完成回调和清理策略 |
| 任务授权快照 | 审批键扩展为 Agent + WorkItem + tool call + action + target + policy version |
| 文件与浏览器操作 | 页面 DOM 操作与桌面像素操作按任务选择，不把 GUI 自动化作为默认路径 |
| 记忆与技能 | Agent 级 profile/memory 与全局 Skill 分开；技能正文、脚本、来源和注入预算分别治理 |
| 自动化 | Routine 采用事件优先、安静时段、触发去重、运行历史、鉴权失败暂停和自过期 |
| 企业私有化 | 保留 Host/Box 执行面抽象，但用租户、项目、文件 ACL、审计和审批替代个人 Cursor 账号边界 |
| 人工确认 | 将需求澄清、计划审批、动作授权、登录交接和成果验收做成不同协议与状态 |

### 差异化机会

Grok Bot 擅长“一个长期个人 Agent 使用一台电脑持续做事”，但对 WorkPivot 最关键的组织项目、业务事实、Office/PDF 版本、数据权限、成果验收和企业审计并未形成可验证闭环。WorkPivot 可以吸收其执行面和交付语义，同时把“谁授权、基于哪份文件、生成了哪个版本、如何验收、发布给谁”补成完整业务事实链。

## 10. 许可与复用边界

- **上游许可证：** 未发现可复用的公开源码许可证；运行时 bundle 和 prompt 版权归 Anysphere。
- **原样归档：** `grok-bot-0.18-original` 明确写明仅用于研究、不授予代码权利，并会在权利方要求时移除。
- **主流重建：** `NOTICE.md` 明确声明不主张也不授予上游源码许可；使用者需独立完成版权、商标与再分发审查。
- **派生仓库标签：** 某些项目自行标注 MIT/Apache，这种标签不能追溯清除上游代码、提示和资源权利。
- **可复用内容：** 本 WorkPivot 文档只吸收架构思想和可独立实现的协议原则；不复制代码、长 Prompt、前端资源、模型能力清单作为 WorkPivot 事实。
- **第三方依赖：** 重建项目的依赖树包含大量第三方包，若未来做兼容验证，必须分别核对 Electron 运行时、native 模块、MCP SDK、字体/图标和安装器工具许可。
- **研究纪律：** 只检查公开源码归档和文档，不下载未知镜像，不执行第三方重建二进制，不把哈希当作安全证明。
