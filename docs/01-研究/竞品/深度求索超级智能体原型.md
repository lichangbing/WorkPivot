> **结论：** dsh-superagent-prototype 的首要价值不是“会写代码的模型”，而是一套面向长期运行的 Agent 控制面：把外部事件、授权、工单、执行器、副作用和人工监督拆成可持久化、可恢复的生命周期。它证明“超级 Agent”的竞争力可以来自约束、调度和审计，而不只来自扩大模型自主性。WorkPivot 值得借鉴其事件—授权—工单—执行—审计模型、`observe` 渐进放权、持久副作用队列和人工优先通道；不应直接复制其完整领域模型、单机全权限执行方式和对 DSH Alpha API 的深度耦合。

## 1. 产品与用户

- **厂商/作者：** DeepSeek Harness Team（`team@dsh.dev`），代码位于 DeepSeek 官方 GitHub 组织。
- **定位：** 面向单个 github.com 仓库的主动式 Coding Agent，以 DeepSeek Harness（DSH）Bundle 形式运行。
- **目标用户：** 愿意自托管、能够维护 CLI 账号和 Agent 运行环境的小型研发团队。
- **主要场景：** GitHub Issue、Pull Request、评论和 CI 触发工作；可选接入飞书；Agent 研判后创建工单、在独立 Session 中修改代码、提交 PR，并把结果回写到原对话。
- **产品形态：** DSH Web 插件 + 后台常驻服务 + 每工单独立 Agent Session + 管理面板 + CLI 运维脚本。

README 明确说明这是研究原型，不是官方 DeepSeek 产品；公开版经过改编，与内部版本及团队文章所述完整系统并不相同，文章中部分设计仍是未来方向。

截至本次复核，上游主分支只有一个可见初始提交 `6337fc823ce20251c8de8085948165c81aaa701e`，提交时间为 2026-10-31。它更像一份完整度较高但尚未经过长期维护验证的研究发布。

## 2. 核心能力

| 能力 | 成熟度 | 说明 |
| --- | --- | --- |
| GitHub 事件接入 | ✅ | 账号通知、Issue、PR、评论、代码评论、订阅 Thread、PR 生命周期和默认分支 CI |
| 飞书接入 | 🧪 | 可选事件消费、历史补收、Thread 轮询、图片读取和主题回复 |
| 请求研判与工单 | ✅ | 区分显式请求和推断工作；Decision 形成 Mandate 与 Ticket |
| Coding Agent 执行 | ✅ | 每工单持久 Session、独立目录、Git worktree 准备命令、后台任务和子代理 |
| 多 Agent 协作 | ✅ | 主 Session 路由，一个或多个 Worker Session 独立执行 |
| 子代理 | ✅ | Worker 按需派生临时 Subagent，使用 DSH `standard` preset |
| 权限与策略 | ✅ | 允许列表、来源范围、准入表、规则、`off/observe/auto` 和策略版本 |
| 可靠执行 | ✅ | SQLite、事务、幂等、持久 Effects、Outbox、重试、恢复和暂停 |
| 人工监督面板 | ✅ | Source、Trigger、Eval、Execution、Settings、Prompt、历史和健康状态 |
| 提示词治理 | ✅ | 团队区段、内置文本覆盖、不可变版本、默认更新差异 |
| 自动性能优化 | ❌ | 没有轨迹评分、自动调参、自动改写提示词或按历史成功率路由模型 |

这里的 `Eval` 指对外部 Trigger 是否应进入新工单的研判，不是评价 Agent 历史表现或进行强化学习。

## 3. 部署、模型与数据

- **客户端：** 通过 DSH Web UI 打开 Superagent 面板；没有独立桌面应用。
- **运行环境：** Node.js 22.19+ 或 24+、pnpm、git、Python、tmux、GitHub CLI；飞书另需 `lark-cli`。
- **依赖边界：** 项目自身只有 `zod` 和 `proper-lockfile` 两个运行时直接依赖，但强依赖大量 `@deepseek-ai/dsh-*` Alpha/Nightly 能力。
- **模型接入：** 使用 DSH 配置的模型提供商；评估角色和执行角色可分别配置 provider、model 与 reasoning effort。
- **持久化：** 单 SQLite 数据库 `<stateDir>/orchestrator.sqlite`，保存 Trigger、Thread、Decision、Ticket、Effect、Outbox 和 KV 记录。
- **私有化：** 可完全在本地机器运行，但只面向 github.com；不支持 GitHub Enterprise Server。
- **数据与账号边界：** GitHub 必须使用普通用户账号的 `gh` 配置，不能以 GitHub App 作为 Agent；飞书使用受限 Bot 配置。
- **隔离边界：** Worker 以操作者 OS 用户运行，拥有 `danger-full-access`。CLI 包装器和阻断命令只是默认入口，不是安全沙箱。

## 4. 架构与技术观察

### 4.1 主数据流

```text
GitHub / 飞书
    │
    ▼
Source → Trigger → Thread → Eval/Decision
                               │ accept
                               ▼
                         Mandate + Ticket
                               │
                               ▼
                    Assignment → Worker Session
                               │
                     ┌─────────┴─────────┐
                     ▼                   ▼
                Subagents          PR / 评论 / 回复
                     │                   │
                     └──── Result ───────┘
```

### 4.2 领域对象和职责

| 对象 | 职责 |
| --- | --- |
| Source | 把 GitHub、飞书等原生事件规范化为 Trigger，并保存读取位置和来源配置 |
| Trigger | 一个不可变外部事件；有稳定幂等 ID，不直接等同授权 |
| Thread | Trigger 的时序上下文；同一 Thread 至多一个 Eval，可关联多个 Ticket |
| Eval / Decision | 判断请求是否接单；记录原因、证据、匹配规则和结论 |
| Mandate | 不可变授权快照，记录授权强度、策略版本、来源范围、身份和匹配规则 |
| Ticket | 有独立生命周期的授权工作单元；不跟随某个 Agent Session 的临时状态 |
| Assignment | Ticket 与一次执行器实例的绑定，可多次创建、重试和恢复 |
| Effects / Outbox | 持久化外部副作用与消息回执，保证重试、幂等和顺序 |

`src/core/engine.ts` 是核心状态的单一事务写入口；调用方只能获得按角色裁剪后的 `Pick<Engine, ...>` 接口。

### 4.3 多 Agent 与子代理是两个层次

主架构是**多 Agent**：

- `orchestrator` 是主 Session，负责研判、接单、停止、关联工单和转述；
- 每个 Ticket 创建独立 `worker-<ticketId>` Session；
- Worker 有独立上下文、目录、并发槽位和跨回合生命周期；
- 主 Agent 的回合结束后，Worker 仍可继续存在；
- 协调者是宿主中的 `Engine + SQLite + Ticket + Assignment + Effects`，不是主 Agent 的聊天记忆。

执行层又允许**子代理**：

- Worker preset 启用 `tool-subagent`；
- 临时子代理使用 DSH `standard` preset；
- 子代理适合并行检索、审查或局部任务，结果回到 Worker；
- 主 Router preset 不启用子代理，避免调度角色继续扩张技术工作。

因此准确结论是：**主系统是多 Agent，Worker 内部可选使用子代理。**

### 4.4 授权和渐进放权

系统把授权从提示词提升为宿主机制：

- 允许列表决定谁能在某个 Source 发起工作；
- 显式 `@` 与推断工作使用不同强度；
- `off` 不接受推断工作，`observe` 只记录“本来会做什么”，`auto` 才真正接单；
- 接受推断工作必须匹配启用规则，并提交意图证据和已确定方向；
- Mandate 记录策略版本，恢复工单时重新验证；
- 外部消息、评论、引用文档永远只算数据，不能改变权限。

这套设计值得直接借鉴，但 WorkPivot 应把身份、项目成员、文件权限和租户隔离放在宿主服务层，而不是只依赖单一 Worker 进程内的规则。

### 4.5 执行、并发和恢复

- 每个 Ticket 使用持久 Worker Session 和独立目录；
- 通过准备命令创建 checkout，典型做法是 `git worktree`；
- 新任务的 foreground shell 和 job wait 超过 5 秒转入后台；
- 新工单受 `maxWorkers` 限制，人工后续消息可使用额外一个槽位；
- Worker 结束回合但仍有后台任务时继续占用槽位；
- Assignment 结束会回收后台 Job 和子代理；
- 启动、投递、回复和评估通过持久队列执行；
- 进程重启后恢复中断 Assignment、未投递输入和待发送消息；
- PR 合并/关闭是工单生命周期事件，不由模型自报“完成”直接替代。

### 4.6 Agent 导向的系统优化

项目确实有强烈的“先分析 Agent 特性，再调整系统结构”的痕迹：

- 为控制上下文污染，Router 只路由，Worker 才读代码和日志；
- 为减少阻塞，主 Agent 的后台命令和等待有硬上限；
- 为减少通知噪音，执行中不持续播报，只在完成、失败或需人工决定时发言；
- 为降低误操作，工具按角色裁剪，推断工作附带更严格的 Mandate；
- 为保持响应，人工后续消息有独立槽位；
- 为可解释，保存 Trigger、Decision、Mandate、Assignment 和 Prompt/Policy 版本；
- 为长期运行，把外部副作用和恢复机制放在模型循环之外。

但这不是自动优化 Agent。没有证据表明项目会：

- 用历史轨迹自动评价角色或模型；
- 根据成功率自动调整模型路由；
- 自动改写 Prompt 或 Policy；
- 用 Reward/Trace 训练或微调 Agent；
- 自动发现并发布新技能。

它采用“人工分析失败模式 → 设计确定性约束 → 用真实流量 observe → 人工复核后放权”的路线。

## 5. 优势

1. **系统边界清楚。** 模型负责判断与执行，权限、幂等、恢复和投递由宿主负责。
2. **渐进自主可运营。** `observe` 模式让团队先用真实流量校准 Agent，不靠一次性信心上线全自动。
3. **工单而非聊天是事实来源。** Session 可替换，业务工作单元不丢失。
4. **人工消息优先。** 已有工作不会永远排在新任务后面，符合团队协作场景。
5. **可靠性设计完整。** 持久队列、Outbox、重试、暂停、重启恢复和幂等覆盖到实际长期运行问题。
6. **可观测性强。** 能追溯来源事件、决策理由、授权、执行器和最终产出。
7. **角色工具面克制。** Router、Worker、Subagent 各有不同职责，降低模型在不合适层级做错误决策的概率。
8. **文档把规则产品化。** 注意力成本、一个人一个问题、健康状态不占空间等原则可以直接转化为 UI 和交互约束。

## 6. 限制、风险与未验证项

- **研究原型，不是稳定产品。** 无正式 release 或长期维护承诺，公开主分支当前只有一个初始提交。
- **平台覆盖窄。** 一个 github.com 仓库、可选飞书；不支持 GHES、GitLab、Jira、Slack 等。
- **Source 抽象不彻底。** Outbox、资源读取、PR 工具、链接和设置检查仍包含 GitHub/飞书特定逻辑。
- **DSH 版本耦合。** 深度依赖 `0.2.1-alpha.2` 系列包和 Cordis 服务模型，不能直接迁移到 WorkPivot 的服务端技术栈。
- **安全边界不足。** Worker 拥有操作者 OS 用户和完整文件访问，不适合作为多租户执行面。
- **状态机复杂。** Trigger、Thread、Subscription、Ownership、Assignment、Report 和 Outbox 的交互很多，学习和维护成本高。
- **无数据保留策略。** Trigger、Decision、Ticket、历史版本和回执当前会持续增长。
- **没有自动 Agent 评测优化。** 面板和历史用于人工复盘，不形成自动质量闭环。
- **未完成真账号端到端验证。** 本次确认了源码、类型检查、构建和测试状态，但没有连接真实 GitHub/飞书账号运行完整业务流程。

### 本地验证结果

2026-11-01，在 Node.js `22.23.4`、pnpm `11.7.0` 下：

- `pnpm install --frozen-lockfile`：通过；
- `tsc --noEmit`：通过；
- `tsdown` 构建：通过；
- Vitest：`1196/1197` 通过，`58/59` 测试文件通过；
- 稳定失败项：飞书事件消费器测试，错误健康状态被后续 `ready` 状态覆盖；

失败项不阻断构建，但说明当前公开快照尚未达到全绿状态。

## 7. 对 WorkPivot 的启示

### 值得借鉴

1. **事件、授权和工单分层。** 不要把“收到请求”直接变成“模型执行”；至少形成 `Event → Grant → WorkItem`。
2. **`observe` 渐进自主。** 新 Agent 或新规则先影子运行，记录拟接单、拟动作和拟回复，人工校准后再开放执行。
3. **Mandate 授权快照。** 每个任务记录策略版本、授权人、作用域、强度和匹配规则，恢复时重新校验。
4. **工单与 Agent Session 分离。** 会话失败、替换或重启不应改变业务任务身份。
5. **持久副作用队列。** 把启动、工具执行提交、消息发送和成果发布变成可重试任务，而不是模型回合里的隐式副作用。
6. **Outbox 与幂等回执。** 评论、通知和 PR 操作必须防止重试造成重复外部写。
7. **人工优先通道。** 人工对现有任务的追问应有独立调度优先级。
8. **角色化工具面。** 调度 Agent、执行 Agent、Subagent 不应拿到相同的全部工具。
9. **完整溯源链。** UI 应能回答“哪条事件、命中哪条规则、谁授权、哪个 Worker、做了什么、产出是什么”。
10. **Prompt/Policy 版本化。** 让历史行为可以对应到当时使用的规则和提示词。

### 应当规避

- 不要直接复制其完整领域模型；WorkPivot 先保留 Event、Grant、WorkItem 三层即可。
- 不要把 DSH Alpha Session 生命周期当作 WorkPivot 的业务生命周期。
- 不要把 Provider 默认凭据或操作者 OS 用户权限交给 Worker。
- 不要让多个 Agent 仅通过聊天记录协调，必须有服务端事实来源和幂等队列。
- 不要为了“多 Agent”给每个问题都拆角色；清晰职责不足时，多 Agent 只会放大噪音与成本。
- 不要自动开放推断权限；必须保留影子运行、人工抽查和回退开关。

### 与 WorkPivot 的结合机会

| WorkPivot 现有方向 | 可叠加的借鉴 |
| --- | --- |
| 项目 → 任务 → 运行 → 成果 | 在任务前增加 Event/Grant，在运行后增加 Assignment/Report |
| 任务授权快照 | 对齐 Mandate 的策略版本、作用域、强度和来源证据 |
| 文件版本与成果验收 | 让 Worker 产物通过版本与验收器进入交付，而不是自报完成 |
| 私有化与多用户 | Router 可以模型化，Worker 必须进入服务端受控执行面 |
| 记忆、证据与冲突确认 | 将 Trigger、Decision、Policy 和 Prompt 版本作为证据链节点 |
| 多 Runtime | 统一为 WorkItem 调度，不让 Runtime 直接拥有业务任务 |

### 差异化机会

该原型没有解决 WorkPivot 最关心的多用户、RLS、文件权限、Office/PDF 成果闭环、租户隔离和可审计企业部署。WorkPivot 可以吸收其控制面思想，但保留更强的组织权限、文件版本、隔离执行和成果验收能力。
