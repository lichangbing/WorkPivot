## R002 授权卡 AI 风险解读：高危操作前由 AI 分析「为什么做/有什么影响」再让用户确认

**一句话场景**：触发高危/界外授权卡时，除了干巴巴的命令与路径，由 AI 先给一段通俗的风险解读——模型为什么要做这个操作（意图上下文）、这个操作会带来什么影响（波及面/不可逆性/数据风险）——用户带着足够信息做确认，而不是凭感觉点「允许」。

**来源**：用户 2026-09-07 在千问（Qwen）上看到该实现，体验评价「非常好」，要求记录。

**现状差距**：授权卡目前只展示工具名/命令/路径/原因一句话（如「命令引用任务目录之外的路径」），普通用户难以判断风险实质。

**设计要点速记**（登记时初步分析，排期后补正式调研）：

1. **触发时机**：高危命令（bypass-immune 命中）与界外路径访问的授权卡，生成前先调一次轻量分析（可要求走同供应商的低档模型/短输出，控制成本与延迟）
2. **分析三要素**：① 意图——结合最近对话上下文说明「为什么需要这个操作」；② 影响面——会读/改/删什么、波及哪些路径、是否可逆；③ 风险点——最坏情况的后果与缓解建议（如建议先备份）
3. **边界纪律**：分析文本只是参考信息，不得替代权限判定；AI 建议放行不能自动放行（引擎判定不变）；分析本身也不得包含敏感文件内容，只引用路径与命令
4. **降级策略**：分析调用失败/超时（如 3s）直接展示现有卡片，不阻塞确认流程
5. **UI**：授权卡加「AI 解读」折叠区，生成中显示骨架，完成后展开；用户可选全局关闭该功能（设置项）
6. **防诱导**：分析 prompt 需防御「对话内容诱导 AI 给出『此操作安全』结论」——明确要求如实评估，包括「模型自己也不确定」的表述

**实施记录**（2026-09-07，v0.1.1）：同供应商同模型短分析（20s 软截止，失败静默降级为无解读）；仅高危/界外卡触发；卡片先出、解读异步回填 `risk_analysis` 事件，前端折叠区渲染「AI 风险解读（仅供参考）」；eval/W2 断言覆盖。待决策项剩余：独立小模型/解读缓存/采纳率统计。

## R001 多空辩论：企业看多/看空双智能体对抗 + 裁判评分

**一句话场景**：针对同一个企业，看多（Bull）与看空（Bear）两个智能体进行回合制辩论，裁判智能体按 rubric 评分，最终产出结论报告。可推广到尽调、投资决策、方案评审等场景。

**设计要点速记**（2026-08-28 分析结论，详见登记时对话，排期后补正式调研文档）：

1. **编排器驱动的回合制**（LangGraph debate 模式），不用自由群聊（AutoGen 式）——可控、可评测、可复现
2. **公平性约束**：双辩手同模型、同参数、同令牌预算，仅立场 system prompt 不同；各自独立上下文，只见对方公开论点
3. **共享证据包**：对目标企业预建一次 RAG 检索/资料抓取，双方共用同一份；论点必须带证据编号引用，无据论点裁判扣分
4. **裁判是非锚定评分**：每维度先答锚定是非题再映射 1-5 分（防 LLM 印象分漂移，方法源自 OpenWorkBuddy 评测方法论）；输出结构化 JSON（维度分/逐论点裁定/胜方/置信度）
5. **产出报告**：论点对抗矩阵、共识点、不可调和分歧及其证据缺口、评分表——「分歧+证据缺口」比胜负更有决策价值
6. 护栏：整场共享 token 预算闸、轮次上限、裁判判「无新论点」提前收敛、转写落盘可回放

**可参考案例**：LangGraph 官方 debate 示例（辩手+裁判图编排）、AutoGen 群聊辩论、Multi-Agent Debate 论文（Du et al. 2023）、AgentVerse（观众投票变体）；本地已分析项目中 WorkBuddy 专家团（团队编排）、OpenWorkBuddy `delegate_to_team`（接力团队）与「AI 评委只判是否+来源收录」可借鉴。

**待决策项**（排期时定）：单裁判 vs 多裁判取中位；辩论过程是否直播可视化；辩手是否允许实时调用工具取证（MVP 建议仅用预建证据包）；是否支持人作为辩手/裁判参与。

## R003 联网搜索 web_search（已实现，未部署）

**一句话场景**：模型知道要查什么但不知道网址，先搜索拿到候选链接，再用 `web_fetch` 读正文。

**关键取舍**：只检索不读正文（避免整页塞上下文）；服务地址由管理员配置，模型只能改查询词；结果过滤内网/回环地址；搜索内容按不可信数据处理。同时补齐文件链路的 `web_fetch`。

**设计文档**：[联网搜索能力-20261024](../../架构/归档/能力/联网搜索.md)。

## R004 结构化提问 ask_user（已实现，待部署验收）

**一句话场景**：需求不明确时弹带选项的卡片，用户点选后作为新消息继续，而不是正文问一句然后停下。

**边界**：只用于澄清需求，不替代授权卡；同一轮最多一个待回答问题；本轮结束时不触发早停追问。

**实现**：`packages/server/src/database/ask-user.ts`；核心循环按 `Tool.endsTurn` 结束本轮（`packages/core/src/loop.ts`）；
事件以 `type=ask_user` 的 meta 事件持久化；前端 `DatabaseWorkspace` 渲染卡片，回答以 `[回答提问 <id>]` 前缀回传。
用例：`eval/R004-ask-user.mts`（5 项）。

**验收与接口**：[agent 工具面路线图 §3](../../架构/归档/运行时/智能体工具面路线图.md)。

## R005 子代理 delegate（已实现，待部署验收）

**一句话场景**：把独立、上下文长的子任务放进独立循环，父上下文只拿结论；比事后压缩更彻底。

**边界**：单层、同步、同一工作目录、同模型；子代理不能再 `delegate` 或 `ask_user`；并发调用串行化。

**实现**：`packages/server/src/database/delegation.ts`，在 `execution.ts` 按运行动态装配；子事件带 `delegateId` 转发；
子循环失败、超预算或取消都转成工具结果文本，不中断父任务。用例：`eval/R005-delegate.mts`（7 项）。

**验收与接口**：[agent 工具面路线图 §4](../../架构/归档/运行时/智能体工具面路线图.md)。

## R006 事件溯源会话与中断恢复（P1–P4 已实现，待部署验收）

**一句话场景**：进程崩溃、容器重启或发布滚动更新后，任务历史仍然合法（没有悬空的 tool_call），已发生的副作用不会被重放，用户可以点“继续”接着做。

**关键取舍**：只保证 at-most-once —— 已派发但结果未知的工具调用，恢复时补一条“结果未知”的合成结果，绝不重跑；续跑从检查点开始，不重放模型流。

**进度**：P1（对账+历史合法+标记中断）、P2（一键续跑，`POST /api/tasks/:id/resume` + 对话区"继续"）、P3（文件链路 `.workpivot/runs/<runId>/` 检查点与启动对账）、P4（`WORKPIVOT_AUTO_RESUME=1` 下的有限自动续跑，每任务 1 次）均已实现，`eval/R006-recovery.mts` 11 项通过；真实 `kill -9` 验收待部署新镜像后执行。

**设计文档**：[事件溯源会话与中断恢复-20261024](../../架构/运行时/事件溯源与中断恢复.md)。

## R007 对话记录入库（混合存储，已实现并部署）

**一句话场景**：聊天记录与任务元数据写 PostgreSQL，工作目录、上传件与成果文件继续留在磁盘；解决“聊得越久、任务越多，加载越慢”。

**关键取舍**：不切数据库链路（不把文件改成版本、不取消工作目录）；不迁移历史（可清空重装）；不把附件字节写库；不双写。

**设计文档**：[对话记录入库（文件链路混合存储）-20261024](../../架构/历史/对话记录文件链存储.md)。

**进度（2026-10-24）**：已实现并部署。消息与任务元数据都写 `chat` schema；为保留 `tasks.ts` 的同步 API（`filePolicy` 等同步回调依赖），元数据采用"启动预载内存视图 + 写入落 PG"：读走视图、PG 是重启后的唯一真值，chat 模式不再写 `task.json`/`transcript.jsonl`。转写分页（`before/limit`）、历史 200 条、降级（未配置走 JSONL、配置了连不上拒绝启动）均已验证；安装器 `--with-chat-store` 一键启用；本地栈已启用并完成容器内往返验收（`rows=2 seqs=1,2`）。已知取舍：元数据写为"视图立即生效 + 异步落库"，崩溃窗口内可能丢最后一次状态变更，消息逐条 await 不受影响。

## R008 多 agent 协作（❌ 不实施，2026-10-24 决策）

**结论**：不做。保留设计与调研作为参考，不进入排期。

**原因**：

1. 协作层本身不成熟——Codex 的多 agent 仍在 feature flag 后、默认只允许显式请求；Claude Code 的 swarm 是实验实现；OpenWorkBuddy 的“专家团”本质是提示词接力。
2. 收益未被证明——没有一家用评估说明“多 agent 比单 agent 更好”；评审团 + 裁判的 token 是单 agent 的 3–6 倍，质量提升未知。
3. 适用面窄——只在“多视角评审 / 多轮返工”这类特定任务上有意义，办公场景的多数需求（写作、分析、生成文档）用单 agent + 子代理足够。
4. 风险不对称——裁判容易趋同产出假共识，成本与延迟不可控，失败时用户更难理解发生了什么。

**保留**：子代理（R005，单层同步）已实现，继续作为上下文隔离手段；不扩展并行委派与团队协议。

**如果将来重启**：先做离线评估（20 个真实办公任务，单 agent vs 自我检查 vs Panel 盲评 + 成本对比），证明收益后再建，判据见 [设计文档 §11](../../架构/归档/运行时/多智能体协作.md)。
