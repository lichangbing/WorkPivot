# 用户交互与确认协议

> 状态：✅ 已实现并部署；RC.3 双客户端、故障恢复和真实模型任务门禁通过
> 适用：数据库持久化对话、Web、桌面端和手机端
> 对应需求：[PRD-02](../../产品/产品需求/产品需求-02-对话与任务.md)

> 2026-11-05：本地与正式环境均已部署 0.3.0 / schema v72。四类持久交互、单运行单阻塞项、计划修改、运行中请求相关性分流、后续队列、检查点恢复、资源范围增量扩展和客户端更新清单已上线。真实复杂办公质量仍按业务样本验收。

## 1. 目标

把 Agent 与用户之间的澄清、计划、动作授权和成果验收统一成持久化协议，解决四个问题：

1. Agent 能从资料确认的内容不重复询问。
2. 多步任务先形成可审阅、可修改的计划。
3. 高风险动作展示真实对象和影响，拒绝原因回传模型。
4. 等待状态可跨端恢复，停止、超时和重启不产生悬挂任务。

## 2. 四类交互

| 类型 | 权威数据 | 阻塞 | 终态 |
|---|---|---|---|
| `clarification` | `workpivot.interactions` | 是 | 已回答、过期、取消 |
| `plan_approval` | `workpivot.run_permissions` + `workpivot.task_plans` | 是 | 批准、拒绝、过期、取消 |
| `action_permission` | `workpivot.run_permissions` | 是 | 本次允许、拒绝、超时、取消 |
| `artifact_review` | `workpivot.interactions` | 否 | 验收通过、退回、过期、取消 |

所有交互使用同一个 `InteractionEnvelope` 事件形状，包含：

```text
id / kind / userId / taskId / runId / revision
state / blocking / risk / reason / payload / response
createdAt / expiresAt
```

旧 `ask_user` 和 `permission_request` 事件继续发送，供旧客户端兼容；新客户端只使用 `/api/tasks/:id/interactions` 的统一列表，避免重复渲染。

## 3. 持久化与并发

### 3.1 一致性

- 澄清和成果验收写入 `workpivot.interactions`。
- 动作与计划审批继续由 `workpivot.run_permissions` 作为权威表；统一接口在读取时合成交互信封。
- 计划文档写入 `workpivot.task_plans`，每次修改生成新 revision 和 SHA-256 哈希。
- 同一运行最多一个 `pending + blocking` 澄清/验收交互；动作授权继续由环境索引保证单待处理。
- 回答和决策使用任务行锁；重复相同响应幂等，不同响应返回 409。

### 3.2 失效

以下任一变化使旧批准失效：

- 计划 revision 或 hash 改变；
- 工具、参数或调用摘要改变；
- 文件版本、记忆层或自动化范围改变；
- 运行中范围扩展会撤销旧计划和所有待处理/已批准未消费动作；
- 任务停止、执行租约过期或服务重启；
- 用户修改范围或更换任务。

## 4. 执行流程

```text
用户消息
  → 读取任务、资料、知识、记忆和业务事实
  → 有用户专属阻塞歧义：批量澄清
  → 复杂任务：update_plan → 计划审批
  → 首个副作用：核对计划 revision
  → 高风险动作：逐次动作授权
  → 执行并记录工具派发/结果
  → 登记成果并机器核验
  → 必要时成果验收
  → 完成、退回或停止
```

### 4.0 运行中补充与纠正

任务为 `running` 或等待用户时，消息接口不再把它当作第二个并发运行，而是写入 `workpivot.run_steering_messages`：

1. 用户消息立即持久化，状态为 `pending`，Web/桌面/手机同步显示；
2. 不在任意位置直接插入模型消息，避免破坏 `assistant(tool_calls) → tool_result` 结构；
3. 模型当前流式输出结束后、派发工具前检查一次；若存在新要求，丢弃本条模型提出的旧工具调用并重新采样；
4. 工具批次全部完成并写入检查点后再次检查，并由轻量关系路由判断消息与当前任务是否相关；
5. `related`：作为最新普通用户消息加入当前上下文，更新目标/约束，必要时调用 `update_plan` 并撤销旧批准；
6. `unrelated`：标记为 `deferred`，不进入当前模型上下文；当前运行正常完成后，系统取队首请求自动开始下一轮；
7. 相关性模型失败时，明确“另外/新任务/完成后再做”进入后续队列，其余默认按当前纠正处理；
8. 已应用记录为 `applied` 和真实用户事件；待分类或排队记录可撤销为 `cancelled`；
9. 显式停止时取消待分类和后续队列；服务崩溃时保留，续跑的新运行会重新分类并接管。

运行中新增文件版本或记忆层走独立范围扩展接口，不在任意位置直接改范围。服务端使用 `baseRunId + baseEpoch` 防止跨页面覆盖，要求 `requestId` 幂等，只允许增加，不允许在当前运行中缩减或切换既有范围。范围变更会撤销旧计划和待处理审批，并在下一安全步骤要求模型重新读取资料、核对结论和必要时重新规划。

当前运行不支持热启用专家：专家提示、经验和工具集在运行开始时固定。用户需要启用专家或缩小范围时应停止当前运行后重新配置；界面不会把仅修改标记误报为当前轮已生效。

### 4.0.1 检查点与恢复

数据库会话在每次工具批次完成后保存：

- 完整 `model_messages`；
- 已用步数和步数上限；
- 工具派发与结果状态；
- 未应用运行中补充。

租约过期后，恢复流程把运行标记为 `interrupted`，为未闭合工具调用补“结果未知”，已派发副作用绝不重放。用户继续时创建新运行，从最近检查点继承上下文和剩余预算，并应用崩溃前尚未应用的补充要求。文件链路也使用对应检查点，但恢复能力以当前数据库运行链路为主。

### 4.1 澄清

`ask_user` 一次接收 1-3 个问题。每个问题支持：

- 2-6 个选项；
- 单选或多选；
- 最多一个推荐项；
- 选项说明和短预览；
- 自由输入。

回答按问题 ID 校验完整性和选项有效性。旧单题字段保留兼容。

### 4.2 计划

计划字段：

```text
goal / assumptions / dataScope / businessRules / steps
externalActions / outputs / risks / verification
```

进入审批前必须至少包含目标、读取范围、步骤、成果和验收方式。简单任务直接执行时，服务端会根据当前请求、已选范围和真实工具补成最小可审阅计划，不允许无计划副作用。

用户可以编辑计划。编辑会保存新 revision，并拒绝旧动作许可，Agent 收到修改内容后必须按新版重新请求审批。

### 4.3 动作授权

风险矩阵由服务端根据工具声明和真实参数计算：

| 等级 | 示例 | 策略 |
|---|---|---|
| 低 | 任务内只读 | 默认允许 |
| 中 | 受控写入、普通网页读取、隔离执行 | 按执行模式确认 |
| 高 | 外部发送、共享、发布、删除、覆盖、MCP、网页提交 | 每次确认，无永久豁免 |

拒绝原因写入运行授权记录并回传模型。核心循环记住“工具 + 规范化参数”的拒绝摘要，完全相同的调用不会再次请求授权；模型必须修改参数或路线。

### 4.4 成果验收

- 成果工具成功后才创建验收交互。
- `machineVerified` 仅表示成果已登记并通过基础完整性检查，不代表业务正确。
- 验收通过只结束交互；退回时必须填写原因，并以新运行继续修改。

### 4.5 请求交付状态

运行状态与用户可见交付分开：

```text
运行：accepted / running / waiting_user / stopping
      completed / interrupted / failed / stopped

交付：not_visible / acknowledged / delivered / blocked
```

- `not_visible`：请求已持久化，但还没有非空助手正文；前端显示“已接收，正在准备”。
- `acknowledged`：已有持久化可见正文，任务仍可能继续。
- `delivered`：完成且已有最终可见正文。
- `blocked`：等待用户、已中断、失败、停止，或完成但没有生成可读答复。
- 工具调用、思考过程、用户消息本身不推进“可见交付”。
- 交付状态从现有运行、事件和续跑链投影，不复制正文，也不新增业务事实表。
- “继续”产生的运行通过 `resumed` 元事件归回原请求；原请求不会因续跑而生成一个无关的新状态。
- 系统必须保证刷新、换设备和重启后仍能从持久状态恢复，而不是依赖最后一次 SSE 推送。

## 5. API

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/tasks/:id/interactions` | 统一待处理列表、阻塞数和队列数 |
| POST | `/api/tasks/:id/interactions/:interactionId/respond` | 回答澄清、批准/拒绝计划、动作、成果验收 |
| GET | `/api/tasks/:id/permissions` | 旧动作授权兼容接口 |
| POST | `/api/tasks/:id/permissions/:permissionId` | 旧动作决策兼容接口 |
| GET | `/api/tasks/:id/plan` | 读取最新计划 revision |

任务 SSE 的 `state` 事件同时携带统一交互列表。Web 和手机都从持久列表恢复，不依赖某次 SSE 推送是否在线。

## 6. 提示分层

系统提示拆为：

1. 稳定交互规则：先查再问、澄清/计划/授权边界、拒绝不可原样重试；
2. 办公成果规则：Word、Excel、PPT、PDF 分别核验；
3. 动态状态：执行模式、记忆层、是否存在计划、是否声明外部动作；
4. 工具说明：参数、副作用和适用范围靠近对应工具。

稳定前缀不随单个任务资料变化，便于缓存、快照测试和定位行为回归。

## 7. 灰度与回退

服务端环境变量：

```text
WORKPIVOT_INTERACTION_CLARIFY_V2
WORKPIVOT_INTERACTION_PLAN_APPROVAL
WORKPIVOT_INTERACTION_PERMISSION_PREVIEW
WORKPIVOT_INTERACTION_ARTIFACT_REVIEW
```

取值为 `0` 或 `off` 时关闭对应能力。旧 `ask_user` 与 `run_permissions` 通道保留。回退前应取消待处理交互，不能让任务静默悬挂；已批准但未消费的动作许可在停止或范围变化时统一失效。

## 8. 验证

| 层 | 覆盖 |
|---|---|
| 单元 | 问题批量、多选、推荐、计划完整性、风险矩阵、拒绝重试 |
| PostgreSQL | 计划 revision、单阻塞约束、幂等回答、反馈持久化、成果验收 |
| HTTP | 统一列表、动作拒绝接口、跨端状态 |
| Web | 计划修改、队列、高风险反馈、成果验收、窄屏结构 |
| 移动端 | 与 Web 共用事件协议，类型检查和移动构建通过 |
| 固定任务集 | 预算 Excel、合同 Word、项目 PPT、调研 PDF、知识整理、业务事实、网页采集、外发共享 |

正式发布门槛：高风险漏确认、旧授权复用、拒绝原样重试、悬挂交互均为 0；手工模式完成至少 20 个合成办公任务和 5 个真实业务形态任务。
