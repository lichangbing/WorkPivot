## 背景

WorkPivot 同时包含浏览器 UI、桌面外壳、Agent 编排、HTTP/SSE 服务、数据库访问、工具协议和执行器客户端。早期产品需要快速形成端到端竖切，并保持 Web 与桌面端共享类型和行为边界。

候选方向包括：

1. TypeScript + Node.js 全栈。
2. Python/FastAPI 服务端 + TypeScript 前端。
3. Java/Spring Boot 服务端 + TypeScript 前端。
4. 多语言拆分，按 Agent、API、前端分别选栈。

## 决策

采用 **TypeScript + Node.js 22**：

- pnpm workspace 管理共享包和应用。
- React + Vite 构建 Web 管理端和用户端。
- Electron 承载桌面壳；Capacitor 作为移动端方案。
- HTTP/SSE、Agent 编排、数据库访问和桌面桥接保持同一语言生态。
- 共享类型和协议定义放在 `packages/shared`，前端只通过 HTTP/SSE 访问服务端。

## 理由

- 大幅降低前后端协议、工具参数和事件类型漂移。
- 同一运行时可以快速实现流式 SSE、MCP、浏览器和容器 Worker 客户端。
- Node 22 与现有办公文档、前端工具生态兼容，适合小型团队维持全链路交付。
- TypeScript 允许用 `tsc`、ESLint 和依赖边界规则形成机器可检查的约束。

## 后果

### 正面

- 端到端迭代和原型验证速度快。
- 运行、工具、记忆和成果模型可共享类型。
- 桌面、Web、移动端可复用大部分交互与协议层。
- 团队只需维护一套主要语言和构建链。

### 代价

- Node 原生 CPU 密集任务不适合放主进程，必须交给 Worker/容器。
- 超大型后端需要明确的模块边界，避免所有业务堆进单一服务。
- Office、OCR、浏览器等能力必须通过独立执行服务或明确依赖实现。
- TypeScript 类型校验不能替代运行时输入验证和权限检查。

## 约束

- 所有外部输入必须做运行时校验。
- 前端禁止导入服务端内部模块，通信只经 HTTP/SSE。
- 命令、Python、LibreOffice 等执行能力不得在服务进程内无隔离运行。
- 数据库 schema、API、Worker 协议和前端按兼容版本配套发布。
- 关键协议变化时必须同步共享类型、测试和文档。

## 未选择的方案

- **Python 服务端**：数据和 AI 生态强，但当前 UI、桌面、工具和协议代码会形成双语言边界，增加小团队维护成本。
- **Java 服务端**：适合大型企业服务，但早期竖切与流式 Agent 迭代成本偏高。
- **多语言按域拆分**：当前规模不足以抵消部署、类型同步和调试成本；出现独立容量或算法边界后再评估。

## 复核触发条件

- Node 主进程成为持续性能瓶颈，且 Worker 拆分仍无法解决。
- 团队和组织边界导致前后端无法共享维护节奏。
- 合规或供应链要求必须替换运行时。
- 单服务无法满足多实例、高并发或独立发布需求。
