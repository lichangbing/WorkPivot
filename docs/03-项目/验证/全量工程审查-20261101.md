## 4. 性能热点

### P-01：模型流式输出的每个事件都查询两次数据库

- **级别**：P1
- **证据**：`database/runtime.ts` 的 `for await (const event of client.streamChat(...))` 内，每个流事件都调用 `suggestions.epoch(actor)` 和 `businessFacts.epochForTask(actor, taskId)`。
- **影响**：一次长回答可能产生数百到数千次数据库事务，拖慢流式响应、占用连接池，并放大审计与日志压力。
- **建议**：在工具派发前、工具结果后和最终收尾前检查版本；或按时间窗口/事件数量节流。保持“发现变化立即中止”的语义。

### P-02：请求审计导致每个 API 请求重复鉴权和双写

- **级别**：P1
- **证据**：
  - `requestAudit` 先调用 `accounts.resolve(token)`；
  - 后续认证中间件再次调用 `accounts.resolve(token)`；
  - 每个请求先写 `request_audit`，响应结束再写 `request_audit_results`。
- **影响**：一次普通 API 请求至少多出一次身份事务、两条审计写入。结合前端轮询和 SSE 重连，会显著增加数据库写放大。
- **建议**：认证中间件先执行，审计复用 `res.locals.user`；读轮询可按操作聚合，不逐请求写两条记录；登录、权限、写操作和外部调用保留完整审计。

### P-03：自动化列表存在 1+N 查询

- **级别**：P1
- **证据**：`database/automations.ts` 先取最多 200 个计划，再逐计划查询最后一次运行。
- **影响**：最坏约 201 次数据库往返；自动化页面每 5 秒刷新一次。
- **建议**：用 `LEFT JOIN LATERAL` 或 `DISTINCT ON` 一次返回最后运行，目标固定为 1 次查询。

### P-04：业务事实列表最坏执行约 12 万次对象配对

- **级别**：P1
- **证据**：`database/business-facts.ts` 对最多 500 个对象执行双重循环并计算相似度。
- **影响**：单次打开项目业务事实面板可能很慢，对象增长后近似二次增长。
- **建议**：按对象类型分桶；先用名称、别名、标识符前缀和长度差缩小候选；只在候选集中运行相似度；长期模糊匹配使用 PostgreSQL trigram/索引。

### P-05：哈希静态资源被设置为 `no-store`

- **级别**：P1
- **证据**：数据库服务在全局中间件设置 `Cache-Control: no-store`，之后才挂载 `express.static`。
- **影响**：Vite 生成的带哈希 JS/CSS 每次刷新都重新下载，浪费带宽并拉长加载时间。
- **建议**：API、HTML、下载继续 `no-store`；`/assets/*` 使用内容哈希对应的长期 `immutable` 缓存。

### P-06：主界面存在多个独立高频轮询

- **级别**：P2
- **证据**：
  - `DatabaseArtifacts` 每 3 秒刷新，主界面同时挂载“上传资料”和“产物”两个实例；
  - `DatabaseAutomations` 每 5 秒刷新三个接口；
  - `DatabaseEmbeddings` 每 5 秒刷新且未防重叠；
  - `ConnectionStatus`、`DatabaseModelStatus`、`DatabaseExecutionStatus`、`TaskSidebar` 等仍各自维护定时器。
- **影响**：叠加工作区 SSE 和请求审计后，形成持续数据库/网络压力。
- **建议**：统一可见性轮询或事件驱动；列表更新优先复用工作区 SSE 通知，低频兜底而不是高频全量拉取。

### P-07：过程区重复解析和重复遍历

- **级别**：P2
- **证据**：`DatabaseTurnProcess.tsx` 每个步骤重复过滤事件计算统计；每条工具结果反复 `JSON.parse`；检索状态同一条内容计算两次。
- **影响**：流式更新时常驻浏览器主线程，长任务过程区容易卡顿。
- **建议**：用 `useMemo` 从事件数组一次性生成展示模型，保存统计、工具元数据和解析结果。

### P-08：后台调度按用户串行扫描所有队列

- **级别**：P2
- **证据**：`database/runtime.ts` 中记忆、专家、恢复、解析、索引、向量和浏览器登录回收分别运行定时器；多数按所有启用用户逐个 `await`。
- **影响**：单用户影响小，小团队扩展后会形成多个固定频率的全用户扫描。
- **建议**：先查询全局待处理队列，再按 `SKIP LOCKED` 分派；合并相近调度的数据库扫描；增加队列长度、等待时间和失败次数指标。

### P-09：工作区启动存在 REST 与 SSE 快照重复

- **级别**：P2
- **证据**：`DatabaseWorkspace` 登录后请求任务/项目，同时工作区 SSE 首条事件再次发送完整快照。
- **影响**：重复查询和传输，任务变多后会放大。
- **建议**：明确一个首屏主数据源，另一条只做失败兜底；或者给 SSE 增加版本协商，避免重复快照。

## 5. 可维护性

### M-01：两套主界面和成果组件并行

- **级别**：P2
- **证据**：`App.tsx` 约 1300 行，仍保留文件链路界面；PostgreSQL 主链路使用 `DatabaseWorkspace.tsx`；`TaskSidebar`、`ArtifactBrowser`、`DatabaseArtifacts` 提供不同成果入口。
- **影响**：权限、版本、轮询、删除和同步逻辑容易在两条链路漂移。
- **建议**：标记 Legacy 入口；把 PostgreSQL 链路作为唯一主实现，抽取共享成果、任务和设置组件。

### M-02：核心文件过大

- **级别**：P2
- **证据**：`business-facts.ts` 约 92 KB；服务端 `app.ts` 约 76 KB；`AdminApp.tsx` 约 57 KB；`DatabaseWorkspace.tsx` 约 46 KB。
- **影响**：单文件承载数据访问、校验、业务编排和 UI，审查范围大，冲突概率高。
- **建议**：跟随具体性能和功能改造按职责拆分，不为行数单独做一次性大重构。

### M-03：旧四档类型仍保留在现行代码里

- **级别**：P2
- **证据**：`permissions.ts` 的 `Tier` 仍包含 `readonly/workdir`，但界面和 API 只有 `ask/auto`。
- **影响**：类型系统无法阻止后续新代码重新使用废弃值。
- **建议**：保留只读兼容类型，业务接口统一两值类型；旧值只在迁移入口解析。

### M-04：后台异常多处静默吞掉

- **级别**：P2
- **证据**：运行时调度、轮询组件和恢复任务大量使用空 `catch`。
- **影响**：符合不输出敏感内容的原则，但缺少失败计数和原因分类，长期运行可能静默失败。
- **建议**：只记录固定错误类别、作业 ID、重试次数和耗时；增加健康指标。
