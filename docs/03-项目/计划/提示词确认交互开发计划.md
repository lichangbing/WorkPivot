## 1. 为什么现在做

Claude Code 是 Coding Agent，不是办公 Agent。它的价值不在于让办公任务“多问几句代码问题”，而在于以下系统设计：

1. 把用户模糊需求转成结构化选择；
2. 在复杂执行前形成可审批的计划；
3. 在具体副作用发生前展示动作和影响；
4. 拒绝后把原因反馈给 Agent 并改变后续行为；
5. 将等待用户的时刻作为显式状态，可通知、超时、取消和恢复。

WorkPivot 面向 Office/PDF、项目知识、业务事实和外发协作，误操作后果与 Coding Agent 不同。尤其需要保护的是：

- 错误数据范围进入模型；
- 业务数字和口径未经确认即交付；
- 文件版本被覆盖或半成品被发布；
- 网页填写、邮件/聊天发送等动作造成隐私外泄；
- 多个确认来源互相覆盖或重复提示。

## 2. 当前基线

### 2.1 已具备

| 能力 | 当前实现 |
| --- | --- |
| 结构化提问 | `database/ask-user.ts`，带选项并结束本轮 |
| 任务计划 | `update_plan`、`plan_update`、计划回显 |
| 计划闸门 | 确认模式下，首个写入/执行动作前请求一次 `plan` 授权 |
| 工具授权 | `tool-authorization.ts` 绑定规范化参数摘要，执行前复核 |
| 等待状态 | 权限请求使任务进入 `waiting`，支持超时、取消和重启后查询 |
| 前端卡片 | Web/移动端已有待确认操作和待回答问题区域，高危动作附 AI 风险解读 |
| 审计 | 工具调用、授权、拒绝和策略事件持久化 |

### 2.2 主要缺口

| 缺口 | 现状 | 影响 |
| --- | --- | --- |
| 提问没有持久交互对象 | `ask_user` 发一个事件，回答作为普通消息回传 | 难以统一等待、幂等、超时、恢复和多端同步 |
| 单轮只能问一个问题 | 不能批量收集一组相关决策 | 多轮往返增加注意力成本 |
| 选项能力不足 | 无推荐标记、多选、预览 | 用户难以比较模板、结构和业务方案 |
| 计划审批内容太泛 | 只显示“确认执行计划” | 用户看不到目标、数据范围、步骤、风险和验收 |
| 计划审批不能修改 | 只能近似允许/拒绝 | 用户要拒绝后完整重述，容易丢失决策 |
| 拒绝缺少反馈 | 权限决策主要是布尔值 | Agent 只能收到“未授权”，容易换路重试 |
| 授权范围粗 | 当前基本按一次授权处理 | 重复打断，或为省事扩大到过宽范围 |
| 风险分类分散 | 工具 kind、网络列表和提示文字分别判断 | 不同工具与自动化的风险口径可能漂移 |
| 提示规则未分层 | 系统规则、任务状态和动态上下文连续拼接 | 难缓存、难评测、难定位哪条规则导致多问或少问 |
| 缺少确认质量指标 | 有调用日志，但没有“打断成本/返工收益”基线 | 无法判断优化是否真正减少用户负担 |

### 2.3 会话存储边界

本计划只考虑**交互会话保存在数据库**的部署：

- 会话、运行、消息、计划、授权和交互状态以数据库记录为权威来源；
- Web、桌面和移动端通过同一 API/SSE 读取和恢复；
- 支持多端同步、运行栅栏、权限复核和断线恢复；
- 不修改、也不以本地持久化会话的行为作为验收前提。

协议设计保持存储无关；未来若需要支持本地会话，可以新增适配器，但不在本计划内实现。

## 3. 目标与非目标

### 3.1 目标

1. 用户只在真正需要其决定时被打断。
2. 澄清、计划、动作和成果四类确认在协议和 UI 上不混用。
3. 每个待确认项绑定用户、任务、运行、revision 和过期时间。
4. 用户可查看具体影响，可修改、批准、拒绝并附带反馈。
5. 批准内容发生变化后旧批准自动失效。
6. 拒绝、超时、断线、重启和重复点击均不会静默卡死或重复执行。
7. 用固定办公任务集量化确认收益和打扰成本。

### 3.2 非目标

- 不复制 Claude Code 的源码、Prompt、React 组件或权限匹配实现。
- 不为每个工具都增加弹窗。
- 不让另一个分类模型替代服务端权限判定。
- 不在本次实现 Agent 自主改写用户 Prompt。
- 不在本次实现“预测用户下一句”的 Prompt Suggestion。
- 不重启多 Agent 协作项目。
- 不改变现有高风险动作的最低授权要求。

## 4. 目标交互架构

```text
用户请求
  ↓
读取现有任务/资料/记忆，先自行消除可查歧义
  ↓
仍有用户专属且阻塞的歧义？
  ├─ 是 → Clarification
  └─ 否 ↓
复杂、多步或高影响任务？
  ├─ 是 → Plan Proposal → Plan Approval
  └─ 否 ↓
执行
  ↓
即将产生外部/高风险副作用？
  ├─ 是 → Action Permission
  └─ 否 ↓
机器核验成果
  ↓
需要业务验收？ → Artifact Review
  ↓
交付 / 修改 / 停止
```

### 4.1 统一交互协议

建议在 shared/core 层增加稳定的判别联合类型，具体持久化可按现状分适配器实现：

```ts
type InteractionKind =
  | 'clarification'
  | 'plan_approval'
  | 'action_permission'
  | 'artifact_review'

interface InteractionEnvelope {
  id: string
  kind: InteractionKind
  userId: string
  taskId: string
  runId: string
  revision: number
  state: 'pending' | 'answered' | 'approved' | 'denied' | 'expired' | 'cancelled'
  blocking: boolean
  risk: 'low' | 'medium' | 'high'
  reason: string
  payload: unknown
  response?: unknown
  createdAt: string
  expiresAt: string
}
```

第一阶段**统一协议和 UI，不强推把所有交互塞进一张新表**：

- `run_permissions` 继续作为动作授权的权威表；
- 澄清和计划审批在数据库会话中新增持久记录；
- 服务层用适配器统一生成事件和响应；
- 后续数据量证明需要时再合并存储，避免当前高风险迁移。

### 4.2 何时问、何时不问

| 场景 | 默认行为 |
| --- | --- |
| 可从当前资料、知识、记忆或业务事实得到答案 | 自主读取，不问用户 |
| 低风险且可逆，存在合理默认值 | 采用默认值，明确记录假设并继续 |
| 用户偏好、业务口径、模板、范围、验收标准缺失 | 批量提出 1-3 个结构化问题 |
| 任务预计 ≥3 步、影响多个成果或存在多种合理路线 | 生成计划并请求审批 |
| 普通确认模式中的可逆写操作 | 执行计划建立并确认后再开始 |
| 外部发送、网页提交、共享、发布、删除 | 在执行前进行动作确认 |
| 已批准计划中的同类低风险动作 | 不重复逐次确认 |
| 自动化或后台运行且无法交互 | 只执行事先明确授权范围；超范围则停止 |

原则：

> 澄清可以合并，审批必须明确；信息能从资料得到的不问，高风险动作不能跳过。

## 5. 开发任务

### 5.1 阶段 A：协议和澄清（预计 3-4 人日）

#### PC-01 产品规则与竞品边界落文

- **落点**：PRD-02 §7、任务授权与安全边界、竞品主卡。
- **交付**：
  - 定义四类交互及其互斥关系；
  - 定义何时可以假设、何时必须问；
  - 定义办公任务计划必填字段；
  - 明确 Claude Code 的 Coding Agent 定位与不可迁移边界。
- **验收**：文档检查通过；产品、研发、测试对“澄清不是授权、计划不是动作授权”形成同一口径。
- **依赖**：无。

#### PC-02 统一交互事件与状态

- **落点**：`packages/shared` 或 `packages/core` 类型定义；`packages/server/src/database/execution.ts`、`app.ts`。
- **交付**：
  - 新增 `InteractionEnvelope` 和兼容现有 `permission_request/ask_user` 的事件协议；
  - 每个交互至少绑定 `userId/taskId/runId/revision/expiresAt`；
  - 回答、批准、拒绝、超时、取消均可幂等处理；
  - 同一运行只允许一个阻塞交互，其余进入有序队列；
  - 断线后可从持久状态恢复，不依赖 SSE 连接内存。
- **验收**：
  - 重复提交同一次回答不产生两条业务事件；
  - 跨任务/跨用户伪造交互 ID 被拒；
  - 停止、过期、重启后没有悬挂 Promise；
  - 现有授权事件和 API 向后兼容。
- **依赖**：PC-01。

#### PC-03 `ask_user` v2

- **落点**：`packages/server/src/database/ask-user.ts`、`packages/core/src/loop.ts`、Web/移动端确认区。
- **交付**：
  - 单轮支持 1-3 个相关问题，每个问题 2-4 个选项；
  - 支持推荐项、互斥单选、多选、说明、可选预览和“其他”；
  - Agent 不能生成“其他”，由 UI 自动提供；
  - 问题结束后任务进入 `waiting`，回答保存为结构化事件；
  - 回答批次作为一条工具结果回填，防止重复追问；
  - 明确禁止用 `ask_user` 询问执行权限或“计划是否可开始”。
- **验收**：
  - 单题、多题、多选、自由输入、预览和长文本边界；
  - 重复调用、重复点击、刷新、断线恢复；
  - 能从资料得到的答案不提问；
  - 移动端和 Web 键盘可操作；
  - 未回答时任务不提前显示完成。
- **依赖**：PC-02。

### 5.2 阶段 B：计划审批（预计 3-4 人日）

#### PC-04 办公任务计划模型

- **落点**：Plan 工具与持久化状态；任务/运行 API；PRD-02。
- **建议结构**：

```text
goal
assumptions
dataScope
businessRules
steps[]
externalActions[]
outputs[]
risks[]
verification[]
```

- **交付**：
  - 计划有稳定 `planId + revision + hash`；
  - 计划变化产生新 revision，旧批准自动失效；
  - 计划明确区分“将读取什么、将生成什么、将对外做什么”；
  - 敏感原始参数不进入长期转写，UI 使用受控摘要。
- **验收**：缺少数据范围、成果目标或验收方式的计划不能进入审批；revision/hash 变更后旧批准不能复用。
- **依赖**：PC-02。

#### PC-05 `plan_approval`

- **落点**：`database/plan-gate.ts`、`database/execution.ts`、Web/移动端计划卡。
- **交付**：
  - 首次写入/执行动作前展示计划，而不是泛化“确认执行计划”；
  - 支持批准、请求修改、拒绝并反馈；
  - 用户修改后的计划作为新 revision，并回传给 Agent；
  - 批准绑定计划 hash、资源范围和运行栅栏；
  - 自动模式仍对高风险动作保留动作级确认。
- **验收**：
  - 只读阶段不弹计划卡；
  - 首次副作用前弹一次；
  - 用户修改计划后 Agent 使用修改版；
  - 计划修改、资料范围变化、运行重启后旧批准失效；
  - 拒绝后模型收到明确原因并停止原路线。
- **依赖**：PC-04。

### 5.3 阶段 C：动作授权与反馈（预计 3-4 人日）

#### PC-06 统一风险矩阵

- **落点**：`execution-policy.ts`、`tool-policy.ts`、`plan-gate.ts`、`runs.ts`。
- **风险级别**：

```text
low       任务范围内的只读、可逆本地操作
medium    受控写入、隔离执行、普通网页读取
high      数据外发、共享发布、删除、覆盖、权限变更、生产操作
```

- **交付**：
  - 服务端根据工具声明和真实参数判定，不信任模型自述；
  - 同一规则同时用于手动/自动模式和自动化；
  - `high` 操作不得升级为永久豁免；
  - 所有数据库会话界面的文案、范围和审计字段一致。
- **验收**：风险矩阵表单测；绕过工具名称、修改参数、切换链路仍不能降低级别。
- **依赖**：PC-01。

#### PC-07 动作级确认内容

- **落点**：`ToolAccessRequest`、`runs.ts`、`App.tsx`/移动端确认卡。
- **交付**：
  - 展示具体对象和后果：文件版本及 diff、命令、URL/目标域、发送资料范围、输出目标、删除/覆盖影响；
  - 支持“仅此次”；
  - 只对安全、可归纳的动作提供“本任务内同类允许”；
  - 拒绝可填写反馈，并作为工具结果返回模型；
  - 被拒绝后提示模型不得原样重试，必须调整路径或停止。
- **验收**：
  - 用户无需展开原始 JSON 即可判断动作；
  - 参数、revision、URL、页面代次变化后旧授权失效；
  - 拒绝反馈在下一轮模型上下文中可见；
  - 高风险动作没有“永久允许”；
  - 审计不记录未脱敏秘密。
- **依赖**：PC-06。

#### PC-08 拒绝与改路闭环

- **落点**：`authorizeTools`、`runAgentLoop` 的拒绝工具结果。
- **交付**：
  - 拒绝结果包含操作未执行、原因和可调整方向；
  - 同一调用摘要不可自动重试；
  - 若模型重复同类越权动作，触发已有的循环/安全拦截；
  - 用户修正后重新审批，不复用旧许可。
- **验收**：脚本化模型先被拒、再尝试完全相同调用时被拦截；改变合法参数后可重新请求。
- **依赖**：PC-07。

### 5.4 阶段 D：Prompt、UI 与质量（预计 3-5 人日）

#### PC-09 提示规则分层

- **落点**：`buildSystemPrompt`、`executionGuidance`、工具描述和模式提示。
- **交付**：
  - 稳定段：角色、真实性、先读后改、调查优先、澄清/计划/授权边界；
  - 动态段：任务资料、记忆、执行模式、可用工具和当前计划；
  - 工具规则放在工具描述中，不全部堆入总 Prompt；
  - 办公输出约束按 Word/Excel/PPT/PDF 分别定义，不采用代码输出的词数锚点。
- **验收**：同任务在不同资料范围下可验证动态段变化；稳定前缀不因无关工具状态频繁变化；Prompt 规则不漏掉高风险确认。
- **依赖**：PC-01。

#### PC-10 前端统一确认区

- **落点**：拆分 `App.tsx` 中的确认渲染，形成独立 `InteractionDock`；Web/移动端复用协议。
- **交付**：
  - 澄清、计划、动作、成果四类卡片视觉和操作一致；
  - 同时最多一个阻塞项置顶，其余显示队列数量；
  - 支持键盘、屏幕阅读器、移动端软键盘；
  - 计划卡支持可编辑预览；
  - 拒绝反馈、过期、断线和已处理状态明确。
- **验收**：固定 Chromium 与移动端交互；同一事件重复推送不重复卡片；刷新后恢复；390px 布局无遮挡。
- **依赖**：PC-02、PC-03、PC-05、PC-07。

#### PC-11 评测与灰度

- **新增评测**：
  - `eval/interaction-clarification.mts`
  - `eval/interaction-plan.mts`
  - `eval/interaction-permission.mts`
  - `eval/interaction-recovery.mts`
  - `eval/interaction-ui.mjs`

- **固定办公任务集**：
  - 预算分析并生成 Excel；
  - 合同要点提炼并修改 Word；
  - 项目周报 PPT；
  - 调研报告导出 PDF；
  - 多来源知识整理；
  - 业务事实冲突确认；
  - 网页数据采集后写入成果；
  - 对外发送/共享前确认。

- **指标**：

| 指标 | 目标 |
| --- | --- |
| 可自行发现的信息仍向用户提问 | 0 |
| 高风险动作无确认执行 | 0 |
| 重复确认率 | 相比基线下降 ≥30% |
| 因确认不足导致的返工 | 不高于基线 |
| 授权修改参数后旧许可复用 | 0 |
| 拒绝后原样重试 | 0 |
| 任务完成率 | 不低于基线 |
| Web/移动端确认操作成功率 | ≥95% |

- **灰度开关**：

```text
interaction.clarify_v2
interaction.plan_approval
interaction.permission_preview
interaction.artifact_review
```

- **顺序**：
  1. 合成环境默认关闭，仅测试用户开启；
  2. 手工确认模式先开启；
  3. 收集至少 20 个办公任务基线；
  4. 再按任务类型开放自动模式中的同类允许；
  5. 任一高风险绕过、悬挂或重复执行即回退开关。

## 8. 验收门槛

### 8.1 工程验收

- 数据库迁移可升级、回退路径明确；
- Web、桌面、移动端类型检查和构建通过；
- 相关 ESLint、文档检查、许可检查通过；
- 既有 `R004`、M5 授权、O-16/O-17 和工具授权回归全过；
- 无凭据、业务正文或敏感参数进入长期事件/日志。

### 8.2 场景验收

- 需求可从资料消歧时不提问；
- 用户专属歧义一次批量问清；
- 多步任务计划可审阅、修改和拒绝；
- 计划变化后旧批准失效；
- 高风险动作前展示真实对象与后果；
- 拒绝原因进入下一轮模型输入；
- 重复点击、跨端点击、断线和重启不会重复执行；
- Office 最终成果必须通过机器核验后才进入成果验收。

### 8.3 发布门槛

- 手工确认模式至少完成 20 个合成办公任务；
- 选取 5 个真实业务形态任务完成 Web + 移动端联调；
- 高风险动作绕过数、重复执行数和悬挂交互数均为 0；
- 对比基线，在任务成功率不下降的前提下减少重复打断；
- 未完成真实模型验证前只标记“已实现/待验收”，不得标记生产完成。

## 9. 风险与回退

| 风险 | 控制 |
| --- | --- |
| 确认过多导致用户放弃 | 同类合并、低风险默认值、风险矩阵只拦截必要动作 |
| 计划审批拖慢简单任务 | 简单/可逆任务不进入计划阶段 |
| 用户修改计划后执行旧版 | 计划 hash/revision 绑定，变化即失效 |
| Agent 绕过拒绝 | 服务端每次执行前复核，拒绝后禁止同调用原样重试 |
| 断线造成悬挂 | 所有交互持久化，超时和停止都产生终态事件 |
| 移动端能力落后 | 先统一协议和组件能力，再分别渲染 |
| Prompt 规则越加越长 | 稳定/动态分层，工具规则靠近工具，设长度预算与快照测试 |
| 许可风险 | 只实现独立设计，不复制 Claude Code 代码、提示词或组件 |

回退策略：

1. 以 feature flag 关闭新交互，保留旧 `ask_user` 与授权链路；
2. 新表只追加，不修改旧记录语义；
3. 已产生的待交互在回退前统一取消并通知用户；
4. 不在运行中被回退清理的审批继续按旧版本安全默认拒绝。

## 10. 完成定义

本计划完成不等于“增加了一个更大的确认弹窗”，而是满足以下闭环：

```text
Agent 先自主消除可查信息
  → 只在关键歧义处问结构化问题
  → 复杂任务先审计划
  → 高风险动作展示具体影响
  → 用户拒绝可反馈、修改可继续
  → 所有等待可跨端、可恢复、可审计
  → 成果机器核验与必要业务验收分离
```

只有同时通过工程回归、办公场景评测和真实用户链路验证，才能把相关能力标记为生产完成。
