# 2026 AI 办公工作台与 Agent 参考项目格局

> 状态：✅ 统一结论
> 研究窗口：2026-08 至 2026-10
> 证据边界：商业产品来自公开文档与本机可观察行为；开源项目来自公开源码/文档。未复验的部分明确标为观察，不把推断写成事实。

## 1. 结论先行

2026 年的同类产品正在从“聊天机器人”向“可执行任务的 Agent 工作台”迁移，竞争重点从模型回答质量扩展到：

1. 能否操作真实文件并交付 Office/PDF。
2. 能否把会话、任务、工具和工作区组织成可恢复的运行。
3. 能否通过 Skill/MCP/专家扩展企业方法。
4. 能否在私有模型、企业权限和敏感数据条件下工作。
5. 能否让记忆、引用和自动执行可控、可纠错、可审计。

WorkPivot 的机会不在复制更多聊天功能，而在把“私有化、任务授权、证据、记忆纠错、成果闭环”做成一个一致系统。

| OpenAI Codex CLI | 开源 Agent | 终端/云 | 代码与工作区强 | 内置工具、skills、MCP | 工具面收敛、沙箱、恢复与上下文工程 | 偏开发场景，产品 UI 非办公工作台 |

| OpenClaw | 开源个人助理框架 | 自托管 | 个人助理与渠道 | Gateway、记忆、插件 | 通道生态、记忆/人设格式、运行时 | 非企业办公交付中心 |
| Hermes Agent | 开源自改进 Agent | 自托管 | 通用任务与多终端 | 技能自动生成 | 技能沉淀闭环、多执行后端 | 自动生成质量与审批策略需治理 |
| Pi Agent Harness | 开源 Agent 内核 | 嵌入式 | 依赖扩展 | 极简工具 + 动态加载 | 可嵌入、分层包、扩展 API | 不是完整企业产品 |
| DeepSeek Harness | 开源桌面 Agent | 本地桌面 | 开发者任务 | 548 个模块化包、Cordis | 事件溯源、子代理、持久 PTY | 单机/开发者导向，企业治理不足 |

## 3. 统一产品卡

### 3.1 WorkBuddy（腾讯）

| 字段 | 内容 |
| --- | --- |
| 定位 | 面向企业与个人团队的 AI 智能体工作台，以“下达任务、专家执行、交付文件”为核心 |
| 用户与形态 | 业务用户；桌面端、Web/云服务及企业协作入口 |
| 核心能力 | 多专家 Agent、文档/表格/PPT 生成、行业调研、Skills/连接器、企业版管控 |
| 技术观察 | 桌面或本地执行能力与云端 Agent 服务结合；扩展体系接近 Skill/专家/连接器组合 |
| 优势 | 产品叙事完整、办公任务覆盖面广、渠道与生态强、运行流程贴近业务交付 |
| 限制与风险 | 核心实现不公开；与厂商生态结合较深；私有化模型选择和审计边界需逐项确认 |
| 证据等级 | A/B：官方文档 + 本机产品与文件工作流观察 |
| 对 WorkPivot 的启示 | 保留“任务交付”心智；同时强化模型中立、任务授权和证据可追溯 |

专项证据：[产品分析](workbuddy.md)、[官方文档](workbuddy-official-docs.md)、[技术拆解](workbuddy-technical-analysis.md)、[扩展系统](workbuddy-extension-system.md)、[Office 证据](workbuddy-office-static-20261017.md)。

### 3.2 QwenWork / 千问办公（阿里）

| 字段 | 内容 |
| --- | --- |
| 定位 | 面向中文个人和团队的综合 AI 办公工作台 |
| 用户与形态 | 桌面优先，覆盖对话、任务、Office、浏览器自动化和技能市场 |
| 核心能力 | 本地 Agent CLI、Office 工作区、VM 沙箱、浏览器扩展、AgentSkills 技能生态 |

### 3.3 Claude Code（Anthropic）

| 字段 | 内容 |
| --- | --- |
| 定位 | 面向开发者和知识工作者的终端 Agent |
| 用户与形态 | 单用户/企业开发者；CLI、IDE 与企业集成 |
| 核心能力 | 工具循环、代码编辑、MCP、subagent、hooks、SKILL.md 与岗位技能包 |

| 优势 | Agent 交互成熟、技能格式影响力大、工具与上下文工程经验丰富 |
| 限制与风险 | 核心代码和部分文档技能不可复用；企业私有化与模型自由度有限 |
| 证据等级 | A：官方开放仓库和公开规格；核心内部行为为间接证据 |
| 对 WorkPivot 的启示 | 对齐有用格式，采用自研技能发布和权限控制；不复制专有内容 |

## 4. 对 WorkPivot 的产品取舍

### 应吸收

- 以任务和成果为中心，不把聊天长度当产品价值。
- 工具面保持精简，复杂能力通过 Skill/Worker 提供。
- 事件、工具派发和成果版本持久化，支持中断恢复。
- Skill 从使用经验中沉淀，但发布前必须试运行和用户确认。
- 记忆、引用和来源形成可回溯链路。
- 办公文件必须有结构检查和真实预览，不以“生成代码执行成功”代替质量验收。

### 应避免

- 为了覆盖竞品功能而扩大工具面和隐式权限。
- 将第三方 Skill 文本直接当系统指令或可信代码。
- 使用全局长期记忆混合不同项目的数据。
- 通过自动回退到宿主 shell 掩盖隔离服务不可用。
- 只写成功路径，不记录失败、取消、删除和恢复。
- 在许可未确认时复制竞品代码、技能内容或专有模板。

### 下一步研究

| 课题 | 目的 | 优先级 |
| --- | --- | --- |
| 真实企业用户访谈 | 验证行业、角色、数据合规和付费动机 | 高 |
| Office 复杂样版基线 | 建立可重复的视觉和业务验收集 | 高 |
| 企业身份与协作 | 评估 IAM、项目共享和撤权 | 中 |
| 模型成本与路由 | 比较本地模型和云模型的任务质量/成本 | 中 |
| 竞品版本复核 | 更新商业产品发布后的能力变化 | 低，按发布节奏 |

## 5. 参考原则

本结论只用于产品和技术决策，不构成对竞品内部实现的完整还原。商业产品能力以官方公开信息为准，开源项目复用前必须重新核对许可证和第三方依赖。原始专项文件保留研究证据，但新增结论应先合并到本卡片，避免口径继续分叉。
